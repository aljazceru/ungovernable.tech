The Week in Detail

Tor 0.4.9.12: First Post-EOL Security Release + CGO Negotiation Fix

Tor 0.4.9.12 released Sep 8 with the subject line "Fwd: Tor Project Forum: Security Release 0.4.9.12" posted to oss-sec on the same day. The release contains three classes of fix:

TROVE-class security fixes (the headline): - TROVE-2026-036: Limit DNS resolution resource consumption for IP addresses with small VirtualAddrNetwork values. Tor clients with small VirtualAddrNetwork values were especially vulnerable to memory-based DoS. Bugfix on 0.2.1.29 — a 12-year-old bug class that only recently became exploitable at scale. - TROVE-2026-042: Limit the size of consensus diffs, in bytes and in lines, to prevent a class of memory-based denial-of-service attacks. Bugfix on 0.3.1.1-alpha — another long-latent bug class. - CGO negotiation fix: Negotiate CGO cryptography with every hop that supports it. Previously we failed to negotiate CGO with hops other than the final hop of a circuit. This is the follow-through to Arti 2.6.0's "CGO always-on" (Sep 1, last week's update): Arti clients now get CGO on every CGO-capable hop, not just the last one. The promotion from opt-in to always-on only matters if every hop can actually negotiate it. - Defense-in-depth (ticket 41361): Tor clients no longer accept consensus instructions to downgrade the congestion control algorithm — a hardening move tied to TROVE-2026-042-style attacks but more general. - SRV generation double-entry fix: Two SRV records that tied on every field except one previously caused honest authorities to disagree about the resulting SRV. Fixes bug 41356; bugfix on 0.2.9.1-alpha.

Operational: - Regenerated fallback directories Sep 8. - GeoIP files updated to match IPFire Location Database, retrieved 2026/09/08. - Seccomp compilation fix with recent glibc (ticket 41317). - Controller assert fix.

The release timing is the story: 0.4.8 was deprecated Sep 1, 2026; 0.4.9.12 was released Sep 8, 2026 — seven days. Tor Browser 15.0.22 (Sep 9) is the first browser bundle on 0.4.9.12. For relay operators still on 0.4.8 who somehow survived the cut, the only safe action is to upgrade.

Tor VPN Beta Retrospective (Sep 9, by pavel)

The first long-form writeup on how Tor VPN Beta works and what they've learned. The article is a meta-post — the product is in beta and this is the report back. Key points:

  • Per-app circuit isolation — each mobile app on the device gets its own Tor circuit, rather than sharing a single tunnel. "This type of app isolation is a design choice heavily inspired by the cross-site tracking protections in Tor Browser."
  • Built on Arti — explicitly stated: "Tor VPN is built on Arti, our next-generation Tor implementation written in Rust. Under the hood, that means a new, solid technical foundation rather than patching around legacy architecture."
  • What doesn't yet work from C-tor — "There are still performance features from Tor's C implementation, like congestion control, that are not yet available in Arti. Bringing those capabilities over is part of what comes next." This is a public commitment that congestion control is on the Arti roadmap and that it's the main missing piece.
  • WebTunnel bridges — added in 1.4.0 beta: "helps Tor traffic look like regular encrypted web traffic. This makes it harder for censors to detect and block connections."
  • Reproducible builds + F-Droid — "Reproducible builds let anyone verify that the binary you're running matches the published source code, while F-Droid availability gives users a way to install and update the app without relying on Google Play."
  • UX lesson from usability testing — exit selection was the wrong lever for users trying to bypass censorship; users in censorship environments should use bridges, not pick exit locations. The current design forces connecting to the Tor network first before selecting an exit to prevent the wrong choice.
  • Where it's used — "strong adoption in highly censored regions, including Iran and Turkmenistan. This stood in contrast to Tor Browser for Android, which tends to skew more toward users in the Global North."
  • Future work — exit selection to be reintroduced "in a way that doesn't create user error in high-risk situations"; more congestion control / perf features from C-tor; broader mobile support.

The Sept 9 release is the closest thing to a "Tor VPN 1.0 roadmap" the project has published: Arti-based, per-app circuits, WebTunnel bridges, reproducible, F-Droid available, with congestion control as the named missing piece.

HOPR #8365: SURB Protocol-Version Boundary

PR #8365 (feat(session)!: generation-tagged SURB consumption, Sep 9) is the most consequential protocol change in HOPR since the SURB-ID rework. From the PR body:

⚠️ SIGNIFICANT BEHAVIOR DIVERGENCE FROM 4.0

When a return path dies deep in a 1–3 hop forward or return route, the failure is invisible to the replying side — only the SURB creator, seeing which replies never came back, can tell. This change makes the return-path identity explicit so the replying side can react precisely rather than by heuristic.

The mechanism:

  1. Creator stamps every SURB batch with a generation — a dedicated u8 (RFC-1982 serial) in SurbReceiverInfo.
  2. Creator advances generation on every return-path re-plan.
  3. Replier keeps only the highest generation it has seen — the first push carrying a newer generation clears the per-pseudonym buffer wholesale, so SURBs for the superseded (and possibly dead) path are dropped at once and the next reply uses the live path.
  4. Generation tagging is orthogonal to SurbPopOrder — FIFO is the default; LIFO remains fully functional. The two mechanisms compose: generation tagging handles an explicit re-plan; the pop order chooses consumption order within a generation.

The cost:

The SURB wire size grows by one byte, so this is a protocol-version boundary: nodes across the boundary cannot exchange SURBs. The /hopr/mix/1.2.0 bump enforces the boundary in code — mixed-version nodes will not establish the mix protocol — so ship this as a coordinated release.

This is the HOPR equivalent of Tor's CGO wire-format bump: a small change in the packet structure that breaks compatibility at the protocol boundary. The semantic difference is return-path liveness becomes part of the wire format, not just a runtime signal.

The cluster is operator-experience work: when a service node fails to start, the operator needs to see one clean error message in the log, with stderr captured, and not double-printed. This is the same UX thread as last week's silent-packet-drop instrumentation (#1114).

kpclientd hardening (Sep 7): - #1115 (Sep 7): kpclientd: fix shutdown hang and connection races. Shutdown hang that was waiting for connections to drain; races between accept loop and shutdown. - #1118 (Sep 7): kpclientd: multiple unix listener sockets with stale-socket repair. The big UX win. [Listen.Unix].Addresses lets the daemon bind several unix sockets at once, in any combination of filesystem paths and leading-@ abstract names. A single Address behaves exactly as before, so existing configs are unaffected. A crashed kpclientd leaves its filesystem socket file behind, so the next bind would fail with EADDRINUSE. Each socket is bound through a repair step: on EADDRINUSE, if the path is a socket that no live daemon answers on (a dial is refused), the stale file is removed and rebound once. A socket a live daemon still answers on is left in place, so a second instance cannot evict a running one. Abstract sockets never outlive their owner, so EADDRINUSE there is a live owner and is passed through. - #1118 also combines the prior multi-socket PR and the stale-socket-repair PR into one change.

Resilience + tooling (Sep 4–6): - #1129 (Sep 6): docker: put base port seed in compose project name. The local-dev docker mixnet had colliding ports across services; put the port seed in the compose project name so each deployment has its own port namespace. - #1127 (Sep 4): client/config: fix race condition in TestUnmarshalTOML. I2P: haoxucu Week — Three DoS-Class Fixes + Path Traversal

I2P Java I2P shipped 11 i2p.i2p commits Sep 4–10, all on the security/hardening thread (all reported by haoxucu, the same researcher who reported the SOCKS auth bypass and the bdecode recursion):

CVE-class (security-critical): - b6ce258 + b12dfad + 0d801ff (Sep 4 + Sep 8): i2psnark: Improve path traversal checks (3 commits). Path traversal hardening in the BitTorrent client's file-handling path. - 641f06f (Sep 4): i2psnark: Catch unbounded bdecode recursion. BDecoder applied no recursion limit to untrusted bencode, so a large nested list/map produced StackOverflowError that passed through every catch(Exception) on the receive path and killed the shared I2P session dispatcher thread. Fix by declaring and catching Throwable everywhere. This is the kind of bug that takes down the whole router on a single peer-supplied torrent. - ff63e0c (Sep 4): i2ptunnel: Fix SOCKS 4/4a downgrade bypass of proxy auth. The guard meant to reject SOCKS 4/4a on auth-enabled tunnels checked for legacy proxyUsername/proxyPassword properties that are no longer used for SOCKS (we now store SHA-256 digest under different properties), so when auth was enabled an unauthenticated SOCKS 4a CONNECT was accepted. Fix by removing check for legacy properties.

Operational: - a884b90 (Sep 4): Addressbook: Check for dest mismatch in action=update. Addressbook correctness. - d2392ae (Sep 4): SAM: Fix DG2/3 subsessions. SAM bridge protocol fix.

i2psnark hardening (Sep 8–10): - 7852931 (Sep 8): i2psnark: Use uppercase for infohash in magnet names. Cosmetic but standardizing. - 2f0fb93 (Sep 9): i2psnark: Request throttle adjustments. Anti-DoS throttling. - 3f17761 (Sep 9): i2psnark: Restore 2-arg getNameAndInfoHash(). Compatibility fix.

Misc: - 77f8827 (Sep 10): bump -6. Internal version bump. - cff95a3 (Sep 10): susidns: CSS tweak. UI polish.

~9,331 relays (Sep 8) is the lowest count since the early-2024 LBTM pruning pass. The trajectory since Sep 1 (10,137 → 9,331) is a ~8% drop in 7 days. The pre-existing Hetzner de-peering (Dingledine DEF CON 34: ~20% of network's relay-exit infrastructure) and the 0.4.8 EOL cut-off are the most likely explanations. The network did not collapse — it shrank to the operators who upgraded, plus whatever un-upgraded exits self-disconnected over the week.

The network appears to have stabilized around the ~9.3K range — not back to ~10.5K where it sat in mid-2026, but no longer in free-fall. The 2-week browser cadence + the new Tor VPN Beta Arti build should draw modest new-user attention (and modest new-relay donations in the long run) but no immediate surge.

Research Scan: Sep 5–11

ePrint keyword searches for mixnet, onion routing, anonymous communication returned no fresh first-line mixnet papers in the Sep 5–11 window. The active anchors remain:

  • DumboMix (ePrint 2026/1699, async anonymous broadcast with G.O.D. via Shamir-share MPC, O(1) multiplicative depth)
  • De-SyRIS (ePrint 2026/1723, decentralized Sybil-resistant identity without trusted issuer)
  • Proof-of-Uniqueness (ePrint 2026/1725, threshold-OPRF Sybil-resistant pseudonymous DIDs)
  • Cao & Green reputation-framing attacks on Nym (ePrint 2026/101)
  • Verifiable SelfMix (ePrint 2026/1617)
  • QuMixnet (post-quantum mixnet protocol)
  • MOCHA (ePrint 2025/861, IH&MMSEC 2025, Loopix client-anonymity measurement)
  • Outfox (ACM SIGCOMM 2025, simplified Sphinx for PQ)
  • Anonymous Communication on Expander Networks (ePrint 2026/1404, approved 2026-07-13) — Tufts/Brown result: differentially-private and anonymous protocols in polylog rounds with polylog server load over expander graphs.

The pattern continues: measurement + committee-based alternatives + expander-graph anonymous protocols, while the shipping work consolidates the existing primitives (CGO always-on in Arti; SURB generation in HOPR; kpclientd Unix multi-socket in Katzenpost; SDK feature gating in Nym).
