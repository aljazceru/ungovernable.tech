The Outfox removal (#7048, merged Aug 11, shipped djibouti) deserves separate emphasis because it changes the on-wire traffic class: every client talking to the mixnet — SOCKS5, WASM, native — is now Mix-packet only. The old Outfox format (a Layered-Encryption-in-the-PQ-era Sphinx variant) was always a secondary packet type; the breaking removal is the formal retirement of a never-default code path that was contributing to traffic-class confusion. For deployment: any client that pinned Outfox for forensic/fingerprinting reasons loses that capability; standard Mix-packet flows are unaffected. This is the second PQ-packet-format retirement in the mixnet ecosystem in 2026 (after Katzenpost's deprecation of the legacy non-PQ Sphinx header in the catsov migration), and both retirements are running ahead of user pushback because the alternative format has been the default for ≥12 months.

NymVPN v2026.12.4-beta.1: Pinned Gateway Blacklist Bypass

The Sep 3 beta continues the client release tempo (12.3 stable was Aug 27; .4-beta.1 lands six days later). The single substantive fix in this beta is PR #6272, titled "Make pinned gateways respect the blacklist." The body makes the bug vivid:

A pinned entry/exit gateway identity bypassed all selection filters (NotBlacklisted, MinScore, Residential, ...) via an unfiltered lookup, so a user who pinned a gateway that was actively being blocked (e.g. GFW UDP blackholing) would retry the same doomed gateway on every connection attempt forever, with no cooldown and no useful error.

This is a textbook example of a user-trust feature (pin a gateway for repeatability) silently defeating an adversary-defence feature (the blacklist), and the failure mode is exactly the wrong way around: the user keeps retrying a known-blocked path. The fix routes pinned-gateway lookups through the same filter pipeline as random selection, so a blacklisted pinned gateway is rejected with a clear "filtered from selection" error rather than a silent retry.

The CodeRabbit summary adds two more affected code paths: - Gateway error reporting now identifies invalid entry gateway identities correctly. - Selection vs filtering are now distinguishable, with clearer connection-error surfaces for unavailable / filtered / nonexistent gateways.

Also in this beta: - macOS disconnect: After disconnect, restore DNS and the physical default route, and do not re-apply the kill-switch when already disconnected — a kill-switch re-apply when the tunnel is down was leaving users with no network at all. - Win/Linux animation: replaced lottie animations with manual CSS animations (smaller binary, less native dependency). - iOS/macOS widget removal: simplification. - Component set unchanged: nym-vpnd (daemon), nym-vpnc (CLI), nym-socks5-proxy (geo-exclusion SOCKS5), nym-diagnostic, nym-setup (macOS helper). - F-Droid APK signing-cert SHA-256 still 3c98a016aa4f14a3ba185c764ed363415cf7ff3c3d328a87ffff2ff1b140ff06 (per apksigner verify instructions in release notes).

Arti 2.6.0: CGO + Congestion Control Always-On

The Sep 1 Arti release is the second numbered release in 2026 (2.5.0 stable CGO on Jun 30, 2.5.1 experimental CGO on onion circuits on Aug 4, 2.6.0 on Sep 1). Per the official blog:

This release continues our ongoing development towards using Arti as a relay and as a directory authority, with much of the work focusing on document parsing, directory mirror support, and DNS stream handling. Additionally, on the RPC front, we are making steady progress towards RPC-based configuration management. Finally, congestion control and Counter Galois Onion cryptography are both now always enabled in arti.

The two always-on promotions are the headlining moves:

  1. Counter Galois Onion (CGO) — the Sphinx successor that uses a counter-mode Galois-field construction for ~half the per-hop processing cost. Was opt-in/experimental since 2.5.0 (Jun 30); always-on in 2.6.0 is the formal "CGO is the default onion format for Rust Tor clients" milestone.
  2. Congestion Control (CC) — the flow-control layer that lets Tor clients back off when cells queue, smoothing burst loss and improving bulk throughput. Was opt-in via feature flag in 2.5.x; always-on in 2.6.0.

Both promotions are the kind that need to land before Arti ships as a default relay: a relay that only understood CGO traffic and a client that only understood pre-CGO traffic would silently drop each other's cells. Promoting both to always-on in the same release is the prerequisite for the relay-build-out work (document parsing, directory mirror support, DNS stream handling) that the 2.6.0 changelog foregrounds.

The relay + dirauth trajectory is the most consequential structural shift in 2026: when Arti can run a relay, the C-tor retirement conversation moves from theoretical to scheduled. The dirauth plugin work documented last week (compute-mds, FlavoredConsensus compile-time refactor) is in the same trajectory.

Contributors for 2.6.0: Andrew Kloet, Steven Masnada, iqdecay, pryty26, steven (plus the usual Arti maintainers gabi, dgoulet, nickm).

The 0.4.8 deprecation cut-off is Sep 1, 2026, the same day as Arti 2.6.0 and Tor Browser 15.0.21. Per Tor Project guidance:

The Tor Project has announced plans to stop supporting Tor 0.4.8 and earlier releases on September 1, 2026, as it prepares the network for the deployment of Arti, its Rust-based implementation of Tor. [...] Administrators running Tor relays, onion services, or applications that embed Tor should verify which Tor software version they are using and upgrade to the Tor 0.4.9 series or later before September 1, 2026.

Effect: un-upgraded relays and onion services lose connectivity once the deprecated directory fields are removed. Tor Browser users are not directly affected because current browser bundles already include a supported Tor version — but relay operators were on the clock.

Katzenpost: Replica Epic Closes; Ping Loss Attribution Lands

The Aug 28 update documented the 7-part replica-proxy congestion umbrella (#1091) as the operational-maturity work-in-progress. This week, the umbrella closes:

  • #1107 (Aug 29, merged): docker: simplify port architecture and fix collision issues — operator-facing fix; the local-dev docker mixnet had colliding ports across services.
  • #1105 (Sep 1, merged): client: agree on a PKI epoch instead of pinning one — substantive protocol improvement. Clients previously pinned a single PKI document, which meant a misaligned client clock or a missed round-trip left the client out of sync with the network. Now clients negotiate an epoch with the dirauth, which is more resilient to clock skew and network lag.
  • #1099 (Sep 2, merged): replica: document the proxy path as self-tuning (7 of 7) — the documentation commit that closes the epic. The replica proxy path is now self-tuning by design: sweep budget is sized to one ProxyRequestTimeout, read-repair is gated on box-not-found, and the proxy responds to load rather than to fixed schedules.
  • #1102 (Sep 2, merged): replica: gate read-repair on box-not-found and fix shutdown ordering (5 of 7) — order-of-operations correctness in the replica's repair path.
  • #1103 (Sep 2, merged): replica: size the proxy sweep to one ProxyRequestTimeout (6 of 7) — sweep budget alignment with the per-request timeout, so the proxy never schedules more work than it can drain in one round.
  • #1112 (Sep 2, merged): client/transport: harden the websocket listener — the 6-commit hardening series:
    • explicit ws://host:port listen address required (no implicit defaults)
    • websocket Origin header enforcement
    • close bound port on Close (no listener leak)
    • InsecureSkipVerify flag added as opt-in (default-secure; explicit operator override)
    • default missing listen host to loopback (no public-by-default listener)
    • Accept/Close race + Origin coverage (race-condition correctness)
  • #1114 (Sep 3, merged): server: instrument seven silent packet drop sites — the first step toward attribution: before you can say which node is dropping packets, you have to count the drops per drop-site.
  • #1120 (Sep 3, merged): Ping probabilistic packet loss attribution — the pay-off:
    • Compare service nodes too, not only mix layers (so loss is attributed per node, not per kind of node)
    • Fix two ways the loss estimate was wrong (sample-bias and confidence-interval fixes)
    • Explain the attribution maths (probabilistic loss-attribution formulas documented)
    • Attribute loss to nodes, with the uncertainty stated (each attribution carries a confidence)
    • Client reports the route a message took to the thin client (so external observers can correlate observed throughput with the actual path)

The combination of #1114 + #1120 is a network-wide attribution layer for Katzenpost packet loss: thin clients now get probabilistic per-node loss estimates with stated uncertainty. This is the kind of measurement primitive mixnets need in order to defend against selective-loss attacks (a node that drops only traffic from a specific sender or to a specific recipient, in order to deanonymize them) — and until now, mixnet operators had to rely on aggregate counts, not per-node attribution.

The PIX supervision track is now visible in the public commit stream as a coordinated effort: deposit plumbing (#8362) → test reliability (#8336) → supervisor (#8237) → parameterized admission (#8377).   • De-SyRIS (ePrint 2026/1723, decentralized Sybil-resistant identity without trusted issuer)
  • Proof-of-Uniqueness (ePrint 2026/1725, threshold-OPRF Sybil-resistant pseudonymous DIDs)
  • Cao & Green reputation-framing attacks on Nym (ePrint 2026/101)
  • Verifiable SelfMix (ePrint 2026/1617)
  • QuMixnet (post-quantum mixnet protocol)
  • MOCHA (ePrint 2025/861, IH&MMSEC 2025, Loopix client-anonymity measurement)
  • Outfox (ACM SIGCOMM 2025, simplified Sphinx for PQ)

The research frontier continues to be measurement (MOCHA-style client-anonymity simulation, Katzenpost's per-node loss attribution) and committee-based alternatives to mixnets (DumboMix), rather than new mixnet protocols. The pattern: the field is consolidating around the existing primitives (Loopix/Sphinx/Katzenpost-catsov) and shipping them, while exploring committee-based asynchronous broadcast as a substitute for federated-mixnet trust models.
