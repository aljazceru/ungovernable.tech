2. GnuPG 2.5.22 (2026-08-31) — TOFU Trust Model Fixed

The dominant OpenPGP implementation shipped its 2.5.22 release on 2026-08-31 (NEWS). The WoT-relevant changes:

Bug fixes (T8404):

gpg: Fix TOFU trust models to actually check UTK signatures.

This is the most consequential change in the entire 2.5.x series for WoT operations. The TOFU (Trust On First Use) trust model has been the de-facto fallback for OpenPGP users who don't want to maintain a full Web of Trust — it's what gpg --trust-model tofu activates, and it's what most modern OpenPGP clients default to when they can't resolve a certification path through the WoT. The fact that it wasn't actually checking UTK (Ultimately Trusted Key) signatures meant the most popular non-WoT trust model was silently making weaker validity assertions than users thought. The fix means: after upgrading to 2.5.22, every TOFU-validated key will be re-evaluated against the UTK set, which can change trust status for keys that were previously validated only against a TOFU-good rating. Users on a gpg earlier than 2.5.22 have been trusting keys more than they should have.

WoT-adjacent fixes also in 2.5.22: - bkuptocard regression fixed ([T8344]) — long-standing pain for users who move keys between OpenPGP smartcards and host trust databases. The WoT consequence: trust signatures stored against an old card-resident fingerprint could be silently dropped on backup, breaking certification paths. - gpgsm: Emit issuer and serial no. when the certificate is not found ([T8363]) — X.509 path-building reliability. - gpgsm: Return 0 if decryption of multi recipient file succeeds ([T8340]) — affects group-encryption workflows where a recipient-validation failure could cascade into a "no recipients" false negative.

Other 2.5.22 changes: Windows GpgOL registry-key surfacing (Sept 2), Nitrokey 3 added to pcsc-shared interference detection (Sept 2), LDAP upload flags now also work for KS_SEARCH (Sept 2 — used by gpg --keyserver-options), partial-file-guard fix ([T8399]), new primary option for --card-edit generate ([T8344]). 7 commits since Aug 27; 975★ (up from 971).

Why this matters for WoT: The TOFU fix is not on the same hot path as bkuptocard or gpgsm multi-recipient, but it is the most-advertised line in the release notes — and it is the one that, if a maintainer is reading the NEWS file before bumping their tooling, would prompt "huh, should I finally do that PQ Nostr thing now?" The empirical correlation with the kind:10203 bump is suggestive, not conclusive — but two NIP-85 publishers landing on the same day as a GnuPG release that improves TOFU correctness is the kind of coincidence the freedom-tech community would notice.

The 2.5.23 cycle is now open; T8425 is the release-info page.

3. Sequoia: 16 PQC Commits in a Week — The Doc Era Is Over

This is the largest non-trivial OpenPGP-PQ development since RFC 9980 was published in mid-2025. After three weeks of SLH-DSA documentation and dependency bumps, Sequoia's main branch received 16 commits since 2026-08-27 with substantial PQC content:

Aug 27 — FIPS integration lands: - openpgp: Load FIPS provider in permissive mode (ddd5d78b) - Merge branch 'jjelen/fips' into 'main' (1f52b67d) - 4× XXX: Use temporary version of ossl (f8cf53e7, 7dc30d06, 8c97dd4c, 34ffea8d, e4d69148) — these are scaffolding commits enabling the FIPS OpenSSL 3.x provider to be loaded alongside the standard provider, which is a prerequisite for FIPS-validated ML-KEM/ML-DSA operations.

Aug 29 — PQC algorithm IDs assigned (the historic week): - openpgp: Move NIST and Brainpool PQC algorithms to assigned IDs (cb912137, b4bfa8d4) - openpgp: Add NIST and Brainpool PQC cipher suites (850ea66d, ff422bd7) - openpgp: Update NIST/BP test vectors for assigned algorithm IDs (6dfd49d1) - openpgp: Require ossl 1.5.2 (f42d6c52) — pins the OpenSSL dependency that supports these algorithm IDs. - 2 merges: fluppe2/pqc-nist-bp-assigned-ids → malte/integrate-nist-…, fluppe2/pqc-nist-bp-cipher-suites-upstream → malte/integrate-nist-…

Aug 31: - Merge branch 'neal/insert-packets-merge-components' into 'main' (b3572827) — packet-insertion refactor that enables ML-KEM encapsulation packets to be assembled cleanly with existing v6 OpenPGP certificate structures.

Why "Move to assigned IDs" matters: OpenPGP algorithm identifiers are split between IANA-assigned numbers and "private/experimental" ranges. Until this week, Sequoia's PQC implementation was using experimental IDs — meaning other implementations could not interoperate. Moving ML-KEM, ML-DSA, and Brainpool variants to their assigned IANA IDs means a Sequoia-generated PQ-signed message can now be verified by an OpenPGP.js v6 client that also implements the same IDs, and vice versa. This is the interoperability step that turns "two prototype implementations" into "two production implementations."

The complementary Cipher Suite commits are the OpenPGP analogue of TLS cipher suite negotiation: they let two peers advertise which PQC combinations they support (e.g., "ML-KEM-1024 + ML-DSA-87 + AES-256-GCM + HKDF-SHA-512") and pick a mutually supported one. This is what RFC 9580's AEAD container infrastructure was built to support — and until this week, no OpenPGP implementation had wired the PQC cipher suites into the actual negotiation path.

The FIPS work is the other half: FIPS-validated cryptography is a hard requirement for any US federal customer and most large enterprises. The permissive-mode FIPS provider load means a Sequoia-built OpenPGP application running on FIPS-mode OpenSSL can use the FIPS-validated ML-KEM/ML-DSA implementations while still using non-FIPS code paths for non-PQC operations. This is the configuration the Sequoia team has been pointing toward since the NLnet funding announcement, and it shipped.

No new release yet — Sequoia last released 2.4.1 on July 9. But the gap between "code on main" and "a usable 2.5.0 release" just became a few weeks of stabilization rather than a few months of feature work. For freedom-tech: when a 2.5.0 ships, the dominant Rust OpenPGP library will be able to do PQ signature verification on a key it has not seen before, with algorithm IDs interoperable with OpenPGP.js v6 — closing the loop that the nostr-wot team's PR #2434 was trying to open on the Nostr side.

Strategic Analysis — Convergence Without Ratification

The two tracks are now landing in the same week

Last quarter's framing was "the institutional OpenPGP track advances by documented steps; the insurgent Nostr track freezes once the specs are written." That held through August. This week it inverted on the institutional track while the Nostr track held its plateau.

The GnuPG 2.5.22 TOFU fix and the Sequoia PQC algorithm-ID assignments are the kinds of changes that took the longest possible time to land because they are infrastructure-deep. Moving PQC algorithm IDs from experimental to IANA-assigned is the kind of patch that requires an implementer to read RFC 9580 §9, RFC 9980 §5, and the IANA OpenPGP registry and decide that this is the right moment to break any forward compatibility for code paths that were using experimental IDs. GnuPG fixing a long-standing TOFU bug is the kind of patch that requires someone to write a regression test, demonstrate the bug, get it reviewed, and land it — work that nobody is paid to do unless the bug is embarrassing enough. Both landed this week.

Why it matters for the Nostr side: the nostr-wot org's PR #2434 is a NIP that says "let's use the same cryptographic primitives that Sequoia and GnuPG are now wiring up." PR #2434 cannot move without fiatjaf's approval. fiatjaf has not been heard from on the issue since Aug 11. The institutional track is moving anyway — not because Nostr approved it, but because the IETF OpenPGP WG did, and because the FIPS-validated OpenSSL provider now exposes the algorithms. The Nostr PQ shadow protocol is now using a stack that exists whether or not the NIPs merge it.

The kind:10203 stair-step is real, but small

Two new publishers in 13 days is not a wave. It is a single coordinated event (the two attestations were signed within seconds of each other on Aug 31 10:22:05 UTC) by two maintainers who were waiting on something — and that something is most likely the GnuPG 2.5.22 release with its TOFU fix, or perhaps just the general news cycle around PQC. The August 18 single event (one new publisher in 7 days) was similar in shape, but smaller. The launch-cohort step (22 in 48 hours Aug 10–11) was the kind of step you get when a project publishes its spec and the founding team plus interested observers run the tool once.

The right read is: each institutional PQ release prompts a small stair-step, not a wave. Sequoia's 16 commits this week haven't shipped yet (no new release); when the next Sequoia 2.5.0 ships, expect another 1–3 new publishers within 48 hours. The total ceiling is probably 100 in the optimistic case, 50 in the realistic case, and 24 in the pessimistic case. None of these scenarios put kind:10203 into "you can rely on it for production" territory; all of them put it into "the experiment continues to work."

The newsroom has passed its first real operational test

Fourteen daily runs, twelve published, two skipped, zero paused, zero failed. The kill switch (content/news/PAUSE) has not been triggered in production. The pause logic is documented and reviewed; it has just never had to fire. The Daemon-network-relevant pattern — structured-API-only sourcing, log-every-run semantics, kill-switch-as-file, in-repo editorial governance — is now a working artifact rather than a design proposal. The freedom-tech takeaway is concrete: a small organization with no full-time editor can run a daily publication on the strength of a 7.5 KB playbook, as long as the playbook is enforced by the agent itself and the failure modes are observable in git.

The next test for the newsroom is the first contested factual claim. So far the agent has only covered uncontroversial protocol additions (NIP-A3, NIP-67, NIP-84). The NIP-A3 rewrite story — which has a verbatim commit message with mild editorializing ("Rewrite NIP-A3 because jesus christ.") — is the closest to opinion the agent has published, and it reported the rewrite neutrally without commenting on the original. The first time the agent has to write something like "this NIP is being contested" or "this client released a controversial update," the playbook's editorial rules will be tested for completeness.

Pyramid's revival is the only non-empty data point for "WoT is moving forward"

This week's biggest under-the-radar development is fiatjaf making pyramid's WoT-distance thresholds operator-configurable. It looks like a minor UX change ("you can pass a string now"); it is actually the first time the WoT-policy surface of a major Nostr relay has become runtime-tunable without a rebuild. Until now, if you wanted to run a WoT-gated relay with different distance or popularity thresholds than the default, you forked pyramid and edited constants. Now you write a config file. This is the same shift that made wot-relay and Chronicle practical to self-host last year: removing the "fork + rebuild" step from operator customization. The shift doesn't make the news, but it is what makes the difference between "an experimental pattern that fiatjaf runs in a corner of his relay set" and "a deployment pattern that any operator can adopt."
