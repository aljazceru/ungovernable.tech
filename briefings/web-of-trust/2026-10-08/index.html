The Week in Detail

Nostr-WoT extension v0.8.11 (Oct 6 21:45 UTC) — Account Archive and popup startup

The v0.8.11 release notes open with five Highlights: Add Account Archive in Settings: manual or scheduled sync across all selected relays, encrypted local storage, relay groups and resumable checkpoints. Sync relays concurrently with shared deduplicated storage. Show event counts, archive size, progress, error details and independent per-relay retries. Export and import password-encrypted archives. Migrate eligible original signed events to a verified destination after confirmation, retry failures once after the first pass, and inspect remaining failed events. Authenticate archive queries when relays request it, including responses prefixed with ERROR:. Retry recoverable failures up to three times and report relay configuration failures accurately. Prevent stalled language or theme initialization from leaving the popup blank by rendering bundled defaults after a bounded wait.

The release is shipped via PR #39 "Fix popup startup and add encrypted Account Archive", which was renamed from "Add encrypted account archives" before merge. The PR opened Oct 5 04:01:38 UTC, was force-pushed, and merged Oct 6 21:41:43 UTC at commit 989930a — 41 minutes before the v0.8.11 tag. The v0.8.11 release tarball carries 989930a directly; the v0.8.12 release tarball is a different commit (6976903) on top of the same merge. This is the standard pattern: each release commit is a self-contained snapshot, the tag points at it, and the next release tag points at a different commit on main.

The Archive section's operational detail is the key part. Configure hourly, daily or weekly automatic sync, or sync manually. Archive settings use profile relays by default, reusable relay groups and validated custom relay URLs. Archive does not add an onboarding step. The phrase does not add an onboarding step is the structural argument: this is a user-controlled feature, not a user-mandated one — the extension does not require the user to set up archiving to use it. The rest of the section: Preserve existing records and per-relay checkpoints during retries. Event counts include verified events already stored; the archive total stays deduplicated. Continue active work between bounded slices without waiting for another alarm. Keep migration progress, results and pause controls inside Migrate archive. Start migration checks the destination with a normal bounded query and opens a confirmation before publishing. Migration preserves local data and original signatures, and skips ineligible events. Resume the failed-event retry pass after worker interruption. Show remaining event IDs, kinds, dates, relay responses and attempt counts in Failed events.

The "eligible original signed events" phrasing is the load-bearing one. The migration path moves events that (a) are original — not derivatives or auth-tag re-broadcasts, (b) are eligible — pass signature verification, (c) are signed — the original signature is preserved, the migration does not re-sign, (d) go to a verified destination — the destination relay is queried with a normal bounded query first. The data model is "preserved across migration, never rewritten" — the same model as kind:10203's "the original signature is the artifact". This is consistent with the W39 + W40 reading of the org: rebuild what is broken at the cryptographic envelope, never alter what the user signed.

The Popup startup section is the second headline. Render bundled English and theme defaults after 1.5 seconds if preference initialization stalls, then apply saved preferences when available. Preserve the existing splash and fade timing. This is a defensive bound: a 1.5s timer guarantees a non-blank popup, even if the i18n / theme init path is hung. The previous v0.8.10 release also addressed a startup regression (the theme selector under the menu footer, etc.) — v0.8.11 is the architectural fix for the worst case (a blank popup is worse than a wrong theme).

The Maintenance section covers two more. Pin the test-only DOM dependency to a working version and make the remote-signer refusal fixture use an unlocked test vault, preventing stalled compatibility tests without weakening production unlock checks. The fixture change is the operationally interesting one: a test that uses a locked vault for the "remote-signer refusal" case can flake in CI when this library's password-derivation timing varies. Unlocking the fixture vault makes the test deterministic without weakening the production check (the production check is on a different code path). Document Archive storage, authentication, import/export and migration boundaries, and update source-build and Mozilla reviewer instructions. The doc-update is the Mozilla reviewability argument: an AMO / Chrome Web Store reviewer needs to know what archive does without reading the source — the boundaries are the safety properties, and the documentation now names them.

Nostr-WoT extension v0.8.12 (Oct 6 22:22 UTC) — passwordless archive import

v0.8.12 is 37 minutes and one commit on top of v0.8.11. The release body: Download and import Archive files without a password. Imports verify that events belong to your account and have valid signatures; older encrypted exports remain supported. Archive download and import dialogs now open above the entire popup. Two changes; one substantive, one cosmetic.

The substantive change: a passwordless archive format. The v0.8.11 archive is encrypted with a password — the user picks a password, the file is encrypted with that password, and the password is the recovery key. v0.8.12 adds a passwordless format that binds the archive to the account's pubkey via signature verification on import. The release notes: Imports verify that events belong to your account and have valid signatures. The verification is: each event in the archive carries a Nostr signature; the import path checks that the signature verifies against the archive's claimed pubkey; and the claimed pubkey is the active account on import. A passwordless archive can be safely stored in cloud backups, sent to a friend, or committed to a public repo — the safety is the signature, not the password. The catch is that the archive is only useful to the same pubkey — a different pubkey would import and see the events, but the events would not be reachable from that pubkey's normal Nostr view (they were signed by someone else).

The older encrypted exports remain supported line is the migration path. A user who has v0.8.11 password-encrypted archives can import them into v0.8.12 without re-exporting. The reverse path is not stated — v0.8.11 cannot import v0.8.12 passwordless archives. This is asymmetric by design: the new release is a superset of the old.

The cosmetic change: Archive download and import dialogs now open above the entire popup. This is a z-index / focus-management fix; a dialog that opens behind the popup cannot be reached by keyboard navigation, which is an accessibility bug. v0.8.12 fixes it.

The Compass #43 coverage summarizes the v0.8.11 + v0.8.12 pair: Account Archive synchronizes original signed events across relays with checkpoints and encrypted local storage. Version 0.8.12 makes exported archive files passwordless while checking signatures and account ownership on import; older encrypted exports remain supported. Exported files and encrypted local storage have different privacy boundaries. The two-clause summary captures both the operation (sync + import) and the security model (signed-at-transport, encrypted-at-rest).

@nostr-wot/bunker 0.2.0 — first NIP-46 server-side package

@nostr-wot/bunker 0.2.0 was published to npm 3 days before Oct 8, putting the publish date at Oct 5. The README: The NIP-46 responder: the bunker / remote-signer side of Nostr Connect. @nostr-wot/signers and the browser extension are NIP-46 clients; this is the other half, the thing they talk to. This is the first public server-side Nostr-WoT package — the prior packages (@nostr-wot/sdk for queries, the extension for the user-side signer) are all client-side.

The package's design contract, verbatim: It is a transport adapter and nothing more. It listens on relays for kind 24133 requests addressed to a connection key, decrypts the NIP-44 payload, hands the request to one injected function, and publishes the encrypted response. Vaults, permissions, accounts and approval UI never enter this package: every policy decision is the handler's. The split is the same as the extension split: the package is the transport, the host application is the policy. A bunker built on @nostr-wot/bunker has to implement the handler — the function that receives a decrypted NIP-46 request and returns the response. The handler can be a vault, a HSM, a paper-key cold store, a YubiKey-backed signer, or — and this is the threat model — nothing at all, in which case the bunker refuses every request.

The release notes specify a few correctness properties: verified replay bounds and authenticated pairing state. Hosts still own approvals, key storage and durable revocation state. The replay bound is the standard NIP-46 id uniqueness check (each request id can only be answered once); the pairing state is the secret-based pairing protocol from NIP-46 §"Connecting to a remote signer". Both are enforced by the package, not by the host.

The npm install: npm i @nostr-wot/bunker nostr-tools. The peer is nostr-tools; the package itself has 2 direct dependencies (likely nostr-tools and a NIP-44 helper, though the dep graph was not pulled). The package is ESM-only: ESM only, as every package in this release is. import it, or await import() it from CommonJS; there is no require entry point. One format rather than two is deliberate: a dual CJS/ESM build can be loaded twice in one process, once per format, and a package that holds state (a vault session, a bunker's client and secret registries) would then keep two of it. The argument is the same one Sequoia-PGP made for the sequoia-openpgp crate: stateful packages that load in two formats hold two state machines, which is a bug. The org is consistent in this — the previous @nostr-wot/sdk is also ESM-only.

The package is at v0.2.0, not v0.1.0 — implying an internal v0.1.0 was used in development, and the v0.2.0 is the first public release. There are 0 dependents (per npm), so no production deployments have been built on top of it yet. The threat model is the same one the extension has had: hosts own the policy, which means a malicious host can refuse requests, but a malicious host cannot extract keys from the package. The trust boundary is the function-call interface.

kind:30385 dispute — still open at 75+ days

PR #2418 "NIP-XX: Trusted Relay Assertions" (Letdown2491, opened 2025-07-18) and the NIP-85 spec are still in conflict over kind:30385. NIP-85 (master, unchanged) allocates kind 30385 to NIP-73 external identifiers, with d tag value (space, indicating user). The NIP-85 purpose is to publish trusted assertions — Web of Trust scores, engagement metrics, reputation data — for one of four subjects: pubkeys (kind 30382), regular events (kind 30383), addressable events (kind 30384), or NIP-73 identifiers (kind 30385). PR #2418 re-uses kind 30385 for a different purpose: a relay asserting a list of relays a pubkey trusts, with an algorithm tag (e.g. v0.3.0) and a relays list. Letdown2491's reference implementation has shipped 100+ events on nos.lol under the disputed kind with algorithm=v0.3.0.

The Sept 10 W39 update named this as a protocol collision. The Sept 24 W40 update noted the reference impl had shipped more events. The Oct 01 W40 update noted 27 days since the last comment on PR #2418. The Oct 08 reading (this update): 75+ days since PR open, 130+ days since Letdown2491's reference impl went dormant, last comment 34+ days ago, no proposal to renumber, no proposal to merge with NIP-85 reconciliation. The most likely outcome is the collision becomes a de-facto standard — NIP-86 absorbs the method semantics, kind 30385 has two documented uses with different tag patterns (the d tag distinguishes them: NIP-85 expects for the user case, NIP-XX expects a relay-list value), and clients that consume both have to switch on d-tag shape. The downside is spec ambiguity; the upside is that 100+ already-shipped events become reachable.

The Nostrability issue #301 "Trusted Assertions [NIP-85] Positive Interoperability Tracker" is the canonical cross-implementation reference. It tracks clients that read NIP-85 assertions (kinds 30382–30385, 10040). The org's contribution: Spec: [link to nips/85.md]. nostrCI schema: [schemata#91]. NIP-85 enables clients to outsource Web of Trust calculations to trusted service providers. Providers publish signed assertion events; clients fetch and display pre-calculated trust scores, engagement metrics, and reputation data. Kinds: 30382, 30383, 30384, 30385, 10040. The issue is a positive-interop tracker (what works), not a kind-30385 collision tracker (what conflicts). It is a useful reference for the question which clients support NIP-85, but it does not adjudicate the PR #2418 collision.
