2. Nostr-WoT Extension v0.7.0 — GitHub Release Shipped + The Full Audit Picture

Last week's update closed with "v0.7.0 is pending store publication" and noted the AMO/Firefox-pending review process gates disclosure. On 2026-09-10T22:29:29Z (one day after last week's update was written) the project tagged v0.7.0 as an annotated GitHub Release. The tag SHA is d00074612d2c05aa53998a1fcbfd0c1a37d3eca6; the prior tags visible in the tag refs API were all older (v0.5.2 was the last one before the v0.6.0/v0.7.0 cycle that began on integration/round-2).

The full CHANGELOG.md body for v0.7.0 enumerates substantially more than the last week's update captured:

Security audit A1–A7 — the project's first ever public security audit. Per CHANGELOG.md:

Addressed security audit A1–A7: bind payment/signing authorization to account and vault session; honor account-specific payment denials; cancel stale operations after lock, switch or wallet replacement; reject credential-bearing redirects and insecure provisioning; enforce request and payload limits.

This is the most important single fact in this week's update: a Nostr-WoT extension that holds payment/signing authority for users has now had an external security audit, the findings have been addressed, and the audit's response is in a public GitHub Release. No specific auditor is named in the changelog; the audit artifacts (PDF, methodology) are not linked from the changelog and are not in the repo as of Sept 17.

Two security-adjacent wizard fixes — the worst kind of bug because they touch account creation:

Two security-adjacent fixes in the wizard. Both PasswordStep and SubAccountStep called vault_unlock directly, so the add-account path was an unthrottled password oracle while every other unlock carried the escalating lockout. Worse, PasswordStep offered the empty password to any locked vault rather than only never-lock ones — and the background charges failed unlocks to a persisted guard, so an abandoned wizard re-running that probe on each popup open could lock a user out of their own vault in five opens without them typing anything.

This is the kind of bug that gets a CVE in a security-focused project; in this codebase it gets a CHANGELOG entry and a regression test. The Sept 10 update missed this entirely because it focused on the relay-reader fix.

The zap-redirect forgery fix — still the headline, now with the audit context. Per CHANGELOG.md §"Fixed — security":

Two relay readers accepted events without verifying signatures. fetchKind0Read and fetchMuteList open their own sockets and matched on pubkey and kind only — fields a relay merely asserts. Both feed a read-modify-write of a replaceable event that the user then re-signs and publishes, so a forgery was not just displayed: a kind:0 carrying the attacker's lud16 would have redirected the user's zaps, and a forged kind:10000 replaces their NIP-44-encrypted private mutes with ciphertext the relay chose. liveQuery verified all along; these two bypassed it. A relay that serves a forgery can no longer vouch for emptiness. Rejecting the bad event was not enough on its own — these reads also report reachable, and reachable: true with nothing found means "safe to overwrite", so garbage followed by EOSE would still have wiped a profile. reachable now counts only sockets that answered and never served an invalid event. See docs/security.md §12.1.

docs/security.md §12.1 is the public disclosure artifact for this vulnerability. It is referenced in the changelog but does not appear to have been blog-posted or X-threaded yet. Last week's reading ("the disclosure is gated by AMO/Firefox review") holds, but the GitHub Release is the immutable public record — even if all extension stores reject the submission, the audit, the fix, and the disclosure are in git.

Stack/paint fixes — the "popup painting over its own consent surfaces" cluster:

The lock screen and the approval sheet could be painted over by a deposit QR. Five dialogs escaped to #root portals to get out of a containing block created by the menu's slide animation. That cause was fixed in c01f087; the portals outlived it, and because they landed outside .card's stacking context they outranked every consent surface. All five now render in place. The in-popup unlock prompt sat at z-index: 360 while wallet dialogs sat at 500 — the surface demanding an unlock outranked the one asking for it. There is now a stacking ladder in theme.css, and --z-lock beats every task surface by construction.

PBKDF2 iterations 210,000 → 600,000 — the most subtle bug in the security cluster. Per docs/security.md §1:

User password fed to PBKDF2 with SHA-256, 600,000 iterations, random 32-byte salt, producing a 256-bit AES key. 600,000 is OWASP's recommendation for PBKDF2-HMAC-SHA-256. The vault previously used 210,000 — which is OWASP's figure for SHA-512, the wrong row of the same table, so the parameter looked calibrated while being ~2.9x weak. The record now stores the iterations it was written with; a record without that field predates the change and is read back at 210,000, then transparently re-encrypted at 600,000 on the next successful unlock, since that is the one moment the password is in hand. A failed upgrade is logged and leaves the working record alone.

The migration story is the right one (transparent re-encryption on next successful unlock) — but the existence of the bug is what matters for freedom-tech: a wallet with a deliberately-low KDF and a documented "looks calibrated" rationale is the same shape of bug as a TLS library that documents its bad cipher without flagging it as a known weakness.

The Tailwind v4 refactor — not WoT per se, but the test suite that protects WoT. Per CHANGELOG.md:

Tailwind v4, wired to the tokens that already existed rather than to its own defaults, so a utility and a stylesheet reaching for the same idea get the same value. The spacing scale needed no mapping at all: it was already exactly n x 2px, so p-6 is --sp-6 by construction. 58 stylesheets became 24; 6,280 lines of CSS became 1,115. What remains is what utilities genuinely cannot express: custom @keyframes, adjacent-sibling rules, :global, 3D transforms, and the handful of properties a caller sets through an inline custom property. Preflight is deliberately off. It is a global reset — every margin and padding zeroed, headings unsized, lists unmarked — and the stylesheets here were written against browser defaults. Switching it on changes the spacing of every paragraph and heading at once, which no test in this repo can see. It goes on as its own change, verified with the extension loaded.

This is the structural test discipline story of the release: "tests/tailwind-classes.test.ts checks every static class name against the generated stylesheet — verified against typos planted in four positions, after two earlier versions of the scan passed while a planted typo sat in the source." The same pattern appears for the test inventory (tests/test-registration.test.ts), the CSS-selector test (tests/css-selectors.test.ts), and the form-error role="alert" consolidation.

Star count: 8, unchanged from last week. The extension is not yet on AMO/Firefox public release for v0.7.0 — the AMO/Firefox review process gates that. Chrome Web Store / Edge Add-ons / Opera Add-ons are not measured in this library's automation. The Sept 17 tripwire for next week: whether AMO/Firefox publishes v0.7.0 publicly.

Strategic Analysis — The GnuPG ↔ Extension ↔ Nostr-WoT Triangle

The institutional PQC track woke back up — but only GnuPG moved

Last week's reading was "institutional track cooled, insurgent stack had its busiest news week." The reading inverted this week, but only partially: GnuPG moved (RFC 9980 merge, 2.5.23 imminent) while Sequoia stayed silent (24 days, last release July 9). The institutional track is no longer monolithic — GnuPG and Sequoia are on different cadences. GnuPG's Sept 11 merge of wk/rfc9980 puts it 2–3 weeks ahead of where it was a week ago. Sequoia's 24-day silence is now the longest gap in 2026.

For freedom-tech, the practical implication is that GnuPG 2.5.23 is the next major PQC-Nostr-relevant release to watch. Once 2.5.23 ships with RFC 9980 default-on, the OpenPGP-side PQ identity story has a usable implementation. Until 2.5.23 ships, the only "PQC is in OpenPGP" claim that holds is "GnuPG has merged RFC 9980 to master and the parser accepts the packets but the release is unreleased." This is a story about implementation, not adoption — and it's the same story NIP-XX PQ Identity Keys (PR #2434) has been waiting on for 37 days.

The Nostr-WoT extension v0.7.0 release is the soft-disclosure story of 2026

The Sept 10 weekly update called the zap-redirect forgery fix "the most consequential WoT-adjacent vulnerability of 2026." The Sept 11 tag of v0.7.0 as an annotated GitHub Release upgrades that claim: this is the first Nostr-WoT extension release with a complete security audit response in the changelog, and the audit findings are visible to anyone with a web browser.

The disclosure posture has now shifted: - Last week's posture: vulnerability fixed, changelog entry in main, AMO/Firefox review pending public release. The disclosure was gated by the store review process. - This week's posture: vulnerability fixed, changelog entry in main, annotated GitHub Release tag with immutable SHA, CHANGELOG.md enumerating 7 audit findings + 2 wizard fixes + the zap-redirect fix + the PBKDF2 fix. The disclosure is in git history regardless of what the stores do.

The next disclosure artifact — a public blog post, an X thread, a NIP — is still missing. The extension team has chosen git as the disclosure channel. For a security researcher who runs a Nostr wallet, this is enough to know that v0.7.0 is the version to install; for a casual user who only reads blog posts, the disclosure has not reached them.

The kind:30385 collision is becoming structural

Last week's reading: "the kind:30385 collision is the new structural risk vector." This week's reading: the collision is 13 days old and growing. The implementation-vs-specification drift is now 110 days old (the reference impl last pushed June 29). The 100 published events on nos.lol under the disputed kind are unchanged. fiatjaf has not commented.

The structural risk is now concrete: any client that reads kind 30385 today will mis-interpret Letdown2491's events as NIP-73 identifier assertions. This is no longer theoretical; it is a production data-integrity problem. The NIP-85 spec has not been updated since June 13. The reference impl has not been updated since June 29. The NIPs repo maintainers have not commented since Sept 4. The implementation has drifted from the spec in silence.

For freedom-tech, this is the same shape of bug as a draft RFC with divergent implementations that nobody reconciles. The pattern recurs in Nostr — kind:1 reply semantics, kind:30023 long-form, kind:9735 zap receipts — each had a period of implementation drift before a NIP was either merged or deprecated. The kind:30385 case is the first time the drift has happened at the assertion-provider level, where a provider's published events are the source of truth for other clients' decisions. That makes the structural stakes higher than for ordinary event kinds.

The newsroom's blast radius is the soft tripwire that tripped

Last week's reading: "the newsroom's first paused or failed daily run is the next tripwire; kill switch untested in 41+ runs." This week: the first pending run, not a paused or failed run — but the soft-pending path is now in the public log.

nip-22-amethyst-loads-nested-comments (5 sources; seven editions and social copy prepared; PR CI, merge and production verification pending; LinkedIn and Nostr delivery pending scheduled workflow and durable ledger).

The pending state captures the agent's own understanding of where it is in the pipeline — content PR open, CI run, merge, production deploy, then social posting on a separate scheduled workflow. The 8-minute gap to published is the time between "PR merged and deployed" and "social channels posted with durable receipts." The agent now logs this gap explicitly and uses the next run to verify the social channels landed.

This is a soft-tripwire rather than a hard tripwire — the agent did not pause or fail, it just didn't complete in a single run. But it is the first observable instance of the agent exercising its multi-step workflow publicly. The cumulative tally (8 published, 3 skipped, 0 paused, 1 pending→resolved, 0 failed) is still pristine in the sense that no hard tripwire has fired. The Sept 16 entry is the first non-publish state in the log.

Amethyst v1.15.0 is the client-side event the newsroom was waiting for
