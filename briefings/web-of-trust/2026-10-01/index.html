2. NIPs Repo: Three Merges in Three Days — NIP-39 Unification + kind:10040 + kind:10021

The NIPs repo's three W40 merges represent the most active weekly merge cadence of the year — and each merge closes a structural gap in the Nostr protocol surface.

PR #2483 (TheSeydiCharyyev, merged Sep 25 by vitorpamplona) — Four missing kinds added to the Event Kinds table

The PR body is precise:

Four kinds are defined in their NIPs but were missing from the Event Kinds table.

  • 10040 — NIP-85, section "Declaring Trusted Service Providers": "Kind 10040 lists the user's preferred source for each result." The table already lists NIP-85 kinds 30382, 30383 and 30384.
  • 21059 — NIP-59, section "Ephemeral Gift Wrap Event Kind". The table already lists kind 1059, which this one mirrors with ephemeral semantics.
  • 33534 — NIP-43, section "Role Definitions": "Relays MAY publish a kind 33534 event which defines a role". The table already lists NIP-43 kinds 8000, 8001, 13534, 28934, 28935 and 28936.
  • 38000 — NIP-87 names it in its first line: "This NIP describes kind:38173, kind:38172 and kind:38000". The other two are already in the table.

The freedom-tech takeaway is in the 10040 row specifically: without 10040 in the table, a reader has to know NIP-85 exists, find the "Trusted Service Providers" section, and know that 10040 is a preference-list row — most clients can't subscribe to "all kinds with tag X" without enumerating, and the kinds table is the canonical enumeration. With 10040 in the table, the kind is a first-class addressable entry — clients subscribing to kind:10040 receive the user's choices for "who computes my trust scores / who is my trusted relay oracle" without the NIP-85 deep-link. The W40 surface for trust-source preferences is now structurally equivalent to the surface for trust-source assertions (kinds 30382 / 30383 / 30384, all in the table for >1y).

PR #2417 (fiatjaf, merged Sep 27 by vitorpamplona) — Favorite follow sets → kind:10021

fixes #2413 (comment)

The PR moves favorite follow sets to kind:10021 because the previous kind "is already being used" for something different. This is a clarification of NIP-51 — favorite follow sets and favorite relay sets share NIP-51's "lists" surface, but they need distinct kinds to avoid clients subscribing to one and receiving the other. The W40 surface for favorite follow sets is now first-class addressable.

PR #2486 (alexgleason, merged Sep 27 by fiatjaf) — NIP-39 unification

The PR is the first published measurement of NIP-39 proof-validity in the wild. From the PR body:

One verification text

Each claim type currently specifies a different proof text (github has no quotes around the npub, twitter uses an entirely different sentence, mastodon and telegram use quotes). This replaces them with a single string for every claim type:

Verifying that I control the following Nostr public key: <npub encoded public key>

It also says verifiers SHOULD accept any proof by <identity> that contains the user's npub, so existing proofs keep working.

Why the lenient verification rule

I surveyed kind 10011 across 11 major relays (5,859 authors, 756 with i tags) and fetched every github/twitter/mastodon/telegram proof. Of the 611 proofs, only 27 contain the exact spec text for their platform. Of the ones that could be fetched, most contain the correct npub with other wording: 101 are a bare npub, and about 77 use Divine's own template. Requiring the exact string would invalidate almost every proof in the wild; requiring the npub keeps about 290 of them valid.

The freedom-tech takeaway: 97% of in-the-wild NIP-39 proofs would fail a strict-text check (27 of 611 contained the exact spec text). The lenient rule preserves real-world interop for ~290 proofs (those with the npub) while a single canonical text prevents future drift. Plus, alexgleason's survey surfaces 271 bluesky claims and 70 discord claims already in the wild without spec support — the W40 PR retroactively legitimizes ~340 in-flight claims that previously had no spec backing.

The combined W40 NIPs surface is:

  • NIP-39 unified verification text + bluesky + discord (PR #2486)
  • NIP-51 favorite follow sets on kind:10021 (PR #2417)
  • NIP-85 / NIP-43 / NIP-59 / NIP-87 kinds enumerated in the table (PR #2483)

Four NIPs touched, three merges, zero breaking changes. The repo is operating in its "polish and legitimize" mode rather than its "add new primitives" mode — the W40 surface is structurally tight rather than structurally novel.

  • Reference implementation Letdown2491/trustedrelays last push (2026-06-29) = 129 days dormant
  • Drift now crossed the 5-month mark

The drift is structural and proposal-driven:

boyroywax (Sept 4) proposed two paths forward, either of which Letdown2491/trustedrelays would implement:

1. Pick another addressable kind in the NIP-85 block (30386 is free as far as I can see) and keep the proposal's shape as is. 2. Keep 30385 and become a profile of the merged kind: a relay is a URL, so d = the canonical relay URL, k = web per NIP-73, and rank for the headline score. The proposal's other tags (status, reliability, quality, accessibility, the operator, policy and jurisdiction tags) can then be added as relay-specific metrics on top, the way NIP-85 already declares per-kind metric tables. Kind 10385 collapses into kind 10040 under 30385:rank.

For what it is worth, meshstr nodes now publish option 2 today: a kind 30385 per relay endpoint, derived from the node's own signed conformance evidence, with k = web, rank and an a tag citing the evidence event. Spec text and the serialiser are at https://gitlab.pocketlabs.dev/meshstr/meshstr (see the ecosystem bridges section of the spec). nostr-veil (forgesworn/nostr-veil) publishes relay scores under the same reading. If this proposal settles on 30385 with its current shape we will add a second serialiser for it, but we would rather not have to tell the two apart by absence of a k tag.

The boyroywax proposal (option 2) is now the production shape on two independent implementations (meshstr + nostr-veil). The drift is the proposal author's response is the implementation drift — Letdown2491/trustedrelays keeps publishing under algorithm=v0.3.0 with no k tag, meshstr publishes under k=web + rank + a tag, nostr-veil publishes the same shape. A reader can't tell them apart by absence of a k tag — the same kind, two shapes, three implementations, two of which chose option 2.

The W40 drift reading: the protocol-level resolution is unlikely to come from the NIPs repo on its current trajectory — 27 days without fiatjaf or any maintainer engaging, 75 days open, zero other commenters. The resolution will come from the implementations choosing option 2 en masse — once meshstr + nostr-veil + wot-scoring + (potential future) implementations all publish k=web, the proposal authors either update to option 2 or close the PR. The drift has crossed 5 months; this is no longer "the PR is taking a while" — this is "the implementations are moving faster than the proposal."

Proof of possession: ML-DSA signs pop_message = "nip-pqc/v1/pop:" || pubkey_hex || ":" || kem_pk_b64 || ":" || dsa_pk_b64. Reader MUST reject the attestation entirely if any of the 5 validation steps fail (event signature, v tag, alg tag presence + base64 decode to 1568/2592 bytes, pop verification).

The validator on nostr-wot.com/pqc consumes the live kind:10203 events on public relays and validates them — alg tag lengths, origin matches declared seed strength, proof-of-possession verify. The extension repo and the oracle repo + the validator are aligned on the wire-spec.

Version: 1.4.1 (crates.io 2026-09-14T13:47:40Z) Updates: rustls + ripemd160 revert (per W39 sweep)

Sequoia PQC algorithm-ID assignments are on a branch (per the W39 sweep's reading), not in a release. The institutional OpenPGP PQC track remains GnuPG-only as of Oct 1, 2026.

OpenPGP.js 7 commits on Sep 23 (per the W39 sweep) — all packet-parsing bug fixes, no PQC code path. The Sep 23 sweep's reading:

Plus PR #330 (CI: fix invalid caching of swift tools, merged same day Sep 23 19:29) — the missing prerequisite, the CI cache was silently returning the same Swift toolchain across commits, masking the cuckoo-table tests' actual failure surface. (this is Apple swift-homomorphic-encryption, not OpenPGP.js — confirmation: OpenPGP.js is TypeScript, not Swift)

Wait — clarification: the Swift toolchain CI fix was for Apple's PIR (swift-homomorphic-encryption), not OpenPGP.js. OpenPGP.js is TypeScript-only as of W40 (it dropped Node.js native bindings years ago). The 7-commit bug-fix streak on Sep 23 is TypeScript-only, which means all packet-parsing fixes are in pure TypeScript without the prior history of native-binding compatibility concerns.

The W40 PQC-OpenPGP ecosystem is single-vendor: GnuPG has shipped, Sequoia has algorithm-ID assignments on a branch, OpenPGP.js has no code path, and rnp has a different timeline entirely. For freedom-tech, this means the institutional PQC-OpenPGP migration depends on GnuPG's release cadence alone. The GnuPG → Nostr-PQC adoption curve is therefore the empirical observability of the entire PQC-OpenPGP migration — and the kind:10203 stair-step pattern is the only signal that the migration is happening.
