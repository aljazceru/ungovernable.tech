Signature is still 64-byte Schnorr/secp256k1 (128 hex chars). The kind:10203 entries are identity-declaration events, not signature events: the alg/pop/origin/seed_strength/v tags are the metadata; the signature is Nostr-standard secp256k1 because no NIP-PQC signature scheme has been adopted yet. The 64-byte sig is consistent with the Aug 10 entries' sigs (also 64 bytes), so the structure has not changed — only the alg tags have been updated to ML-DSA-87.

Why this matters for WoT: - The pattern is identical to Aug 31 → GnuPG 2.5.22 → 2 new entries and Sept 23 → GnuPG 2.5.23 → 2 new entries. The library's prior reading ("the Aug 31 stair-step was a single event") has now upgraded to "the stair-step is a stable pattern that triggers on each GnuPG release." Two-for-two is now data; one-of-one was noise. - The NIP-PQC draft metadata shape is the same shape proposed in NIPs PR #2434 "PQ Identity Keys" (frozen 44 days, sole comment = fiatjaf's nostr-tools#541 link). The vault has been tracking this PR since July; the live relay data is the first measurable adoption signal. - The 24 → 26 jump is still small in absolute terms. kind:10203 adoption is release-driven, not network-effect-driven. Each GnuPG release day adds 1–3 entries; each non-release day adds 0. - The ML-DSA-87 + ML-KEM-1024 combination matches FIPS 203/204 (the FIPS-140-3 PQC suite). The seed_strength=256 matches the security level of the underlying symmetric primitive. The v=nip-pqc/v1 is a version tag. The origin=derived means the key was derived (likely from a 256-bit seed via BIP-32-style derivation, but for ML-DSA-87 — which is the experimental part). - For freedom-tech, the practical implication is there are now 26 Nostr pubkeys advertising ML-DSA-87 PQC identity declarations on a public relay. This is the first measurable public PQC Nostr identity corpus — even if the signatures themselves are not yet PQC, the metadata is sufficient for clients to filter, route, or display these pubkeys as PQC-aware.

Tripwire: any GnuPG point release will now likely add 1–3 kind:10203 entries; the next GnuPG release day is expected to be 2.5.25 (unreleased, NEWS empty).

The NIP-02 merge (PR #2472) adds the petname-paths feature to NIP-02. From the merged spec:

Petname scheme

Clients can use follow-list petnames as local names for profiles. A petname is stored as the fourth value in a p tag:

json ["p", "21df6d143fb96c2ec9d63726bf9edc7121df6d143fb96c2ec9d63726bf9edc71", "", "erin"]

Here, the pubkey is known and can be displayed as erin in the current user's context. Likewise, if Erin has a petname of charlie assigned to one of her contacts, then Charlie can be displayed as ~/erin/charlie in the current user's context.

Petnames can also work on the other direction and resolve a pubkey from a name path. A path is resolved one component at a time: each component is looked up in the follow list of the profile resolved by the previous component.

For example, if the current user's follow list gives a profile the petname erin, and Erin's follow list gives another profile the petname charlie, then ~/erin/charlie resolves to Charlie.

If no user is logged in or the current user context is not relevant, an absolute root can be specified:

text ~npub1.../erin/charlie ~carol@names.com/erin/charlie

In order to qualify for petname resolution they must have only ASCII letters, numbers or _.

This is the formal addition of Zooko's-triangle-resolving identifiers to Nostr: human-readable, decentralized (no registry), and secure (path resolution depends on actual follow-list content). The ~carol@names.com syntax allows arbitrary naming services to anchor the chain. The ASCII-only qualifier is the Sept 23 follow-up newsroom entry ("nip-02-limits-petnames-to-ascii") — fiatjaf added the restriction the same day as the original merge.

The NIP-86 cluster (three PRs, staab + iqbqioza) adds claim management to NIP-86 (Relay Action Management). The use case from PR #2408:

This is so admins can manage NIP 43 invite codes. The use case I have which requires this is collecting payment for a community relay before the user's identity has even been created. This allows me to create an invite code associated with a role, collect payment, give the user the invite code and redirect to flotilla. They then use the invite code, meanwhile my bot listens to the kind 28935 sent to the relay, then assigns a role to the user automatically granting them access to a specific room.

NIP-86 is now the canonical WoT-for-paid-relay pattern: paid invites → identity creation → role assignment → relay access. This is the first WoT protocol feature that explicitly integrates payment as a trust-anchor source (you paid, therefore you get a higher-trust path through the invite system). PR #2477 adds the unallow/unban event + list methods — the inverse of allow/ban. PR #2481 reformats the methods section.

Strategic Analysis — Institutional PQC Shipped, Nostr Adopted

The institutional PQC track shipped, and the Sept 23 stair-step confirms the trigger pattern

Last week's reading was "GnuPG moved (RFC 9980 merge) while Sequoia stayed silent." This week's reading is "GnuPG shipped (2.5.23 + 2.5.24) and the Sept 23 kind:10203 stair-step confirmed the trigger pattern." The 2-for-2 GnuPG-release → kind:10203-stair-step correlation (2.5.22 → Aug 31, 2.5.23 → Sept 23) upgrades the Aug 31 reading from "single event triggered by 2.5.22" to "releases drive adoption." Each institutional release day adds 2 entries; non-release days add 0. The Nostr PQC corpus is now release-driven by GnuPG, not by Nostr-side adoption pressure.

The maintainer's NEWS note is politically significant: "PGP folks requiring some PQC resistance should keep on using the standard LibrePGP Kyber algorithm introduced 2 years ago." This is not GnuPG endorsing RFC 9980 as the right path — it is shipping the implementation for compliance regimes that require it, while explicitly recommending the LibrePGP alternative. For freedom-tech, the practical implication is there are now two production PQC paths in GnuPG: the institutional RFC 9980 path (with the "governmental approved" framing) and the LibrePGP Kyber path (the recommended one). The kind:10203 entries' ml-kem-1024 alg tag is algorithm-agnostic — the same metadata shape would work for either path.

The Nostr-WoT extension v0.8.0 is the deployment-ready release of 2026

Last week's reading was "v0.7.0 was the audit-response release." This week's reading is v0.8.0 is the deployment-ready release: window.nostr.wot is back behind opt-in, the follow-list replacement guard is in, the PQC/WoT proposals panel is organized, and NWC app connections (v0.8.3) give users per-app spending limits with server-side enforcement. Five releases in five days is the extension's most active window in its history, and the v0.8.x cycle is the first one where every release has a clear user-facing feature (not just internal refactor).

For freedom-tech, the practical implication is a Nostr-WoT extension user can now: (1) opt into the window.nostr.wot API for any web client that respects it, (2) see PQC Nostr identities organized in a dedicated UI panel, (3) prevent accidental follow-list replacement, (4) connect their wallet to NWC apps with per-app spending limits and expiry, (5) revoke any connection from Wallet Settings. This is the kind of feature set that makes the extension safe enough to recommend to non-technical users. The store-submission process (AMO/Firefox) has not yet approved v0.7.x or v0.8.x publicly; that remains the deployment-side bottleneck.

NIP-02 petnames resolve Zooko's triangle for Nostr

The NIP-02 "make petnames great again" merge is the single most consequential Nostr protocol update of the month. Petnames as ~/alice/bob paths give Nostr human-readable, decentralized, secure identifiers — the three properties Zooko's triangle says cannot all coexist in a single namespace. The compromise is paths instead of single names: the resolution is secure because it depends on actual follow-list content, decentralized because no registry controls it, and human-readable because the path components are chosen by humans.

For freedom-tech, this matters because petnames-as-paths is the trust-anchor primitive for Nostr WoT: a user can now say "I trust the user at ~carol@names.com/erin/charlie" and the resolution is verifiable. This is the same conceptual move as OpenPGP fingerprint + Web of Trust, but applied to a much more usable UX. Clients that implement the new NIP-02 feature (nak did, on Sept 17) can now surface this to users.

kind:10203 is release-driven, not network-driven

The 23-day gap followed by the 2-entry stair-step on the GnuPG release day is the first stable adoption pattern for kind:10203. The library's prior readings — "single event" (Aug 31), "second cohort or single event" (Sept 3) — have now resolved into "release-triggered single event, recurring". The practical implication is kind:10203 will continue to grow 2 entries per GnuPG release day; the next GnuPG release (2.5.25) will likely add 2 more.

For production-use planning, this means kind:10203 will not reach network-effect scale by itself. A different growth pattern — e.g., a client making kind:10203 a default identity declaration, or a NIP forcing kind:10203 for some specific use case — would be needed to break the release-driven ceiling.
