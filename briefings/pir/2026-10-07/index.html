The 4 PRs are 4 distinct correctness fixes: - PR #337 "Account for encryption tag in Symmetric PIR bucket sizing" (Oct 4) — PIRProcessDatabase sizes Cuckoo table buckets from the unencrypted value sizes, but Symmetric PIR appends a 16-byte tag to every value. Processing aborts when the tag pushes the largest value past the bucket size — for a 998-byte value with n_4096_logq_27_28_28_logt_5, the tag pushes it to 1014 bytes and the Cuckoo-table construction fails with Unable to insert value ... (1014 byte value). Fix: add the tag size to the maximum value size in resolveForKeywordDatabase. Behavior change: with Symmetric PIR and a largest value of exactly 997 bytes, the default maxSerializedBucketSize goes from 1024 to 2048 bytes — so the bucket size doubles for Symmetric PIR deployments near the bucket-size boundary. New regression test symmetricPirMaxSerializedBucketSize. - PR #336 "Fix accumulator overflow in modular matrix multiplication" (Oct 4) — Array2d.multiply(_:modulus:) and Array2d.multiply(transposing:modulus:offset:) sum products in T.DoubleWidth and reduce only once at the end. The sum wraps past T.DoubleWidth.max after 16 products at the largest supported modulus. In SimplePIR, SimplePirServer<UInt32> with a 28-bit ciphertext modulus returns incorrect entries at lattice dimension 2048. Fix: reduce the running sum after at most maxLazyProductAccumulationCount products (the same trick the BFV inner product already uses); move the inner loop into a shared Array2d.innerProduct helper used by both functions. Performance: no slowdown when single reduction suffices; 4–24% slower in the cases that were previously wrong (i.e. the fix recovers correctness at a small cost). Note from the PR body: in PrecomputedQueries, one operand is the secret matrix — bounding by the modulus instead of the operand size would slow the UInt32 hint computation; the author proposes "Happy to switch" — i.e. the design choice is open. - PR #335 "Clear stale seed from ciphertext-plaintext inner product result" (Oct 4) — the BFV ciphertext-plaintext inner product builds its result from a copy of the first ciphertext and keeps that ciphertext's seed. If the first ciphertext is fresh, serializing the result uses the seeded format, so deserialization regenerates the second polynomial from the seed and the result decrypts incorrectly. Fix: reduceToCiphertext now clears the result's seed. Covers all three ciphertext-plaintext variants — innerProduct, innerProductAsync, and innerProduct(..., maxConcurrentTasks:). New test schemeCiphertextPlaintextInnerProductTest round-trips each inner-product result through serialization and checks it still decrypts correctly. - PR #334 "Fix sharded index database overwriting its output files" (Oct 4) — with "databaseType": "index" and more than one shard, PIRProcessDatabase accepts outputDatabase and outputPirParameters paths that don't contain SHARD_ID. Every shard is then written to the same path, so only the last shard written survives, and the tool exits with code 0 — a silent data-loss bug. The keyword path already rejects this configuration in ResolvedArguments.validate(); the index path never ran that check. Fix: add Arguments.validateForIndexDatabase() which applies the same SHARD_ID rule as the keyword path; call it at the start of processIndexDatabase, before the input database is read. Behavior change: multi-shard index configurations without SHARD_ID in the path now fail with exit code 64; single-shard configurations (including the default) are unaffected. New test indexDatabaseShardID.

PR #337 (Oct 4) — Account for encryption tag in Symmetric PIR bucket sizing:

Summary — PIRProcessDatabase sizes cuckoo table buckets from the unencrypted value sizes, but Symmetric PIR appends a 16-byte tag to every value. Processing aborts when the tag pushes the largest value past the bucket size.

Reproduction

  1. Generate a keyword database with 998-byte values.
  2. Run PIRProcessDatabase on it with n_4096_logq_27_28_28_logt_5 and symmetricPirArguments set.

Error: Failed to construct Cuckoo table: Unable to insert value ... (1014 byte value)

Largest values of 998...1012 and 2022...2037 bytes are affected.

Fix — Add the tag size to the maximum value size in resolveForKeywordDatabase.

Behavior change — With Symmetric PIR and a largest value of exactly 997 bytes, the default maxSerializedBucketSize goes from 1024 to 2048 bytes.

Testing — New regression test symmetricPirMaxSerializedBucketSize. swift test -c release passes.

PR #336 (Oct 4) — Fix accumulator overflow in modular matrix multiplication:

Summary — Fixes an accumulator overflow in Array2d.multiply(_:modulus:) and Array2d.multiply(transposing:modulus:offset:) that produces wrong results for large moduli.

Problem — Both functions sum products in T.DoubleWidth and reduce only once at the end, so the sum wraps past T.DoubleWidth.max. At the largest supported modulus, this happens after 16 products. In SimplePIR, SimplePirServer<UInt32> with a 28-bit ciphertext modulus returns incorrect entries at lattice dimension 2048.

Changes — Reduce the running sum after at most maxLazyProductAccumulationCount products, as the BFV inner product already does. Derive the count from the largest values in the two matrices, so inputs that cannot overflow keep a single reduction. Move the inner loop into a shared Array2d.innerProduct helper used by both functions.

Testing — Added Array2dTests.multiply, Array2dTests.maxLazyProductAccumulationCount and SimplePirTests.multiplyTransposing. The two multiply tests fail on main for 17 and 64 products and pass with this change. swift test -c release passes.

Performance — No slowdown measured when a single reduction suffices. 4% to 24% slower in the cases that were previously wrong.

Notes for reviewers — In PrecomputedQueries, one operand is the secret matrix, so the count depends on its largest value. Bounding by the modulus instead avoids that, but slows the UInt32 hint computation. Happy to switch.

PR #335 (Oct 4) — Clear stale seed from ciphertext-plaintext inner product result:

Problem — The BFV ciphertext-plaintext inner product builds its result from a copy of the first ciphertext and keeps that ciphertext's seed. If the first ciphertext is fresh, serializing the result uses the seeded format, so deserialization regenerates the second polynomial from the seed and the result decrypts incorrectly.

Fix — reduceToCiphertext now clears the result's seed. This covers all three ciphertext-plaintext variants: innerProduct, innerProductAsync and innerProduct(..., maxConcurrentTasks:).

Testing — schemeCiphertextPlaintextInnerProductTest now round-trips each inner product result through serialization and checks it still decrypts correctly. It fails without the fix. swift test --configuration release passes.

PR #334 (Oct 4) — Fix sharded index database overwriting its output files:

Problem — With "databaseType": "index" and more than one shard, PIRProcessDatabase accepts outputDatabase and outputPirParameters paths that do not contain SHARD_ID. Every shard is then written to the same path, so only the last shard written survives, and the tool exits with code 0.

The keyword path already rejects this configuration in ResolvedArguments.validate(). The index path never ran that check.

Reproduction — An index database with 8 rows and this config:

json { "inputDatabase": "index-db.txtpb", "outputDatabase": "database.bin", "outputPirParameters": "pir-parameters.txtpb", "rlweParameters": "n_4096_logq_27_28_28_logt_5", "databaseType": "index", "sharding": { "shardCount": 4 } }

  • Before: 4 Saved shard to database.bin log lines, exit code 0, and the one remaining pir-parameters.txtpb has num_entries: 2.
  • After: Error: 'outputPirParameters' must contain 'SHARD_ID', exit code 64, nothing written.

Fix — Add Arguments.validateForIndexDatabase(), which applies the same SHARD_ID rule as the keyword path. Call it at the start of processIndexDatabase, before the input database is read. Single-shard configurations, including the default, are unaffected.

Testing — New test indexDatabaseShardID in ProcessDatabaseTests. swift test --filter PIRProcessDatabaseTests passes.
