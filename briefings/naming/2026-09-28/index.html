1. pubky-homeserver v0.13.0 (Sep 23) — WebDAV locks, SDK guards, version-on-startup, dual-arch Docker

Tag: v0.13.0 — Sep 23 13:58:18Z — commit e672ad4 — PR #640 (andrei-21) Published on crates.io as pubky-homeserver v0.13.0 with full Linux/Windows/macOS amd64+arm64 binary matrix (9.1 MB Linux, 9.2 MB macOS, 8.3 MB Windows). GitHub release: github.com/pubky/pubky-homeserver/releases/tag/v0.13.0

9 days after v0.12.0 (Sep 14). The W39 update (Sep 21) called the v0.12.0 release the end of a 26-day plateau and predicted further releases were coming — v0.13.0 is that next release, and it lands just 9 days after, not 26. The Pubky release cadence has accelerated, not decelerated.

Headline features:

PR Author Feature Significance
#630 @86667 Basic WebDAV locks First-class LOCK/UNLOCK semantics on homeserver storage. This unlocks desktop sync clients and collaborative editors (anything WebDAV-shaped — Cyberduck, mountain duck, mobile file managers with WebDAV). The homeserver's storage layer can now claim honest file-management semantics instead of relying on client-side best-effort.
#624 @MCarlomagno SDK guard against oversized payloads Closes the DoS surface where a malicious client could push unbounded response bodies. Closes issue #457 (ok300).
#608 @MCarlomagno SDK configurable error-response limits Closes issue #604 (icota).
#636 @andrei-21 Log version on startup Operational debugging hygiene — every log line can now be paired with the exact release commit.
#605 @andrei-21 Run PR builds on native amd64 + arm64 runners Doubled Docker build coverage — every PR now builds both architectures. The previous architecture-only-amd64 gap masked arm64-specific regressions.
#638 @andrei-21 Update pkarr + pkarr-relay lockfile versions Coordination with pkarr v8.0.2 (chore release same day).

Dependabot bumps (cluster by @ok300, @mdozhdev): opendal, sea-query, argon2, infer, axum-extra, axum-test, flume, fast-glob, wasm-streams, httpmock, ci-workflows.

Documentation: #631 (gcomte, "fix grant session persistence example") and #636 SDK session storage results clarification.

No public API breakage in this release — the breaking changes from v0.12.0 (DockerPostgres::shared() in PR #500 + Docker build target defaulting to homeserver in PR #594) remain the current contract.

For this library: the WebDAV locks feature (#630) is the most consequential because it lowers the integration barrier for any WebDAV-speaking client. The pkarr-relay lockfile bump (#638) signals that the Pubky/PKARR/Pubky-homeserver cluster is being treated as one deployment unit now.

HCA support added Sep 22-era: scoped, time-limited grants to delegate ENS name operations (set text, transfer subnames, renew) without signing every transaction. Permissions are scoped and time-limited, revocable at any time. Gas sponsorship via Pimlico or Rhinestone.

Use cases (per cap.eth Sep 22): set text on a name without holding the parent, manage subnames as an agent, automate renewal.

For this library: HCA is the agent-identity primitive for ENSv2. Combined with the ENSIP-28 Name Owned Accounts model (EIP-712 proofs that an account consents to be listed under a name), HCA closes the agent-economy loop: an ENS name can list multiple agents (Safe + TBA + agent wallet), each with its own consent proof, and delegate specific operations to each. This is the closest ENS has come to the W3C DID/VC model while staying within the ENS data-record pattern.

12. ENSIP-28 Name Owned Accounts — continues to gather feedback

Source: discuss.ens.domains/t/ensip-28-ens-name-owned-accounts/22373 (12 posts through Sep 2); spec published at docs.ens.domains/ensip/28/

Authors: premm.eth, workemon.eth, raffy.eth. Created: Aug 13, 2026. Status: draft.

ENSIP-28 lets an ENS name list more than one account per chain (Safe, token-bound account, agent wallet, etc.) and requires each listed account to prove consent via EIP-712 signature, stored as a data record alongside the listing. Covers EOAs (ecrecover), deployed smart accounts (ERC-1271 SignatureChecker), and token-bound accounts (ERC-6551).

Key fields: - accounts[<chain-id>] = abi.encode(address account1, account2, ...) (one record per chain, accounts in any order). - accounts[<chain-id>][<account>] = abi.encode(uint256 expiresAt, bytes signature) (proof for each account; expiresAt ≤ 2 years from now; proof invalid at and after expiresAt). - Optional accounts-chains record lists all chains with accounts.

For this library: this is the first ENSIP to standardize the agent-identity-list pattern at the protocol layer. It is the consent model (each account proves it consents to be listed) which means an ENS name cannot unilaterally attach an account to itself without that account's signature. The 2-year expiresAt cap is a safety mechanism: accounts can withdraw consent by simply not re-signing.

13. ENSIP-31 Payment Preferences — multichain-token fingerprinting debate

Source: discuss.ens.domains/t/ensip-31-payment-preferences/22431

Author: premm.eth. Created: Sep 17. Status: draft. PR ensdomains/ensips#87.

ENSIP-31 lets a recipient publish an ordered, token-specific list of preferred chains through their ENS name as an ENSIP-24 data record (key payment-preference[]). Wallets read before choosing a chain.

Example: alice.eth publishes that for USDC she prefers Base first, Ethereum second. A wallet asked to send 20 USDC reads the record, picks Base, and resolves the Base address as normal.

The multichain-token fingerprinting question (the unresolved technical question): - Symbols like "USDC" are not canonical. - Contract addresses are canonical but identify a token on only one chain. - Once a token exists across multiple chains, there is no single canonical identifier for the multichain token as a whole. - ENSIP-31 currently addresses this by hashing an immutable snapshot of its chain-specific token representations.

jkm.eth's Sep 21 reply (substantive pushback):

"In practical terms, many people may consider all deployments of USDC to be fungible, because they are all 'backed' by the same entity. However, 20 USDC on one chain isn't guaranteed to always be worth 20 USDC on another chain, as low liquidity or the cost of moving assets between chains can separately impact the value of each. Therefore, trying to present distinct assets as one unified asset is tricky. Alice might say she prefers Base to Ethereum, but that doesn't explain the exchange rate between the two, and Alice might need 21 USDC if sent on Ethereum but only 20 USDC if sent on Base. It seems like payment details comprise 3 data points: which assets are accepted/requested, how much of the asset is required depending on which asset is chosen, and the order of preference between those assets. Publishing just one of these data points seems unhelpful when the other two still need to be conveyed somehow."

For this library: this is the strongest open technical thread on multichain payment routing in 2026. It is also the first ENSIP to tackle recipient-side chain routing at the protocol layer. The resolution of the multichain-token-fingerprinting question will likely require either (a) a Multichain Token Registry maintained by a third party (Uniswap's Universal Token List is the closest analog), or (b) a snapshot-and-hash approach as currently proposed, or (c) per-chain ordering without a unified token identifier.

15. DNS-AID draft-02 expires Nov 28, 2026 — still no new draft

Source: datatracker.ietf.org/doc/draft-mozleywilliams-dnsop-dnsaid/

DNS-AID (DNS-based Agent Identifier) draft-02 is the current canonical reference for AI agent discovery via DNS records. The Cloudflare Agent-Readiness checker (Aug 24) still enforces draft-01 expectations without acknowledging the breakage.

The DNSOP working group has not cut a new draft. The expiry is Nov 28, 2026 — T-61 days from today.

For this library: watch for any cut before Nov 28. Stale but not dead. The DNS-AID pattern matters because any agent-discovery layer for the legacy web will sit on top of the gTLD root, which means the ICANN TSG × alt-naming conversation also applies here — an ENS name or Handshake TLD can carry an agent identifier through the DNS-AID SVCB custom-parameter pattern, but only if the ICANN root recognizes the lookup as DNS.
