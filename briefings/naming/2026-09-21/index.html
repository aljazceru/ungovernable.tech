4. ENSIP-31: Payment Preferences — recipient-side chain routing at the protocol layer

ENSIP-31: Payment Preferences — Standards, ENS Development, 0 replies, Sep 17 by nxt3d (Unruggable Labs / Premm.eth). Forum: https://discuss.ens.domains/t/ensip-31-payment-preferences/22431. Draft PR: ensdomains/ensips#87.

The problem: an ENS name can resolve a receiving address on many chains, so knowing the name is not enough. The sender still has to pick the chain, and the recipient's answer often depends on the token. Today there is no way to learn that preference from ENS — wallets guess, or the two sides sort it out over chat.

The proposal: let the recipient publish an ordered, token-specific list of preferred chains through their ENS name. A wallet can read the list before choosing a chain, then resolve the receiving address on that chain exactly as it does today.

Worked example (from the ENSIP): alice.eth publishes that for USDC they prefer Base first, Ethereum second. A wallet asked to send them 20 USDC reads that record, picks Base, and resolves their Base address as normal.

Storage: ordinary ENSIP-24 data record with key like payment-preference[<multichainTokenHash>]. No new resolver methods.

The open question (worth tracking) — how the Multichain Token Registry fingerprints a token: - Symbols such as USDC are not canonical - Contract addresses are canonical, but each address identifies a token on only one chain - Once a token exists across multiple chains, there is no single canonical identifier for the multichain token as a whole - ENSIP-31 currently addresses this by hashing an immutable snapshot of its chain-specific token representations - The author is "very open to other approaches for identifying a multichain token"

Why this matters for the dDNS stack: this is the first ENSIP in 2026 to standardize recipient-side routing intent at the protocol layer, complementing the resolver layer (ENSIP-24, CCIP-Read, etc.) and the identity layer (ENSIP-26: ENS Native AI Identity, ENSIP-27: Agent Card Schema). Combined with Nostr NIP-05 (which already bridges NIP-01 pubkeys ↔ DNS names ↔ ENS via pkarr) and Nostr NIP-17 (stealth addressing, ongoing NIPs PR #2471 thread per the Identity weekly), the decentralized naming stack now has explicit standards for: - who you are (ENS name ↔ Ethereum address ↔ pkarr record ↔ Nostr pubkey) - what agent you are (ENSIP-26, ENSIP-27, ERC-8004, ENSv2 plugin for MetaMask Agent Wallet v0.8.0) - how to find you across chains (ENSIP-31) ← new in W39 - how to pay you privately (Stealth Address Resolution ENSIP, ongoing — see Sep 14 weekly)

Cross-reference: ENS §"ENSIPs in flight"; Newsletter #120 §"ENSIP proposes payment preferences"; Sep 14 weekly §"ENSIP Stealth."

5. ICANN TSG public comment closes TODAY (Sep 21) — the only formal venue for alt-naming coexistence

Initial Report of the TSG on gTLD Integrations with Alternative Naming Systems — public-comment submission window Aug 10 – Sep 21, 2026.

The scope (per ICANN): "This proceeding seeks input on the initial report by the Technical Study Group (TSG) on generic top-level domain (gTLD) Integrations with Alternative Naming Systems. The TSG was convened to study whether a gTLD can be integrated with the same domain name in an alternative naming system in a secure and stable manner. The report focuses on the potential impact to the security and stability of the Domain Name System (DNS)."

Why this is the single most-important policy event of Q3 for the decentralized-DNS stack: - It is the only formal ICANN venue open in Q3 2026 that specifically addresses whether a gTLD string can coexist with the same string in an alternative naming system (blockchain, mesh, DHT-based). - The output shapes whether .eth, .crypto, .x, .wallet, .bit, ENS subdomains, Handshake TLDs, etc., can be referenced from gTLD governance as "compatible" — and whether root-zone collision risks are formally acknowledged. - The TSG was a community-government initiative; the public comment is the only input mechanism, and closes Sep 21.

For the decentralized-naming ecosystem, the substantive questions are: 1. Whether ICANN formally distinguishes between shared-string (e.g. .eth as both an ENS namespace and a hypothetical future gTLD) and adjacent-string (e.g. .wallet as Unstoppable Domains) coexistence. 2. Whether ICANN accepts the operational-security reasoning that the alternative-naming system can be authoritative for its own namespace even when the gTLD exists in parallel (Handshake's claim; ENS's DNS-import claim is the inverse). 3. Whether the Name Collision Observatory (referenced in the Aug 31 weekly) handles blockchain-TLD strings the same way it handles traditional IDN gTLDs.

Operational status Sep 21: public-comment submissions tracked by ICANN public-comment dashboard show Sep 21 = closing date, with Sep 19/20 submissions visible. The submitted-comment count is not visible from the public dashboard at write-time; expect the TSG to publish its next-stage report (incorporating public comments) within 4–8 weeks.

Cross-reference: Overview - Decentralized DNS §"ICANN TSG on Alt-Naming"; Aug 31 weekly §"ICANN Name Collision Observatory"; ICANN public-comment proceeding URL above.

8. DNS-AID — draft-02 still current, expires Nov 28

draft-mozleywilliams-dnsop-dnsaid-02 — "DNS for AI Discovery", May 2026. Expires 28 November 2026. Authors: Mozley, Williams, et al. Working group: dnsop. Reference implementation: dns-aid/dns-aid-core at v0.4.8+. Public site at dns-aid.org.

Mechanism (unchanged from May 2026): uses SVCB records for connectivity + metadata, a well-known entry point using DNS-SD labels into an organization's agent index, and optionally DNSSEC + DANE TLSA records for trust and security.

Three discovery use cases: 1. Known Agent (SVCB record query for agent-name.example.com) 2. Known Organization (_index._agents.example.com) 3. Known Capability (out of scope, can be derived from #2)

ALPN additions requested for IANA registration: mcp (Model Context Protocol), a2a (Agent-to-Agent).

Status this week: no new draft. Mid-Sep expected for new IETF submission per the Sep 14 weekly's "mid-Sep announcement window" — that window has now closed without a new draft. The next natural milestone is draft-03 in late October / early November ahead of the Nov 28 expiry. If no cut, the working group loses a meeting cycle.

Cloudflare Agent-Readiness checker (Aug 24 weekly) still enforces draft-01 expectations without acknowledging the breakage — the Enforcement-of-draft-01 issue remains unaddressed.
