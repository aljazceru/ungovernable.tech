Why separate DHT/relay timeouts matter:

The PKARR lookup architecture (since v3 / v4) is: a client tries to resolve a public key → it queries the Mainline DHT for the public key's signed resource record → if the DHT is slow or unresponsive, the client also tries the pkarr-relay cache → if the relay has a fresh answer, the client gets it fast. The two paths were gated by a single timeout in the previous API — meaning the client had to choose between "wait long enough for the DHT" and "fail fast and fall through to the relay". With separate timeouts:

  • The relay path can be set to fail fast (e.g., 1 second) — the relay should always have a recent answer; if it doesn't respond in 1 second, the relay is degraded and the client should fall through to the DHT.
  • The DHT path can be set to wait longer (e.g., 10 seconds) — the DHT can be slow under load, but it's the source of truth for the public key's signed record.

The net effect is a faster, more reliable PKARR client — the relay fast-path succeeds quickly when healthy, and the DHT slow-path has enough time budget to actually succeed when needed.

For this library: PKARR's first non-chore v8 release is structurally significant because DHT-vs-relay path tuning is the operational surface that will define PKARR's reliability story as pubky-homeserver deployments scale. The W40 weekly noted that "PKARR is now treated as a stable dependency", but stable ≠ feature-complete. v8.1.0 is the first v8 release that adds a new client capability rather than a chore / lockfile bump.
