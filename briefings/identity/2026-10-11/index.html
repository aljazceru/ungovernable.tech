Three narratives dominate. First: protocol-level signing/identity hardening — NIP-5F brings remote signing into the OS-local socket namespace (NIP-46 over unix://), NIP-42 + NIP-43 rewrite the authentication gate as NIP-DB inside the browser, NIP-94 encryption closes the public-file plaintext gap, and the headline NIP-92 (imeta tags on kind:0 profile pictures) gets implementation within hours: Amethyst 1.17.0's ProfileImageMetas matcher merged roughly two hours after the spec merged on the same day. Third: client / signer operability — Amber 6.6.7 (Oct 5) closes a "relays stuck disconnected until force-close" regression where RelayHealthTracker.isDead was a count-only threshold with no expiry, and onDisconnected was double-counted alongside onCannotConnect; Amethyst 1.17.0 (Oct 5, "Cordn and several updates") is the largest in months (1,253 commits, 176 PRs), with PR #4238 saving entire DM loads from relays that close on refused kinds, PR #4239/#4242 learning max_filters from CLOSED reasons, PR #4209 redesigning the backup-key screen with NIP-49 Poly1305 verification, and PR #4201 shipping Cordn group messaging (51,174 LOC, unticked interop test plan).

TL;DR — This Week

  • NIPs PR #2494 NIP-92 imeta tags for kind:0 picture/banner merged Oct 5 (alexgleason) + Amethyst PR #4320 ProfileImageMetas merged Oct 5 ~2h later. NIP-92's profile-specific section lets the canonical picture and banner URLs in the kind:0 JSON content carry imeta tags for MIME type, SHA-256 x, dimensions dim, blurhash blurhash, fallback URLs fallback, accessibility alt, and other NIP-94 metadata. The URL equivalence is exact-match (whitespace-trimmed only — a different query string does not match). On replaceable kind:0 publication, clients SHOULD carry over tags for unchanged images and DROP tags for replaced/removed images. The merge happened in the same Oct 5 window as the NIPs newsroom piece — a textbook example of spec + implementation + explainer in a 24-hour cycle. Ditto and Armada implement the rendering side; Flutter-side Amethyst publishes imeta tags matching exact URLs and renders the blurhash placeholder while loading. The PR also fixes earlier problems: a stale tag cannot be applied to a newly selected image merely because both came from the same host; an avatar that lost its hosting stays visible through a published fallback; a profile image can render an accessible aspect-ratio placeholder before downloading the file. Backward compatible: non-supporting clients ignore the tags and read picture/banner as before. The trade-off is a mixed-deployment period during which two clients render the same kind:0 differently.
  • NIPs PR #1862 NIP-5F "Remote Signing via Unix Domain Sockets" merged Oct 6 (ChristianChiarulli) after about six months open (merged Mar 2026, originally a separate spec line and reconciled by fiatjaf merges into the NIP-46 family). NIP-5F defines how a NIP-46 bunker answers connection requests over a Unix-domain-socket URI scheme such as nostr+unix:///run/user/1000/my-bunker.sock rather than over a remote relay + secret. The structural value: a local signer can connect to a local client without ever creating a TCP/WS relay channel, without paying for relay bandwidth, and without an open remote-signer port on the network. The companion surface is a permission-to-socket path: a sandboxed app learns where the user's local bunker listens and joins the same OS sandbox via filesystem ACLs (e.g., seatbelt / Landlock / polkit) rather than via network reachability. The two published implementations in Remote Signing (the JS bunkers keep-core/keep-bunker and njalla/nostr-nsecbunker) already accept relay URLs in their connection-string parsers; NIP-5F is the form-fill for the OS-local case where the relay list is empty (or unwanted). This is the year's first NIP-46 cousin that is both cryptographic and not networked, and it complements the existing nostrconnect remote-signer model rather than replacing it.
  • Amber 6.6.7 "gives dead relays a second chance after fifteen minutes" — released Oct 5, newsroom piece Oct 5 — 8 commits, 23 files. Two independent causes for the regression ("relays stay disconnected until force-close"): (i) RelayHealthTracker.isDead was a count-only threshold with no temporal expiry — once a relay passed MAX_RECONNECT_ATTEMPTS = 10, nothing except an OS network change, a successful connection, or a manual reconnect reset the tracker. Cases that miss all three: Wi-Fi that lost and regained internet on the same SSID, weak cell signal that recovers, relay-side outage that clears. The fix introduces a DEAD_COOLDOWN_MS = 15 * 60 * 1000L constant; isDead returns true only when failures > MAX_RECONNECT_ATTEMPTS && clock() - lastFailureAt < DEAD_COOLDOWN_MS. After 15 minutes the relay is eligible again. (ii) onCannotConnect and onDisconnected both called scheduleReconnect, so the streak advanced by 2 per failed dial. With MAX_RECONNECT_ATTEMPTS = 10, the documented threshold was reached after five failed dials. The fix splits scheduleReconnect into recordFailureAndScheduleReconnect (called only by onCannotConnect) and an idempotent scheduleReconnect that checks isDead and reconnects without recording (called by onDisconnected). A plain server-side close is not a connection failure. A clock function is injected so the expiry can be tested without Thread.sleep. Six releases in six weeks (6.6.2 → 6.6.7, Aug 31 → Oct 5) — the most active Nostr-side identity surface in this fortnight.
  • Amethyst 1.17.0 "Cordn and several updates" released Oct 5 — 1,253 commits since 1.16.0, 176 PRs in the notes. Five identity-bearing changes: (1) PR #4238 + #4239 (re-landed as #4242) — relays that answer CLOSED on filters with disallowed kinds (strfry 1.1.1 with kind allowlist) were sinking entire DM loads; PR #4238 learns the refused kind from the CLOSED reason (e.g. kind not allowed: 21059) and strips it from every request built for that relay, both on change and on reconnect; PR #4239 detects a 4-filter refusal and infers max_filters ≤ 3 (strfry doesn't advertise it in NIP-11), then merges filters that differ in exactly one set of values into one filter with the union of those values. Filters with limit are never merged (a per-filter limit and a limit over the union are different requests); filters differing in two fields are never merged. (2) PR #4320 — ProfileImageMetas matches an imeta tag to a profile image only when URLs are equal after trim, so avatars and banners can show blurhash placeholders and try fallback URLs if the primary one fails; metadata for an unchanged image is preserved on edit, metadata for a replaced/removed image is dropped. (3) PR #4209 — backup-key screen redesign: nsec shown as three numbered rows of uppercase groups masked until tap, all-caps with dashes / spaces / line breaks now accepted (login flow previously rejected uppercase NSEC1), password-protected NIP-49 asks twice and requires ≥ 12 chars on creation (a creation policy, not a ncryptsec format change); Poly1305 tag is now checked during decryption (previously a valid key with all-32-byte high bits set was rejected as "no positive byte"); encryption honors its result and throws on tag failure (previously a tag failure could have produced a ncryptsec that no password opens); non-48-byte payloads now rejected. (4) PR #4201 Cordn — MLS-encrypted group messaging through coordinator servers (Cordn feeders), screens for create/join/manage; 51,174 LOC across 419 files; the test-plan checklist on the PR is left unticked. (5) NIP-92 imeta shipped and (6) WebView → NIP-07 browser signing gated by document scope (a departed-document message is discarded; Tor-required pages fail closed on proxy failure).
  • Citrine 3.1.1 NIP-42 AUTH signature-omission closes a forged-pubkey read (Sept 11, newsroom piece Oct 7 retrospective) — the relay's validateAuthEvent checked kind=22242, challenge match, relay-tag URL normalization, and created_at within 10 minutes, but it never verified the Schnorr signature. A client that built a kind:22242 with the right challenge, any pubkey, and no signature would be added to the connection's authenticated-pubkey set as that pubkey. The fix adds the missing event.verify() after the existing checks; on failure it returns CommandResult.invalid(event, "auth event signature verification failed"). Read-side AuthGate covers kind:4 (DMs), kind:1059 (gift wraps), and kind:30078 (application data) — a forged AUTH let a remote client name the owner's pubkey in a filter and pass AuthGate. Reach constraint: Citrine listens on 127.0.0.1:4869 by default, so a default install is reachable only from the device; the bypass matters only on remotes that listen on a wider address. NIP-70 protected-event writes already exempted localhost connections, so the write-side bypass was relevant only on remotes. Companion repairs in 3.1.1: per-connection subscription-id scope (NIP-01 wants ids independent per connection; previously global cache caused CLOSE-for-feed to cancel every socket's feed); NIP-45 COUNT no longer registers (was summing per-filter counts but living as a subscription); #p filter-tag typo (#p vs p); replaceable tie-breaks (NIP-01's lower-id-wins at equal timestamps now honored); exact ids/authors matching (no prefix matches); OK prefixes (blocked:/deleted:/duplicate:); NIP-11 built with Jackson (previously broken JSON on quote chars); NIP-04 dropped from supported_nips; CORS gains Access-Control-Allow-Headers; NIP-86 gains unbanpubkey + unallowpubkey and allowpubkey no longer removes a pubkey from the ban list as a side effect. Citrine 3.2.0 (Sept 18) bundles every 3.1.1 commit; updating to current contains the fix.
  • Nostr-WoT extension v0.8.11 "Account Archive and popup startup" (Oct 6 21:45 UTC, commit 989930a) + v0.8.12 "Archive import without a password" (Oct 6 22:22 UTC, commit 6976903) — 37 minutes apart. Account Archive (PR #39, merged 41 min before v0.8.11 tag) puts an encrypted local archive under the user's control: every original signed event synchronized across relays with checkpoints and encrypted local storage; concurrent multi-relay sync; resumable per-relay checkpoints; independent retries; per-account NIP-46 bunker ↔ user-side signer separation; bounded-wait popup-startup default (the extension no longer blocks startup on a check-and-verify loop). v0.8.12 removes the import-side password. Practical implication: a switching user can move from one machine to another through a pass-phraseless archive without compromising the export-time signature chain; a tab/device-loss scenario uses the same flow. Privacy boundaries differ: exported archive files are intended for self-transfer; encrypted local storage on disk is still encrypted at rest with the in-app key. The archival design is the third Nostr-side archive-tier feature in 2026 (after Nostr Key Custody and Recovery's Sept 21 Amber backup-encryption HKDF split and last week's nostr-wot-extension discussion of full-account archive). NIP-92: imeta tags for kind:0 profile pictures and banners

NIP-92 was extended on Oct 5 with a profile-specific section. PR #2494 (alexgleason) adds 35 lines to NIP-92 and one cross-reference to NIP-24; NIP-92 already described how a note could carry inline media metadata through imeta tags, but a profile image could only supply its primary URL inside the JSON content of the kind:0 event. The new section makes the matching canonical: a kind:0 metadata event may attach imeta tags to its picture and banner URLs through an exact-equality rule (the imeta tag's url is trimmed of whitespace and compared for character-for-character equality with the value of picture or banner). Whitespace-trimmed URL equality is the entire match rule — a different query string, a redirected destination, or a URL rewritten in any other way does not match.

The spec example: a profile picture carries MIME type, SHA-256 hash, dimensions, blurhash, and fallback URL; the banner carries MIME type, hash, and dimensions. NIP-92 inherits any field defined by NIP-94, so a publisher can additionally provide alt, size, thumbnails, or other file metadata. Only url plus at least one other field is required for an imeta tag; the rest remain optional.

The most visible additions are fallback (clients try declared fallback URLs when the primary profile image fails to load) and blurhash (the compact placeholder while the image loads). dim lets a layout reserve the correct aspect ratio before downloading. alt gives an accessibility description. x can carry the file's SHA-256 hash; clients that want integrity still have to verify the hash for it to provide a check. The normative language is mostly MAY and SHOULD because the profile image is fundamentally a hint — NIP-92 does not upload a mirror, prove that a fallback will stay online, or force a client to use any field.

The key maintenance rule: kind:0 is replaceable, so a newer event from the same public key supersedes the older profile. Publishing a new kind:0 should carry over imeta tags for pictures and banners that have not changed and drop tags for images no longer in use. Without that rule, editing a display name in a client that understands profile media metadata could accidentally erase fallbacks and alt text. Carrying every old tag forward would be worse, because it would leave signed metadata for images the profile no longer references.

The implementation evidence: Amethyst PR #4320 merged roughly two hours after NIP-92 began allowing imeta tags for kind:0 picture and banner. A new ProfileImageMetas class matches an imeta tag to a profile image only when the URLs are equal after trimming whitespace. Avatars and banners can now show a blurhash placeholder while loading and try the listed fallback URLs if the primary one fails. When a user edits their profile, Amethyst keeps the metadata for an image that did not change and drops it for an image that was replaced or removed. A 291-line test file covers these cases. PR text notes that Ditto and Armada already implement the rendering side; the submitter's claim is unattested by a compatibility registry.

NIP-5F: remote signing via Unix Domain Sockets

PR #1862 NIP-5F "Remote Signing via Unix Domain Sockets" merged on Oct 6 — about six months after its original March 2026 opening by ChristianChiarulli. The spec defines a URI scheme nostr+unix:// that targets a local socket rather than a relay. The structural value: a local signer can connect to a local client without creating a TCP/WS relay channel, paying for relay bandwidth, or opening a remote-signer port on the network.

The companion surface is the permission-to-socket path. A sandboxed app learns where the user's local bunker listens and joins the same OS sandbox through filesystem ACLs — seatbelt / Landlock / polkit ACLs — rather than through network reachability. The two published JavaScript bunker implementations in the Remote Signing note (keep-core/keep-bunker, njalla/nostr-nsecbunker) already accept relay URLs in their connection-string parsers; NIP-5F is the form-fill for the case where the relay list is empty or unwanted.

The cryptographic surface is unchanged: NIP-46's response-and-request event flow applies over the socket transport. The signing semantics, the connect / sign_event / nip44_encrypt / nip44_decrypt / get_public_key method set, and the bunker-responder authority model are identical to the relay case — only the connection transport changes. The bunker can be reached by a desktop client whose user wishes to keep all material in the OS user namespace (e.g., nostr+unix:///run/user/1000/my-bunker.sock); the bunker can also be reached by a peer app on the same device sharing a sandbox through an explicit Allow-ACL.

NIP-5F is the year's first NIP-46 cousin that is both cryptographic and not networked. It complements the existing nostrconnect remote-signer model rather than replacing it: relay-based NIP-46 remains the right answer when the signer and the client are on different machines, and a Unix-domain-socket NIP-5F is the right answer when they are on the same machine and the network round trip is either undesirable or impossible (offline).

The newsroom did not publish a dedicated NIP-5F piece this week (the schedule's coverage of NIP-46 was already extensive), but the PR merges cleanly with the existing @nostr-wot/bunker 0.2.0 ESM-responder-side package published on Oct 5 (covered in the Thursday WoT update) — that library's NostrConnect surface can be pointed at a nostr+unix:// URI in addition to the relay-based case.

Amber 6.6.7 — gives dead relays a second chance after fifteen minutes

Amber 6.6.7 shipped on Oct 5 with eight commits and twenty-three files separating it from 6.6.6. The reported symptom was relays staying disconnected until the app was force closed. The diff names two independent causes — both in the retry accounting rather than the socket layer:

Cause 1: RelayHealthTracker.isDead was a count-only threshold with no temporal expiry. In 6.6.6, MAX_RECONNECT_ATTEMPTS = 10 failures marked a relay dead; nothing except an OS network change, a successful connection, or a manual reconnect reset the tracker. The streak survived: a Wi-Fi network that lost and regained internet on the same SSID, a weak cell signal that recovered, a relay-side outage that cleared. None of those cases is a default-network change, so the streak remained, and every relay could be marked dead while the device stayed on one apparently healthy network.

The fix introduces DEAD_COOLDOWN_MS = 15 * 60 * 1000L. isDead now returns true only when failures > MAX_RECONNECT_ATTEMPTS && clock() - lastFailureAt < DEAD_COOLDOWN_MS. After fifteen minutes the relay is eligible again. The threshold is unchanged — what changed is that exceeding it is a timed penalty rather than a verdict. A clock function is injected so the expiry can be tested without Thread.sleep.

Cause 2: onCannotConnect and onDisconnected both called scheduleReconnect. Quartz, the library driving the relay pool, reports a failed dial as onCannotConnect followed by onDisconnected. Both handlers called the same scheduleReconnect, which recorded a failure. The streak advanced by two per failed dial. The documented threshold of ten was reached after five. The comment added in 6.6.7 states both halves of the problem: counting both callbacks halved the real threshold, and a plain server-side close is not a connection failure at all.

The fix splits the one function in two. recordFailureAndScheduleReconnect records a failure and is called only from onCannotConnect. scheduleReconnect now checks isDead and reconnects without recording anything, which is what onDisconnected was attempting. A plain server-side close (the relay terminates the WebSocket cleanly) is now neither a dial failure nor a reason to advance the dead counter.

The release maintains the four-week Amber cadence: 6.6.1 (Sept 4), 6.6.2 + 6.6.3 (Sept 9), 6.6.4 (Sept 14), 6.6.5 (Sept 21), 6.6.6 (Sept 28 / F-Droid Oct 1), 6.6.7 (Oct 5). Six releases in six weeks. The amber dev plan from July 2026 (greenart7c3/Amber#milestones) flagged the relay-health-tracker refactor as W41 priority; it closed cleanly.

Most PRs are refactoring and translations; six are identity-bearing:

(1) PR #4238: relays running strfry 1.1.1 with a kind allowlist answer CLOSED to any REQ whose filter names a kind they do not serve. Amethyst asks for gift wraps with a single filter covering kinds 1059 and 21059; the relay refused 21059; Amethyst treated the CLOSED as a refusal of the entire filter set; every gift wrap was lost. For an account whose kind:10050 DM relay was that relay, no NIP-17 direct message arrived and neither did any White Noise invite. The Welcome path failed without logging, so nothing pointed at the cause. The fix teaches the relay pool to read the refusal. When a CLOSED reason names a kind (kind not allowed: 21059), Amethyst records it for that relay and strips the kind from every request it builds for that relay, both on change and on reconnect. (2) PR #4239 (re-landed as #4242): the same relay also closes any request with four or more filters, and it does not advertise a max_filters value in its NIP-11 document. Marmot group messages use one filter per group, so an account in four or more groups there loaded no group messages at all. The fix learns the cap from the refusal: if four filters were refused, the limit is at most three. It then merges filters that differ in exactly one set of values into one filter with the union of those values. Filters with limit are never merged (a per-filter limit and a limit over the union are different requests). Filters that differ in two fields are never merged (the union would match combinations neither filter asked for). If a request still does not fit, Amethyst sends the first filters up to the cap and logs one warning. Citrine 3.1.1 — NIP-42 AUTH signature omission

Citrine 3.1.1 shipped on Sept 11 but the newsroom's retrospective on Oct 7 is the canonical writeup. The structural bug: validateAuthEvent checked that the event was kind 22242, that it carried a challenge and a relay tag, that the challenge matched the one sent on that connection, that the relay URL normalized, and that created_at was within ten minutes of the current time. Those are the checks NIP-42 lists. If they passed, the handler added event.pubKey to the connection's set of authenticated users.

Nothing in that path verified the signature. The challenge is sent to whoever opens the connection, so a client could build a kind 22242 event with the right challenge, put any pubkey in it, leave the signature invalid, and be treated as that pubkey for the rest of the connection. 3.1.1 adds the missing step after the existing checks:

// NIP-42: an AUTH event must carry a valid signature, otherwise any
// client could authenticate as any pubkey.
if (!event.verify()) {
    connection?.send(CommandResult.invalid(event, "auth event signature verification failed").toJson())
    return
}

The commit message names what the authenticated set protected: protected-event writes and private-kind reads. On the read side, AuthGate refuses filters for five kinds unless one of the connection's authenticated pubkeys is an author in the filter or appears in its #p values. The five include kind 4 (direct messages), kind 1059 (gift wraps), and kind 30078 (application data). With a forged AUTH, a client could name the owner's pubkey and pass that gate.

How far that reached depends on configuration. Citrine listens on 127.0.0.1:4869 by default, so on a default install the only clients that can open a connection are the ones on the same device. The listening address is a setting, and a relay configured to listen elsewhere was open to the same forged AUTH from anything that could reach it. On the write side, the NIP-70 protected-event check already exempted connections from localhost, so the bypass there mattered only for remote connections.

The companion repairs in 3.1.1 are larger than the AUTH fix:

  • Subscription ids were global. NIP-01 says relays must manage subscription ids independently for each WebSocket connection. Citrine kept all subscriptions in one cache keyed by the id the client sent. A CLOSE for "feed" on one socket cancelled every connection's "feed", and a new REQ with the same id replaced it. The cache key is now the connection name and the id together; the id on the wire is still the one the client chose.
  • COUNT was a REQ. NIP-45 says the filters in a COUNT are OR'd and aggregated into a single count result. In 3.1.0 a COUNT went through the same path as a REQ: one count message per filter, then an EOSE, and the subscription stayed registered. It received live events later. Version 3.1.1 gives COUNT its own path. It is never registered, it neither replaces a REQ with the same id nor receives live events, and it sends one COUNT message with no EOSE. The total is the sum of the per-filter counts, so an event that matches two filters in one request is counted twice.
  • #p filter tag typo. For filters with no kinds, AuthGate looked for receivers under the key "#p", but filter tags are stored without the #. The kinds branch already used "p"; this one now does too.
  • Replaceable tie-breaks. NIP-01 says that between replaceable events with the same timestamp, the one with the lowest id is retained. Citrine rejected any incoming event when a stored one had an equal or later created_at, so the first to arrive won. Both queries now let an incoming event with an equal timestamp and a lower id replace the stored one.
  • Exact ids and authors. The in-memory filter still accepted prefix matches, which the SQL path and NIP-01 do not. Only exact values match now.
  • OK prefixes. Policy rejections now use blocked: rather than invalid:, a deleted event gets deleted:, and an older replaceable gets duplicate:.
  • NIP-11. The relay information document was built by string interpolation, so a relay name or description containing a quote produced invalid JSON. It is now built with Jackson. NIP-04 is no longer advertised in supported_nips, and the CORS headers now include Access-Control-Allow-Headers.
  • NIP-86. unbanpubkey and unallowpubkey are added, and allowpubkey no longer removes a pubkey from the ban list as a side effect.

Version 3.1.1 is a published release with six Android packages and a signed checksum manifest. The commit message reports assembleDebug, ktlintCheck, test, and lintDebug passing and 24 behavioral checks run on a device; the diff itself adds no test files. Citrine 3.2.0 (Sept 18) bundles every 3.1.1 commit, so updating to the current release includes the fix. The newsroom piece notes: none of this establishes which version a given phone is running, and anyone relying on Citrine for direct messages should check.

The browser and the relay now share a kind-and-event catalog rather than each implementing it independently, and the surface where they meet is increasingly signed.
