TL;DR — This Week

  • Citrine 3.1.1 (Sep 11) fixes a NIP-42 authentication bypass (release, Freedom.Tech). The aggregator was adding kind:22242 AUTH events to its per-connection authenticated pubkey state without verifying the event's BIP-340 Schnorr signature. An attacker who knew a target's pubkey could send an unsigned kind:22242 to the aggregator; the aggregator would mark the connection as authenticated as that pubkey and serve that pubkey's stored NIP-78 application data and any future owner-gated content. The fix is signature verification before mutating connection state — the same check NIP-42 already specifies relays must do. Two other fixes: subscription IDs (REQ ids) are now scoped per connection rather than process-global, eliminating a class of cross-connection subId collisions; the aggregator now speaks NIP-45 COUNT for fast query measurement. Citrine is the de-facto Nostr aggregator on Android (F-Droid, Zapstore, Obtainium, direct APK); the bypass was reachable from any connected client and cost no authentication. The fix is the kind of release relay operators should know about — Citrine runs as a local relay on the phone, so the exposure surface is the user's own device.
  • relayer 2.2.19 (Sep 8) introduces FiltersCounter to fix NIP-45 overlapping COUNT filters (release, Nostr WoT newsroom). NIP-45 says multiple COUNT filters in a single request are OR'd into one result; relayer was calling CountEvents once per filter and adding the answers, so an event that satisfied more than one filter could be counted more than once. The new interface adds CountEventsFilters which receives the full filter list and returns the union count; backends that implement it get exact counts, backends that don't fall back to the old per-filter summation. Three tests pin down the difference (single-filter stays on CountEvents, overlapping filters receive CountEventsFilters, and a union-aware store returns 4 instead of 6 for a contrived overlap case). The fix is interface-shaped: the relay is correct as soon as the storage backend opts in, and stays backwards compatible with stores that have not adopted the new interface. The release is small — two commits, three files — but the observation matters: COUNT is the cheap alternative to retrieving potentially-large result sets, and inflated counts change what a client renders even when the underlying event set has not changed.
  • NIPs PR #2463 (NIP-A3 payment type ambiguity, alopatindev) merged Sep 9 (PR, merged by fiatjaf). The fix adds one sentence to NIP-A3: in case of type ambiguity, use payment-address URI scheme when it's available. The PR was opened Sep 8 with the bitcoin cash case as the worked example (bitcoin cash vs bitcoincash vs bitcoin-cash; the cashaddr spec's qpm2qsznhks23z7629mms6s4cwef74vcwvy22gdx6a example disambiguates via the spec-mandated prefix). The follow-up conversation thread — fiatjaf on Sep 9 asking "What does this mean? Can you give an example?" and alopatindev's same-day response with the bitcoin cash walk-through — is itself a lesson: NIP-A3 was rewritten by fiatjaf within 24 hours of its Aug 26 merge (August 30 update), so the spec text is still settling; this week's PR is a second-order clarification, not a redesign.
  • NIPs PR #2465 (NIP-90 optional DVM heartbeat event, kind 11998, believethehype) opened Sep 10 (PR). The shape: a kind:11998 event with ["expiration", "<unix>"] and otherwise empty content; a DVM publishes one every five minutes; clients filter NIP-89 announcements by whether a fresh heartbeat is observable. The PR ships with a working implementation in believethehype/nostrdvm (a DVM framework where several content-discovery DVMs at kind 5000-5999 already emit heartbeats across multiple relays), and Amethyst committed second-implementation support on Sep 12 ("Now supported in Amethyst."). The proposal is liveness-shaped, not capability-shaped — NIP-89 already covers what a DVM supports, but says nothing about whether the machine is currently running. PR is open with one reviewer (believethehype); no merge in the window.
  • NIPs PR #2461 (NIP-AC WebRTC signaling for p2p connections, Named666, Sep 4) still draft. Two days into the window and ten days after opening; the proposal moves voice/video p2p off the relay hop, which is the same architectural direction Amethyst 1.09.0 (May 15) shipped WebRTC calling on. The Week in Detail

Citrine 3.1.1: the NIP-42 AUTH bypass fix

Citrine is greenart7c3's Android Nostr aggregator — a local relay plus multi-relay client bundled into one APK and distributed via Zapstore, Obtainium, F-Droid, and direct download. As an aggregator it accepts inbound EVENT and AUTH messages on its local WebSocket and exposes the union to other Nostr clients on the device. The 3.1.1 release notes (Freedom.Tech, GitHub release) are explicit about the bug:

Fixed an NIP-42 auth bypass where kind-22242 AUTH events were added to the connection without signature verification.

The NIP-42 authentication flow is straightforward on paper (NIP-42 spec). The relay sends an AUTH challenge with a random string. The client constructs a kind:22242 ephemeral event with ["relay", "<relay url>"] and ["challenge", "<challenge string>"] tags, signs it with the user's Nostr key (BIP-340 Schnorr over secp256k1), and sends it back via the AUTH wire message. The relay then verifies four things on the inbound event before promoting the connection to authenticated state:

  1. The kind is 22242.
  2. The event created_at is close to current time (typically within ~10 minutes).
  3. The challenge tag matches what the relay sent.
  4. The relay tag matches the relay's URL.
  5. The Schnorr signature on the event verifies against the claimed pubkey.

The bug Citrine shipped 3.1.1 to fix was step 5. The aggregator was accepting the inbound AUTH message and updating its per-connection authenticatedPubkey field on the basis of the claimed pubkey in the event, without verifying that the Schnorr signature on the event actually validated against that pubkey. With that check missing, anyone who knew a target's npub could send an unsigned kind:22242 claiming that pubkey, and the aggregator would treat the connection as authenticated as that pubkey.

The impact surface is whatever the aggregator exposes only to authenticated owners. The week before this release, NIP-78 PR #2458 (merged Sep 3) added an AUTH section requiring that relays run NIP-42 before touching kinds 78 and 30078, and return them only to the authenticated owner. Ditto on relay.ditto.pub shipped NIP-78 AUTH enforcement. Citrine's aggregator is a relay-class surface too — it stores NIP-78 events as part of its cache — and so the same NIP-78 enforcement that Ditto shipped could ship to Citrine without spec change. The Citrine 3.1.1 fix is the prerequisite: an authenticated-connection state that any other Nostr client running against the Citrine local relay could trust.

The other Citrine 3.1.1 fixes are hardening rather than security:

  • Per-connection subscription ID scoping. Citrine 3.1.0 (Aug 14) was treating REQ ids as process-global. A second connection on the same Citrine process that opened a subscription with an id matching one already in use would step on the existing subscription. 3.1.1 namespaces subIds by connection.
  • NIP-45 COUNT support. Citrine now answers COUNT messages with the total count matching a filter set, returning the integer the spec promises without forcing a client to retrieve every event just to measure the set.

Citrine 3.1.1 was tagged Sep 11 and shipped to F-Droid, Zapstore, and Obtainium the same day. The signing key (greenart7c3, RSA 44F0AAEB...) is on keys.openpgp.org, the manifest signature verifies, and the manifest-v3.1.1.txt sha256 set is published. Two prior advisories in the 6.x line of Amber were signature-bypass class — Amber 6.5.x (August 23) shipped authorization-scope releases for the relay-auth confused-deputy class of bugs. Citrine 3.1.1 is the same family: signature/permission boundaries not being enforced at the relay hop.

relayer 2.2.19: NIP-45 COUNT over overlapping filters

relayer is fiatjaf's reference Nostr relay implementation in Go. The 2.2.19 release (GitHub, Nostr WoT newsroom) is two commits and three files. The diff is small; the observation it embodies is not.

The bug: NIP-45 says multiple filters in a single COUNT request are OR'd into one result. The relevant text in the spec is "If a filter has multiple authors or kinds, the relay should count events that match any of them." The relay returns a single integer. relayer's implementation called CountEvents once per filter and added the answers. That is correct when the filters cannot match the same event. It is too high when they overlap.

The contrived example from the newsroom writeup: filter A asks for kind 1; filter B asks for kinds 1 and 7. A kind 1 event satisfies both filters but NIP-45's OR rule means it belongs in the result once. Adding two independent counts includes it twice.

The fix is interface-shaped:

// New in 2.2.19
type FiltersCounter interface {
    CountEventsFilters(filters ...nostr.Filter) (int64, error)
}

The request handler uses this path when there is more than one filter. For a single filter, it continues to call the existing CountEvents method. Stores that implement FiltersCounter get exact union counts; stores that don't fall back to the per-filter summation (with the code comment noting the boundary explicitly: that fallback is exact when filters do not overlap).

Three new tests pin down the distinction: (a) a store with only the older counter still receives two separate calls; (b) overlapping filters sent to a union-aware store return 4 instead of the summed value of 6; (c) a request with one filter stays on the original method.

The observable result: COUNT is intended to save clients from retrieving a potentially-large result set merely to measure it. Counts for reactions, replies, reposts, or followers can be built from filters that overlap. Inflating those numbers because one stored event satisfies more than one filter changes the answer the client displays, even though the underlying event set has not changed.

The release also changes error handling on the union path: if CountEventsFilters fails, the relay returns error: failed to count events instead of continuing with a partial result. The older per-filter fallback still logs a failed individual count and continues through the remaining filters.

The narrow release — two commits, three files — is itself the signal. A relay that gets the spec right and exposes the right interface will be adopted as the storage backend grows; a relay that ships with a wrong but fast path will continue to be wrong on top of an updated interface. The 2.2.19 release is the right shape: opt-in correctness, no breaking change for backends, and tests that pin down both paths.

NIP-A3 payment type ambiguity: PR #2463

NIP-A3 — the payto: URI scheme for Nostr — was rewritten by fiatjaf within 24 hours of its August 26 merge (101 lines removed, kind 10133 and the payto tag survived). PR #2463 (GitHub, opened Sep 8 by alopatindev, merged Sep 9 by fiatjaf) is a second-order clarification: in case of type ambiguity, use the payment-address URI scheme when it is available.

The example in the conversation thread is the bitcoin cash disambiguation: bitcoin cash (with a space) versus bitcoincash (camelcase) versus bitcoin-cash (hyphenated). The cashaddr spec defines a prefix/scheme that disambiguates; the NIP-A3 client should consult that spec and use the prefix-formatted address in the ["payto", "bitcoincash", "<prefixed-address>"] tag.

fiatjaf's Sep 9 reply — "I don't know, I feel like that should be obvious and people who didn't follow this approach naturally are also not going to read this line" — is the editorial judgment. The merge landed with the wording that alopatindev rewrote after fiatjaf's "What does this mean?" earlier the same day. The takeaway is the conversation shape: a contributor (alopatindev) opens a clarifying PR, fiatjaf asks for an example, alopatindev gives one, fiatjaf asks whether the line is needed at all, alopatindev rewords, fiatjaf merges. NIP-A3 continues to be the active surface in the protocol where payment targets meet Nostr identities.

NIP-90 DVM heartbeat: PR #2465

NIP-90 — Data Vending Machines — defines how clients request computation from a server speaking Nostr. The protocol shape is: client publishes a job kind (5000-5999), worker publishes a result kind (6000-6999), both are replaceable, the relay routes the job to a worker who can do it. NIP-89 is the announcement half: kinds 31989 and 31990 describe what a DVM supports.

What NIP-89 does not say: whether the machine is currently running. A DVM that went offline leaves its announcement behind, and discovery feeds surface stale machines.

PR #2465 (GitHub, opened Sep 10 by believethehype) proposes a fix:

{
  "kind": 11998,
  "pubkey": "<DVM-pubkey>",
  "content": "",
  "tags": [
    ["expiration", "<unix-seconds>"]
  ]
}

A DVM publishes a kind:11998 heartbeat every five minutes (the expiration tag is the canonical Nostr pattern for this event is valid until this time, after which relays should drop it). Clients filter NIP-89 announcements by whether a fresh heartbeat is observable on any of the DVM's read relays.

The proposal is opt-in — NIP-89 does not require heartbeats, but clients that consume them get a higher-fidelity view of which DVMs are actually live. The kind number 11998 is in the replaceable-event range (10000-19999), so updates replace each other rather than accumulating.

The implementation is already running in production: believethehype/nostrdvm is a DVM framework where several content-discovery DVMs (kinds 5000-5999) already emit heartbeats on a 5-minute interval across multiple relays, and the framework's clients use them for liveness filtering. Amethyst committed second-implementation support on Sep 12 ("Now supported in Amethyst."). That second-implementation note is the operative answer to "how quickly would NIP-90 liveness spread if it lands?" — the consumer of NIP-89 DVM announcements is already consuming the heartbeat within 48 hours of the PR opening.

The PR is open. No merge in the window. The PR diff is one kind and one normative paragraph; the harder part is whether the spec text should say heartbeats are required or merely permitted, and whether clients that filter out dead machines should be required to disclose that filtering. Both are open questions in the PR conversation.

NIP-AC WebRTC signaling: PR #2461

NIP-AC (WebRTC signaling for p2p connections, Named666, opened Sep 4, draft as of this writing) is the standardization proposal behind Amethyst 1.09.0's May 15 WebRTC calling (release). The shape: rather than routing voice and video through a relay that can see the connection metadata, the WebRTC SDP exchange rides on the existing Nostr event surface (kinds, tags) and the media flows peer-to-peer once the SDP handshake completes.

The NIP is draft. The implementation is in the consumer (Amethyst). The gap is the spec text that lets other clients interoperate with Amethyst's p2p calls — and the absence of the spec text is the reason Amethyst's calls are today Amethyst-only.

The PR conversation has seven comments as of Sep 13 and no merge. The two-week window between PR #2461 opening (Sep 4) and PR #2465 opening (Sep 10) is the standardization lag — Amethyst shipped the consumer in May, the proposal to standardize it opened in September, and the second proposal (DVM liveness) opened within a week. This is the consumer-before-spec pattern that runs through Nostr development: a single client implements a feature, the spec text catches up later.

The relay-side correctness thread

The three independent stories this week — Citrine 3.1.1, relayer 2.2.19, NIP-90 #2465 — share a theme that was latent in the spec-text work of the previous fortnight:

Item Surface Class of bug
Citrine 3.1.1 NIP-42 fix local relay aggregator signature-verification bypass on auth events
relayer 2.2.19 NIP-45 fix relay reference implementation interface missing for union-count correctness
NIP-90 #2465 DVM heartbeat protocol layer liveness signaling missing for NIP-89 announcements

Two are code fixes and one is a protocol proposal. All three treat the relay hop as a correctness surface, and the fixes ship together because each was reported independently. The pattern: relays are now the bottleneck layer where spec text is interpreted, and the bugs that surface there are the bugs the spec text was supposed to prevent.

The relay-side correctness story has been building across multiple weeks of this library. August 23 documented Amber 6.5.x's authorization-scope advisories (relay-auth confused deputy class). August 30 documented Cambium admission control for kind-22242 bursts. September 06 documented strfry 1.1.2's WebSocket continuation-frame DoS fix in vendored uWebSockets. This week adds the Citrine auth-bypass fix and the relayer COUNT-overlap fix. The relay hop is where the bugs are being closed — slowly, one release at a time, with second-implementation evidence from a different relay than the one that originally shipped the fix.

The frozen thread: NIP #2434 +33 days

NIP #2434 (GitHub, opened Aug 11 by ConorClancy89) — NIP-XX: Post-Quantum Identity Keys — is now 33 days frozen. The PR proposes standardizing the kind:10203 attestation that nostr-wot-extension 0.4.0 (Aug 16), NDK PR #713 (Aug 23), Gleez reference architecture (Aug 30), and Obelisk (Sep 4) all already ship.

Last week's September 06 update counted the days at 26. This week's count is 33. The window from 26 → 33 has no new comment on the PR — only fiatjaf's Aug 11 redirect to issue #1971 remains in the conversation.

The structural argument the Sep 4 Nostr WoT piece made still stands: kind:10203 is a workaround for an identity layer that never declared its own algorithm, the workaround works, needs no relay changes, and should be replaced by something structural. The structural replacement would be a kind:0 field that survives client-side profile rebuilds — but most clients rebuild kind:0 from fields they know about, so a pq_kem field would silently vanish on the first profile edit. The kind:10203 attestation exists because the identity layer cannot host algorithm identifiers. Until either (a) the identity layer changes shape to host algorithm identifiers, or (b) clients stop rebuilding kind:0 from a fixed field list, the kind:10203 attestation is the only surface that holds.

The plateau: 24 attestations published, no new ones in eight days. The plateau first held at 24 in the September 10 WoT update. The kind:10203 attestation is in the same shape that NIP-42's kind:22242 was in before NIP-78 added AUTH enforcement — a workaround that is correct as far as it goes, but which cannot become the protocol-level answer until the surrounding protocol changes.
