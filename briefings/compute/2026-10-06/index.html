Macro Thread — Fluence MCP Server: First DePIN-Compute Platform With Hosted MCP Endpoint + x402 Agentic Payments

The Sep 22 weekly covered Fluence VPC (private networking for VMs) as the first "non-GPU" infrastructure release of 2026. The Oct 6 reading is a second-order claim: Fluence is now the first DePIN-compute network with a hosted MCP server (per the Oct 1 fluence.ai/blog/fluence-mcp-server post by the team), and the first to pair MCP with x402 for agent-paid compute. The structural shift: the previous DePIN-compute UX required opening a Console, picking a config, signing transactions; the Oct 1 reading replaces all of that with "tell your agent what you need in plain language."

From fluence.ai/blog/fluence-mcp-server (Oct 1, 6-min read):

What the table tells you about the Oct 1 release:

  1. MCP is the new "Console" for AI-agent customers. The previous DePIN-compute UX required the agent's human owner to open a Console, navigate the deploy flow, and monitor the deployment manually. The Oct 1 release replaces that with: agent gets a config snippet, agent reads the available actions via MCP, agent calls deploy(config_name) from a prompt, agent calls status(deployment_id) to verify, agent calls shutdown(deployment_id) to clean up. The console is now an internal detail of the agent's tool surface, not a human-facing UX.
  2. x402 as the agent-payment primitive is what makes MCP + no-account possible. The MCP server alone would still require the user to fund a Fluence balance with USDC via the Console. The x402 flow removes that: agent sends USDC on Base to Fluence, the amount lands on the balance in the same request, the wallet that paid becomes the account, and the agent creates its own API key with the wallet's signature as the auth primitive. This is the first DePIN-compute platform where an agent can be deployed, pay for its own compute, and shut down — with no human in the loop and no email signup.
  3. The 11-client config list is the AI-coding-assistant footprint. Cursor + Claude Code + VS Code + Codex + Gemini CLI + Copilot CLI + OpenCode + Cline + Kilo Code + Zed + Continue is the canonical "every AI coding tool that matters in Q4 2026" list. The Fluence Console's MCP page generates per-client config snippets (each one names the file the client reads from: .mcp.json for Claude Code, settings file for Cursor, etc.). This is the kind of "first-class DX" pattern Phala dstack-cloud v0.6.0 shipped for the CVM-Console path (Sep 29) and Marlin Oyster's x402-gateway shipped for the inference-payment path (Sep 1).
  4. The model of "agent holds API key, acts on user's account, spends user's balance" is the same model as Phala's agent-wallet pattern. Phala's solutions/ai-agents page shows a sign-RPC action log of cal-bot, pnl-monitor, inbox-triage, research-bot, devops-bot, support-bot-v3.2, cal-bot calling calendar.read, wallet.readbalance, gmail.composedraft, web.search, github.writepr.merge, zendesk.writeticket.reply, calendar.writecreate with action-level signed RPCs. Fluence's MCP server is the compute-deploy equivalent: agent calls fluence.deploy, fluence.status, fluence.shutdown with the API key as the auth primitive. Both patterns are doing the same thing — making the agent the operator, with the user's key/balance as the trust anchor.
  5. The Claude Code config lives in .mcp.json (project root) but reads the key from a shell env var. The blog post quotes the exact config: {"mcpServers": {"fluence": {"type": "http", "url": "https://api.fluence.dev/mcp", "headers": {"X-API-KEY": "${FLUENCE_API_KEY}"}}}}. This is the canonical "don't put secrets in the repo" pattern for coding-agent tool config. The other 10 clients have user-level configs (Cursor's ~/.cursor/mcp.json, etc.), which is the same defense-in-depth pattern.
  6. The blog explicitly disclaims the danger: "An agent holding your API key acts on your account and spends your balance. Three things keep that predictable: scope the key, keep the key out of your repo, ask for the price first." This is the same threat model as every other "agent holds a key" pattern (Anthropic's claude.ai, OpenAI's Codex CLI, Google's Gemini CLI) and Fluence is naming it explicitly rather than glossing over it. The "ask for the price first" guard is the agent-deploy-specific part — it forces the agent to surface the price before the deploy is signed.

What MCP + x402 Means for the DePIN-Compute Sector

Three observations on the structural shift:

  1. The "Console → Agent" transition is now an open race. Fluence shipped MCP + x402 on Oct 1. Phala's agent-primitive is the sign-RPC action log (CVMs hosting Claude Code/Codex/Vijil, sealed by the compose-hash, with every diff signed before merge). Render Network's OTOY integration is the 3D-rendering tool chain. io.net's Agent Cloud (Jul 25, Oct 3 re-promoted) is MCP-native compute with sub-3-min provisioning, pay-for-work billing via Stripe + x402 — a parallel implementation to Fluence. The four networks are now in different shapes on the agent-primitive axis: Fluence = hosted-MCP + x402 (Oct 1), io.net = Agent Cloud + Stripe + x402 (Jul 25), Phala = sign-RPC + sealed-OAuth (Q3-Q4 2026), Render = OTOY plugin chain (long-standing). The first three are explicitly built for AI agents; Render is built for human 3D artists with AI tooling.
  2. The MCP server being hosted (not self-hosted) is the key developer-experience choice. A self-hosted MCP server would require the user to install and maintain the server binary; the hosted model means the user only has to add the config snippet and restart their client. This is the same trade-off as "Console is a hosted web app" vs "deploy your own console from source" — the hosted version has lower friction at the cost of vendor lock-in. For the early-agent-CLI market, hosted wins on friction.
  3. x402 + USDC on Base is the cross-network payment primitive. x402 (HTTP 402 Payment Required) is the standard that Coinbase, Cloudflare, and others have been pushing since 2024. Fluence's x402 implementation accepts USDC on Base, lands the amount on a Fluence balance in the same request, and uses the paying wallet as the account. Gonka's x402 facilitator (Sep 18, first live GNK settle) is a parallel implementation on a different chain; Marlin Oyster's x402-gateway (Sep 1) is a third. The convergence on x402 across Fluence / Gonka / Marlin means a wallet-based AI agent can pick any of the three networks, pay for compute, and get the same auth primitive. This is the closest thing to a "DePIN-compute payment standard" that has shipped in 2026.

What Fluence Hasn't Shipped (Yet) — The Open Items

Two things the Oct 6 reading can't confirm:

  1. No public adoption metrics yet. The Oct 1 blog post doesn't quote any usage numbers (active agents, deploys, x402 settles, balance load). The Sep 8 VPC release also didn't ship with adoption metrics. The Sep 22 weekly flagged "no Sep 22-specific Fluence news" and the Oct 6 reading adds the same gap. Fluence is now 3 weeks into the post-VPC period and 6 days into the post-MCP period; the first public "agents deployed via MCP" count is the next adoption signal to watch.
  2. The hosting location of the MCP server (api.fluence.dev/mcp) is not specified. It could be on Fluence's own cloud (Fluence runs on Arbitrum Orbit L2 + its own provider network), on a third-party (Cloudflare Workers, Fly.io), or on the same hosted infra that runs the Console. The Oct 1 blog doesn't disambiguate. This matters for trust-minimization: a hosted MCP server on a centralized cloud is a single point of failure for the agent-UX primitive; a hosted MCP server on Fluence's own provider network is a proof-of-dePIN primitive (the network is being used to host the network's own DX).

The Sep 22 weekly covered Phala's dstack-cloud v0.6.0 (the CVM persona) and the SayGM partner page (the inference-gateway persona). The Sep 30 reading is Private AI Proxy 0.3.0 — the third product line, targeted at the AI-coding-agent persona (Claude Code / Codex / Cursor).

From the phala.com/posts/private-ai-proxy-hardware-verified-private-ai-for-coding-agents (Sep 30, 5-min read):

DeepSeek Harness support Live (0.3.0) New web, desktop, headless, and ACP sessions

Persona scope New persona "AI-coding-agent persona" — distinct from "GPU-tee-pod persona" (dstack) and "inference-gateway persona" (SayGM, OLLM)

What the table tells you about the Sep 30 release:

  1. Private AI Proxy is the "agent ↔ AI service" trust primitive. The threat model: a Claude Code / Codex / Cursor agent can read the user's entire codebase, and the AI service (Anthropic / OpenAI / Google) is the egress point for that code. If the AI service is compromised (a supply-chain attack, a malicious plugin, a model-prompt-injection leak), the codebase leaves the user's machine. Private AI Proxy puts a hardware-verified gate between the agent and the cloud AI service — the AI service is verified by a TDX/SEV-SNP/Nitro attestation before the proxy forwards the request, and the agent can refuse to talk to an unverified service.
  2. The Sep 17 Plugin4Shell disclosure is the structural backdrop. Per shattered.io's Plugin4Shell analysis: "Plugin4Shell is a zero-click remote code execution vulnerability disclosed by Air Security on September 17, 2026. It affects the plugin installation process in four AI coding agents, allowing an attacker who controls a plugin's Git repository to bypass SHA-pinning and swap trusted code for malicious code." The four affected agents: Claude Code, Codex, GitHub Copilot, Gemini CLI. The Plugin4Shell disclosure is the first "AI-coding-agent as supply-chain attack surface" story of 2026, and Phala's Sep 30 Private AI Proxy 0.3.0 release is positioned as the answer: even if the plugin is compromised, the proxy verifies the AI service by attestation, so the malicious plugin can't talk to an unverified AI service.
  3. The three Phala personas now cover the three trust-boundary cases. (a) dstack / dstack-cloud / Confidential AI Inference — the "model is in the TEE" persona; (b) SayGM / OLLM / Private AI Gateway — the "inference gateway with verifiable privacy" persona; (c) Private AI Proxy 0.3.0 — the "agent ↔ AI service trust" persona. The three are complementary, not competitive: a developer using dstack for confidential inference can still use Private AI Proxy to gate the agent that calls the dstack endpoint.
  4. The disconnect semantics are the canonical "restore my config" pattern. Disconnect → revoke the local token → restore the config the proxy took over → user edits outside the app are preserved. This is the same UX pattern as Phala's CVM-disconnect (terminate the lease, return the resources, preserve the local file system) and the same trust pattern as Phala's KMS key release (RA-TLS binds the workload to its attestation, so the key is only released while the workload is verified).

Why the Persona Split Matters

Three observations on the structural shift:

  1. Phala is now the only DePIN-compute platform with three named personas for the three AI-customer segments. dstack = "I run a model in a TEE." SayGM / OLLM = "I want verifiable private inference on someone else's model." Private AI Proxy 0.3.0 = "I want my agent to talk to a verified AI service." Each persona is a different trust boundary, and each one has a different customer. The persona split is what lets Phala address the developer-who-runs-models, the enterprise-that-buys-inference, and the agent-builder in parallel.
  2. The "hardware-verified gate" framing is the same trust primitive as dstack's RA-TLS, but applied to a different boundary. dstack's RA-TLS binds the workload to its attestation so the KMS only releases keys to the verified workload. Private AI Proxy 0.3.0 binds the AI service to its attestation so the agent only forwards requests to the verified service. Both are "verify the other side by hardware attestation before the trust-bearing action"; the difference is the direction of the trust-bearing action (KMS release of key vs. agent release of request).
  3. The Sep 30 ship date is one day after dstack-cloud v0.6.0 (Sep 29). The two releases are back-to-back, which is consistent with the Q4 2026 Phala product cadence (a major release every 2-3 weeks per the Aug 4 weekly's product observation). The next Phala cadence checkpoint is in the Oct 13-20 window per the prior pattern.

What the table tells you about the AEP-85 trajectory:

  1. The Sep 30 deadline was missed by T+6 days (Oct 6) with zero console-side work in the pipeline. No PR on akash-network/console, no template on akash-network/awesome-akash, no image on ghcr.io/akash-network/. This is the second time in 2026 an Akash AEP with an estimated-completion date has slipped the date with no PR (the first was AEP-67 in late July, which got pushed by 2 weeks and then delivered Aug 30/31).
  2. The CNCF graduation of Cloud Native Buildpacks on Aug 11, 2026 is the structural positive. Per the CNCF announcement: "CNCF® today announced the graduation of Cloud Native Buildpacks, an open source project that builds OCI-compliant container images directly from application source code. The graduation reflects the project's maturity in production adoption, vendor-neutral governance and security practices." This is the formal "spec is stable" signal for the upstream AEP-85 depends on. Akash adopting a CNCF-graduated spec is the right architectural choice; the implementation just hasn't happened.
  3. buildpacks/pack v0.40.9 (Aug 9) is the latest upstream pack release. Per the pack releases page, the cadence is roughly 1 release per 2-3 weeks; v0.40.9 is the Aug 9 release. The CNB ecosystem is healthy: Heroku, Google Cloud Run, Fly.io, Cloud Foundry, VMware Tanzu all use CNB in production; the buildpacks.io spec is stable. Akash adopting CNB would put Akash's "Git-to-deploy" flow on the same primitive as the rest of the cloud-native ecosystem.
  4. The DX gap with Phala dstack-cloud v0.6.0 is now both more solvable and more visible. Phala shipped the dstack-cloud CLI on Sep 29 (1.5 weeks before the AEP-85 deadline). Fluence shipped the MCP server on Oct 1 (the day after the deadline). Akash is the only one of the three networks whose "developer builds and deploys a containerized app from source" flow is still Draft. The Sep 22 weekly's "Phala dstack-cloud v0.6.0 closes the DX gap" reading is now confirmed: Phala shipped it, Fluence shipped the agent-front-door version, Akash is still drafting.
  5. What slips to: most likely end of October 2026 based on the AEP-67 (late-July) → mid-August slip pattern. Watch for the akash-network/AEP repo for a new commit bumping estimated-completion to a later date, and watch akash-network/console for a new branch. The structural signal to watch is the first PR referencing BuildpacksConfig.tsx or cnb-runtime — that's the "implementation has started" marker.

What the CNCF Graduation Means for the DePIN-Compute Sector

Two observations:

  1. The "buildpacks over Dockerfile" primitive is now a CNCF standard, not a vendor opinion. Every DePIN-compute network that wants a "Git-to-deploy" flow now has the same upstream spec to point to. Akash (AEP-85), any future Akash competitor (Marin's Render RNP series, the Phala dstack repo's own buildpack integration), and the wider cloud-native ecosystem (Cloud Run, Fly.io, Heroku) all converge on CNB. The risk for Akash is that competitors who adopt CNB faster will attract the "I want Heroku-style DX on a decentralized cloud" customer first.
  2. The CNCF graduation also opens the door to vendor-agnostic CNB builders. The AEP-85 spec names paketobuildpacks/builder-jammy-base and heroku/builder:24 as the two vendor-published builder images. With CNB now a CNCF top-level project, more vendor builders (Google's gcr.io/buildpacks, Microsoft's mcr.microsoft.com/oryx/builder, etc.) become fair game as Akash's "BUILDPACKS_TEMPLATE_ID" choices. This is the same "open up the vendor surface" pattern as the AEP-85 AEP itself.

Caveat: DefiLlama Revenue Is Protocol-Fee Only

The 14x gap between DefiLlama's $914,873 × 12 = $10.98M annualized and Aethir's Q3 2025 $39.8M / $166M ARR marketing is structural, not contradictory. Per DefiLlama's methodology: "Revenue: 20% protocol fees charged by aethir." Aethir's $39.8M Q3 2025 figure is the total service fees (the full gross), not the protocol's 20% cut. Aethir's actual protocol revenue (the 20%) at the Q3 2025 peak would have been ~$8M/quarter / $32M annualized, which is closer to (but still above) the current $11M annualized read. The Sep 22 weekly's "6.1% Rev/MC ratio" test is the relevant test: Q3 2025 $39.8M / Q3 2025 mcap ~$650M = 6.1%; current $10.98M annualized / $122.62M current mcap = 8.95% (DefiLlama's compute) or, if we trust the Aethir-side gross, current annualized gross / current mcap = ~70%. The "6.1% test" reads differently depending on which revenue figure you trust.
