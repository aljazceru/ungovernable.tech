Macro Thread — Bittensor V468: Root Reborn Completes, Basket Trading Goes Mainnet (Correction to Last Week's V461 Reading)

Last week's Sep 22 update characterized basket trading as "V461 on testnet, BasketTradingEnabled defaults OFF until governance flips it on mainnet." That reading was wrong on the version number. Per TAO Daily's Sep 22 article "Runtime v468: Cheaper Claims, Copy-Trading, and Active Basket Yields" (Igé A, 2-min read, published 2026-09-22 02:00 UTC) — and per the subtensor PR #2759 "Root Reborn" by unconst which closed Jul 29 with the Skeptic AI Review's HIGH-severity blockers (one-shot migration scans unbounded root-claim state, unbounded basket fan-out in coinbase, unbounded set_root_weights vector) — the correct version is V468, not V461, and the upgrade path on mainnet has shipped the full active-basket surface. The Sep 22 reading needs the following corrections:

  1. The runtime version that delivered the basket-trading surface is V468, not V461. The Sep 15 weekly's "V461 (Basket Trading, Sep 2026)" mention was a typo or anticipation of a number that got bumped twice (V461 → V463 → V465 → V468) during the root-reborn PR's review cycle.
  2. Basket trading is on mainnet, gated behind the active BasketTrading proxy type (V468 upgrade block) and the per-validator basket_trading_status read (enabled, frozen, budget_tao, remaining_tao, used_tao, refill_per_block_tao, refill_blocks).
  3. The --no-mev-shield testnet opt-out from the V461 spec remains testnet-only; mainnet swaps shield by default.
  4. The Skeptic AI Review's HIGH-severity findings (4 of them) were left unaddressed at PR close — the runtime ships with unbounded work in the upgrade migration, the coinbase fan-out, the subnet dissolve path, and the set_root_weights extrinsic. These are availability risks, not correctness/custody risks, but they are now production risks on mainnet.

The structural complement to last week's reading — "V441 stopped forcing every dollar of root yield to be sold the block it arrived; V461 gives the validator the active lever to deploy existing holdings" — remains correct, just relabeled V468. The three reference docs that were correct last week (Basket trading operator walkthrough, Basket trading for governance enable/freeze/tune/rogue-key guide, Basket trading for stakers "nothing to do" guide) are now live product docs rather than aspirational PRDs.

What the table tells you about the v0.6.0 release:

  1. dstack-cloud is the developer-facing product line that complements dstackOS (the bare-metal runtime) and the dstack SDK (the lib for embedding in apps). Before v0.6.0, all three lived in the same repo and a developer who wanted to launch a CVM had to clone dstackOS, compile it, write a custom launch script, and run their own KMS. v0.6.0 ships the CLI + KMS + governance as separate binaries that install from a package manager.
  2. GCP TDX is the first hyperscaler-specific TDX deployment. AWS has had Nitro Enclaves for years (since 2019 for EC2) but Nitro's TDX-equivalent (Nitro Enclave's NSM) is not Intel TDX — it's a custom Nitro Security Module with a different attestation surface. GCP Confidential VMs (released 2024) are the first hyperscaler Intel TDX deployment. Adding GCP TDX to dstack-cloud means a developer can now launch a dstack CVM on GCP without owning any bare-metal hardware.
  3. The on-chain governance surface (DstackKms + DstackApp + Multisig + Timelock) is the production-grade primitive. Before v0.6.0, KMS key release was either (a) policy-gated by an off-chain admin (single point of failure), or (b) policy-gated by a dstackOS config file (mutable by the host). v0.6.0 wires both KMS key release AND app deployment to on-chain contracts; the contracts are owned by a Multisig+Timelock; key release requires both attestation AND on-chain policy check.
  4. RA-TLS for KMS↔workload is the security primitive that makes production key release safe. Without RA-TLS, the workload cannot prove to the KMS that it is the workload that was authorized (vs a hostile workload that copied the key). RA-TLS binds the TLS cert to the workload's attestation quote, so the KMS only releases keys to the workload that was deployed with the right image + compose hash.
  5. VSOCK proxy for Nitro is the networking primitive — Nitro Enclaves have no direct network access; the only networking primitive is VSOCK (host↔enclave). The dstack-cloud CLI's VSOCK proxy allows the enclave to make outbound HTTPS via the host's network, with the enclave's RA-TLS handshake preserved.
  6. The KMS bootstrap (Onboard → Finish) flow handles the cold-start problem. A new dstack deployment has no KMS yet (because there's no CVM to host one yet, and you can't bootstrap a KMS-on-a-CVM without a CVM). The Onboard → Finish flow uses a temporary file-based KMS for the bootstrap, then migrates to a standalone KMS-on-a-CVM after the first attestation is verified. This is the same pattern Phala used internally for its own Phala Cloud launch.

Phala dstack Cloud Pre-Production Caveats

Three caveats from the release notes page that are worth flagging:

  1. Compatibility requirement: Intel TDX-capable GCP zones OR Nitro Enclave-capable EC2 instances. Not all GCP zones have TDX; the TDX-capable zones are the n2d-standard-*-td and c3-standard-*-td families in select regions. Not all EC2 instance types support Nitro Enclaves; the supported families are c5, c6i, m5, m6i, r5, r6i with nitro-enclaves-enabled AMI.
  2. The KMS bootstrap flow requires a working GCP or AWS account with quota for TDX/Nitro. A solo developer without a cloud account can run dstack locally (Local Key Provider mode) but cannot test the production-grade KMS surface without cloud resources.
  3. The on-chain governance (DstackKms + DstackApp + Multisig + Timelock) requires a deployed chain to anchor to. The default is Phala's own Phala Network; cross-chain anchoring (to Ethereum mainnet, Base, etc.) is roadmap, not shipped. This is the canonical "confidential compute requires a chain anchor" constraint — without an anchor, the on-chain policy check cannot happen.

These caveats don't change the structural story (v0.6.0 is the first developer-usable confidential compute product line) but they are the answer to "why is this still pre-production at the enterprise scale" — the friction is in the cloud account setup, not in the dstack code.

Render Foundation — Sep 25 Small-GPU Node Onboarding Round Opens

The Sep 22 weekly noted the Sep 16 Node Bonus Program announcement (bonus accruals starting Oct 1, claims opening Oct 8, RENDER +3% on the night). The Sep 29 reading is the Sep 25 onboarding-round announcement — Render Foundation opened a new round specifically targeted at small operators.

From the Sep 25 @rendernetwork tweet (12.9K views, 7 reposts, 271 likes on X):

Render Network is opening a new round of onboarding for the rendering node pool. We're currently looking for nodes with fewer than 4 GPUs, 16GB+ VRAM, and reliable weekday availability. Interested in joining? Apply here: [renderfoundation.typeform.com]

Tronweekly's Sep 25 coverage confirms the parameters and adds context:

Render Network is opening a new round of onboarding for its rendering node pool as it looks to add more GPU resources to its decentralized infrastructure. In its latest update, Render Network said it is seeking nodes with fewer than four GPUs, at least 16GB of VRAM, and reliable weekday availability. The initiative gives additional GPU operators an opportunity to contribute computing resources to the network. […] RENDER price is recovering as Render Network opens a new GPU node onboarding round. The network development adds fundamental context to the token's latest market move.

The Sep 29 reading:

  1. The target demographic is explicitly "fewer than 4 GPUs, 16GB+ VRAM, weekday availability." This is the first Render onboarding round that names a specific operator archetype — small, weekday-available, consumer-class — rather than the previous "data center (25+ GPUs) + 3D rendering node (any GPU count)" split.
  2. The "weekday availability" requirement is new. Previous Render onboarding rounds did not specify a schedule; nodes could come and go. The Sep 25 round's weekday-availability requirement signals that Render is targeting AI inference workloads (which run during business hours) rather than 3D rendering (which can be scheduled off-hours).
  3. 16GB+ VRAM is the consumer-class floor. RTX 4080 (16GB), RTX 5070 Ti (16GB), RTX 4070 Ti Super (16GB), and the older RTX 3080 (10GB) all fall under this threshold. The previous "Rendering Node" tier required 6GB minimum but 8GB preferred; the Sep 25 round's 16GB floor is the AI-inference target.
  4. The application URL is renderfoundation.typeform.com (the Sep 25 tweet links to renderfoundation.typeform.com, the Render Foundation's Typeform instance). This is the same form URL structure as the rendering-node application form on know.rendernetwork.com.
  5. The Tronweekly framing "RENDER price is recovering" is the structural context — the Sep 16 Node Bonus Program + the Sep 25 onboarding round are back-to-back supply-side pushes. The Sep 16 +3% and +8% rallies (per the Sep 22 weekly) are the demand-side response; the Sep 25 onboarding is the supply-side push.

Why this matters: Render Foundation is currently the only DePIN compute network with a published 3-month supply-side roadmap (Sep 16 Node Bonus, Sep 25 onboarding, both targeting AI inference). Render Network's net-new GPU onboarding in Q4 2026 is the empirical test of whether the "AI/GPU rotation" demand is real enough to absorb net-new supply.

  3. The Sept 22 reading's "Phala dstack-cloud v0.6.0 closes the DX gap" comparison is now concrete. Akash's "Git-to-deploy" flow has been broken for non-JavaScript languages since AEP-28 (the original "Auto Deployment from VCS") shipped in 2025. AEP-85 would fix it with CNB; Phala dstack-cloud v0.6.0 already ships the Docker-Compose-to-CVM flow with a working CLI. The two products are now in different product generations on the developer-experience dimension.
  4. The CNB ecosystem is healthy — buildpacks/pack had releases through v0.40.9 (Aug 9, per the pack releases page). CNB itself is mature (used by Heroku, Cloud Foundry, Google Cloud Run, Fly.io). The buildpacks.io spec is stable. Akash adopting CNB is the right architectural choice; the implementation just hasn't happened.
  5. What slips to: most likely end of October 2026 based on the AEP-67 (late-July) → mid-August slip pattern. Watch for the akash-network/AEP repo for a new commit bumping estimated-completion to a later date, and watch akash-network/console for a new branch.

The Sep 29 reading on AEP-85 is: spec is right, deadline is missed, implementation gap is real. This is the slow lane of W40.
