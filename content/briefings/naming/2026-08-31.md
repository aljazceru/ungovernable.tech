### 2. Root KSK rollover — T-41 days, hard cutoff restated

ICANN's "Preparing for the Root Zone KSK Rollover: What You Need to Know" (Jul 27 blog, re-shared/expanded Aug 27) and the parallel PDF "What to Expect During the Root KSK Rollover" make the date and failure mode explicit:

- **Oct 11, 2026**: root zone signs exclusively with KSK-2024 (Key Tag 38696). The old key is fully retired Jan 2027.
- **>95% of reporting validating resolvers** already hold KSK-2024 via RFC 5011 add-hold. The remaining <5% are the failure surface.
- **Failure mode**: a validating resolver without KSK-2024 in its trust-anchor set loses *all* DNSSEC validation, which for the growing share of DNSSEC-signed zones manifests as total DNS resolution failure — "websites appear down, email bounces." (Priority Pixels UK summary, citing the ICANN release.)

Lessons from 2018: the original rollover was postponed one year because of operator unreadiness. This is the second-ever rollover — only happens when the root key-signing key itself changes (not when resolvers rotate their own trust anchors). For self-sovereign operators (pkdns instances, GNS proxies to DNS, hand-rolled `unbound`/`knot`/`BIND 9.11+` validating resolvers), the operational deadline is **Oct 11** and the verification tool is `delv @resolver . DNSKEY` plus a check against [IANA trust anchors](https://www.iana.org/dnssec/files).

**Cross-reference**: [Overview - Decentralized DNS](/kb/decentralized-dns/); see Aug 24 weekly for the broader KSK comms context. The Aug 24 weekly correctly stated Oct 11 — this update confirms and adds the Jul/Aug 27 ICANN blog pair.

### 3. Reveal Day — formal schedule, ICANNWiki (Aug 27)

The ICANNWiki entry on Reveal Day (and the parallel "New gTLD Program (2026)" entry) formalizes the schedule post-closing:

- **Closing date**: Aug 12, 2026 (1,600+ primary applications; secondary/replacement-string apps also counted).
- **Administrative Check**: applications that pass this review are what Reveal Day publishes.
- **Reveal Day**: specific date to be announced in mid-Sep 2026; publish *must* happen no later than nine weeks after close (≈ Oct 13).
- **What Reveal Day publishes** (more than 2012): primary applied-for strings, variant strings, replacement strings, public portions of each application, contention groups. *Confidential/protected information not posted in full.*
- **What Reveal Day does NOT publish**: anything that confirms an application — published applications remain subject to evaluation, objection, contention resolution, contracting, and technical checks before delegation.

String Confirmation Day (post-Replacement Period) is the next public milestone; applications can still be withdrawn, replaced, or contested. The 2012 Reveal Day was a London press conference with the complete published list two weeks after close. The 2026 round has a longer internal review period (administrative check is more rigorous).

**Volunteer/informal lists are circulating**, but the ICANNWiki piece and CaptainDNS both flag these as **unverifiable** — Reveal Day is the public record.

**Freedom-tech stakes** (continuing from Aug 24): the applied-strings list is the moment Web3-TLD holders (Unstoppable Domains' 19+ portfolio, ENS's `.ens`, Handshake's on-chain TLDs) can diff against ICANN's pending strings and see real collision zones. The Name Collision Observatory's magnitude data is the signal ICANN's evaluators use to flag risk; any string with non-trivial pre-existing query volume gets extra scrutiny before delegation.

**Cross-reference**: [Unstoppable Domains](/kb/unstoppable-domains/) (UD's 19+ application portfolio); [Overview - Decentralized DNS](/kb/decentralized-dns/) §"ICANN engagement"; Aug 24 weekly §"Reveal Day timeline."

### 5. Handshake — hns-rs 0.3.1 released; PR #952 hard-fork still pending

**Two parallel Handshake efforts** visible this week:

#### handshake-rs/hns-rs v0.3.1 (Aug 23)

[PR #3](https://github.com/handshake-rs/hns-rs/pull/3) merged Aug 23 — bumps all **19 public protocol crates to 0.3.1**, publishes the exact direct-offer protocol source consumed by the HNS wallet, removes the superseded oracle-price vector release assertions, retains checked legacy settlement compatibility vectors. The merge was gated on exact-head CI, CodeQL, and a credential-free 19-crate publish preflight. **This is the Rust-native protocol stack** that the Handshake community is building alongside the legacy Node.js `hsd`. The fact that it's a "release cohort" — not a single crate — implies a coordinated SDK release train.

#### handshake-org/hsd PR #952 "Handshake Hard Fork" (open since 2026-03-04)

The headline Handshake hard-fork proposal has not moved this week — last activity May 11, 2026 in the PR thread. Summary:

- **Arbitrary DNS records on-chain** (expand from 7 custom record types to full DNS zone support — A, AAAA, MX, CNAME, SRV, TLSA, generic RAW; 512 → 8,192-byte resource limit).
- **Unclaimed supply reallocation** (~874.7M HNS from expired airdrop + ICANN/Alexa name-claim windows → Handshake Foundation multisig, controlled by long-standing community members).
- **Tree interval reduction** (Urkel tree commits every block instead of every 36 blocks; proof availability from ~6 hours to ~10 minutes; light-client and proof-based verification latency drops sharply).

The PR thread is the canonical place to track this — the two main open threads are about (a) reorg safety at every-block tree commits and (b) whether a Foundation is the right funding vehicle (one commenter flagged the prior dweb foundation's under-utilized funds).

**Why both matter**: the hns-rs Rust stack is the forward-looking implementation; PR #952 is the consensus upgrade that would unlock uncensorable DNS-on-chain (RAW records) and make light-client verification practical. Neither is "shipping next week" — both are infrastructure work for a multi-year migration.

### 6. ICANN Name Collision Observatory — the pre-delegation gate

Live since **Feb 4, 2026**. The Observatory exposes DNS magnitude data (unique client networks querying a string, not total query volume) for the gTLD applicant pool. ICANN's evaluation framework uses this as one of several quantitative factors in string risk assessment — applicants can see whether their chosen string has a collision profile before they commit.

For decentralized-DNS holders, this is the upstream signal: if Web3 TLD strings (UD's `.crypto`, `.wallet`, `.nft`, `.x`, `.box`, etc., or ENS's `.ens`) draw ICANN applicants, the Observatory's pre-delegation magnitude measurement will surface whether the string has any pre-existing resolver traffic that the new gTLD would clobber.

**Cross-reference**: [Unstoppable Domains](/kb/unstoppable-domains/) (UD's 19+ applications portfolio); see [Overview - Decentralized DNS](/kb/decentralized-dns/) §"ICANN engagement" and Aug 10 weekly for the ICANN window context.

## Freedom-tech takeaways

1. **ENSv2 mainnet is one bug-bounty cycle away.** The Aug 18 → ~Sep 22 audit competition window is the canonical "now or never" interval for security review before ENSv2 contracts go to mainnet. Any researcher holding findings on ENSv1 components (resolver behavior, ENS App auth flow, ENS Explorer data display) still has a window via the $250K Immunefi bounty.
2. **Oct 11 KSK rollover is the operational deadline for self-sovereign validators.** Any Daemon-operated validating resolver — including pkdns instances, GNS-to-DNS proxies, and hand-rolled `unbound`/`knot`/`BIND 9.11+` resolvers — must confirm KSK-2024 (Key Tag 38696) in the trust-anchor set *before* Oct 11. `delv @resolver . DNSKEY` against [IANA trust anchors](https://www.iana.org/dnssec/files); ten minutes of verification buys twelve months of operational safety.
3. **Reveal Day ≈ Oct 13 is the Web3-TLD collision trigger.** When ICANN publishes the applied-strings list, the diff against Unstoppable Domains' portfolio, ENS's `.ens`, and Handshake's on-chain TLDs is the audit task. Any string that gets delegated to a competing applicant creates resolution ambiguity for existing Web3 name holders in every ICANN-resolving browser. Key-rooted schemes (PKARR, Tor `.onion`) are structurally immune.
4. **Pubky is in a stabilization phase.** No new tagged releases since Aug 19, but the v0.10.0 → v0.11.0 migration guide is the real news — it locks the SDK/homeserver API surface and gives downstream integrators a stable baseline. The next feature wave (private `/priv` storage, JSON-LD agent discoverability maturation) likely lands late Sep / early Oct.
5. **Handshake's two-track strategy.** hns-rs is the Rust-native protocol stack shipping actively (19-crate cohort release Aug 23). PR #952 is the consensus upgrade that would unlock uncensorable DNS-on-chain, but it remains an open conversation thread with no merge date. Track the hns-node-rs readiness doc — production authority requires a clean mainnet canary.
6. **Name Collision Observatory is the pre-delegation gate.** Any ICANN applicant for a Web3 TLD string gets measured against existing DNS magnitude before their application passes Administrative Check. The Observatory's data is the upstream signal that determines whether Web3 TLD holders face a collision event at Reveal Day.
