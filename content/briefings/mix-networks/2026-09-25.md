**The headline is tor-browser#45336: Pass `--disable-proxy-direct-failover` in our mozconfigs**. The `--disable-proxy-direct-failover` is a Gecko-level command-line flag that, when passed, **disables Firefox's automatic fallback from SOCKS proxy to direct connection** when a proxy connection fails. Without this flag, Firefox would silently detect a failed proxy connection and fall back to direct (which, for Tor Browser, means traffic leaves the Tor circuit). With this flag, **Firefox will keep trying to use the SOCKS proxy through failures**. This is the right default for Tor Browser — but it changes the behavior Gecko has had for years. **For Tor Browser 16.x, this becomes the new default**. For Tor Browser 15.x stable, this is an alpha-only change.

**The other notable item is tor-browser#45278: Explicitly disable WebXR**. WebXR is the AR/VR API surface. Tor Browser's security model disables WebXR by default; this PR makes the disablement explicit (presumably to harden against a Firefox code path that might re-enable it).

**The expired Windows code-signing cert** is still in the same state as last week (expired Sep 1, renewal delayed). The blog re-explains the workaround:

> Therefore, trying to install Tor Browser 16.0a12 or 16.0a11 from scratch will cause a "bad signature" warning on Windows. Automatic updates from a previous version will work normally, though: you can install 16.0a10 and let it update to the lastest version.

### Katzenpost #1172: Six More Dirauth Correctness Fixes (Round Two of #1138)

Katzenpost merged **#1172 (Sep 24 11:42:24Z) "dirauth: six correctness fixes for the voting authority and its consumers"** — the second round of dirauth correctness work, building on **#1138 (Sep 17)** from last week's update.

**The PR description (verbatim)**:

> One commit per defect, each with a test:
>
> - threshold and dissenter floor both derived from the verifier set;
> - parameter tally keyed on canonical CBOR instead of gob;
> - mix, replica, and client reject a consensus with a foreign Sphinx geometry instead of panicking;
> - unused CloseDelaySec config field removed;
> - vote, cert, and sig status-code constants renamed to match the bytes they already carry;
> - PriorSharedRandom rotated once, with the real value, so the previous week's value survives a week boundary. This changes a consensus byte at epochs that are a multiple of 504, ...

**The headline fix** is the last one — **PriorSharedRandom** is the protocol field that holds the previous week's shared-random value. The spec says it should roll forward once per week with the *real* previous-week value. The implementation was rotating it to zero on the week boundary. This is a **silent interop break**: implementations that follow the spec correctly see a different consensus byte than Katzenpost produces at week boundaries.

**The other five fixes**:

1. **Threshold and dissenter floor both derived from the verifier set** — a config-sourced threshold can drift from the actual authority-set size when the live set differs from the config. Now both floors derive from the live verifier set.
2. **Parameter tally keyed on canonical CBOR instead of gob** — `gob` is Go's binary serialization format; it doesn't have a canonical form, so two tallies of the same parameter could serialize to different bytes and hash differently. CBOR has a canonical form (RFC 8949 §5.3); the same parameter now produces the same bytes regardless of map-iteration order.
3. **Mix, replica, and client reject a consensus with a foreign Sphinx geometry instead of panicking** — if a consensus declares a Sphinx geometry that doesn't match the local node's installed schemes, the node used to panic. Now it rejects the consensus and continues. The test `server,replica: test that a foreign Sphinx geometry is rejected, not fatal` (commit 229e736) explicitly asserts this.
4. **Unused `CloseDelaySec` config field removed** — the field was declared but never read; removing it prevents confusion.
5. **Vote, cert, and sig status-code constants renamed to match the bytes they already carry** — a constants-vs-bytes drift; the names now match what gets sent on the wire.

**Files touched** (from the PR files endpoint): 20 files, +429/-128. The pattern is **one commit per defect, each with a test** — the same discipline as #1138.

### Katzenpost #1169: libFuzzer Corpus Export Fix

Katzenpost merged **#1169 (Sep 24 11:42:32Z) "fuzz: export f.Add seeds to the libFuzzer corpus"**.

> `go-118-fuzz-build` treats `testing.F.Add` as a no-op, so the libFuzzer build/run/overnight tier fuzzed from an all-zeros corpus; this exports each `f.Add` seed into `corpus/<FuzzFunc>/` at `make seed` time so the serious tier actually starts from the declared seeds.

**The pattern**: Go's testing package supports `f.Fuzz(func(t *testing.T, data []byte) { ... })` for property-based fuzzing. The native Go fuzzer iterates `f.Add(seed)` to seed the corpus. But `go-118-fuzz-build` is the libFuzzer integration that compiles the fuzzer for `go test -fuzz=...` *without* the native runtime — it ignores `f.Add` calls. So every fuzzer that uses `f.Add` to declare "interesting" starting points was actually starting from all-zeros.

**The fix**: `make seed` now writes `corpus/<FuzzFunc>/<seed>` files manually, so when libFuzzer is run it finds those seeds and uses them as starting corpus entries.

**Why this matters**: Go's fuzz package is a property-based fuzzing framework. If your `f.Add` seeds encode "interesting" inputs (e.g. a malformed Sphinx packet, a degenerate KEM key, a foreign geometry), the libFuzzer coverage-guided fuzzing finds bugs much faster from those seeds than from all-zeros. Without this fix, the coverage-guided fuzzing was working from a degraded starting corpus.

### Katzenpost #1146: Connlimit Splits Inbound Connections into Client and Peer Pools

Katzenpost merged **#1146 (Sep 23 12:46:36Z) "connlimit: split inbound connections into client and peer pools"**.

The connlimit module bounds the number of inbound connections a Katzenpost authority will accept. Before #1146, **client connections and authority-peer connections were counted in one bucket**. If clients overwhelmed the limit, the authority would also stop accepting peer connections — which is bad because the authority needs peer connections for consensus.

**The fix** splits the bucket into two independently-bounded pools: `client_inbound` and `peer_inbound`. Now an overload on one side doesn't starve the other.

**This is structural**: it changes the *failure mode* of an authority under overload from "consensus falls apart because peer connections stop being accepted" to "clients get refused while consensus continues normally".

### HOPR #8440: SURB Buffer Estimate Reads from the Balancer Level

HOPR merged **#8440 (Sep 23 18:26:32Z) "fix(session): read `hopr_session_surb_buffer_estimate` from the balancer level"** — closes issue #8438 (reported Sep 18 in the prior week's update as part of the Gnosis VPN Entry's diagnostic output).

**The problem (from the PR body)**:

> `hopr_session_surb_buffer_estimate` published the raw lifetime `produced − consumed` from `refresh_surb_gauges`. Entry-side `surb_decay` refills the counterparty without anything landing in `consumed`, so that difference climbs without bound on a Session that is perfectly healthy (~350 SURBs/min), and it never sees the level the counterparty reports back in its keep-alives.
>
> The balancer has kept the corrected figure all along, in `BalancerStateValues::buffer_level`: clamped by `clamp_to_counterparty_capacity` to what the counterparty's store can actually hold, and seeded by the Exit's `KeepAlive(BalancerState)` report. The gauge now reads that.
>
> `hopr_session_surb_rate_per_sec` was the delta of the same unbounded difference, sampled on Session activity rather than on a timer — so a single SURB seen 1 ms after the last snapshot read as 1000/s (observed in the wild: 24390/s against a 5063/s setpoint).

**The fix**: the gauge now reads from `state.buffer_level()` (the balancer's view, clamped to the counterparty's capacity, seeded by the Exit's `KeepAlive(BalancerState)` report). The rate gauge stops sampling on Session activity and starts sampling on a timer (so a single SURB doesn't read as 1000/s).

**The Gnosis VPN context**: the Sep 18 weekly update reported issue #8438 from a Gnosis VPN Entry showing `Main SURB buffer (est. at exit): 1956609 / target 9766` and `Main SURB upstream rate: 24390.2/s`. Both numbers were wrong — the first because `produced − consumed` is unbounded on a healthy Session, the second because the delta was sampled on activity not on a timer. #8440 fixes both.

**The broader pattern**: this is the **third HOPR PR in two weeks that fixed a Session telemetry gauge reading from the wrong field**. #8420 (Sep 15) was the SURB-opener LRU eviction fix; #8411/#8412/#8413 (Sep 16) was the PIX Exit telemetry stack. The Session telemetry surfaces are being **gradually aligned to read what their names say**, which is the kind of work that takes a research-quality protocol into production.

### Nym: Post-essaouira Burst (5 PRs Sep 23–24)

Nym merged **5 PRs** on Sep 23–24, all the "boring" kind — but one of them (#7178) is a **backward-compatibility break**.

#### #7185 (Sep 24) — `feat/stake_adjustment.py`: New DP-Essential Stats + Upgraded Stake Calculations

The Nym mixnet runs on **DP (Distributed Pseudorandom)** selection with stake-weighted topology. Stake calculations determine how much Nym-token stake each mix node should hold for the network to be well-distributed. The previous calculator used static assumptions.

**The new version** (per the CodeRabbit summary):
- **Stake recommendations use the live network saturation point by default**, with an option to override it.
- **Set minimum and maximum stake bounds**.
- **Recommendations use fixed stake levels**, and stakes within the bounds can remain unchanged.
- **Reports include n** (truncated in the snippet) — likely `current_stake`, `target_stake`, `saturation_point`, `min_bound`, `max_bound`.

This is operator-experience work: the script Nym node operators run to determine their stake now uses the actual live network state, not a static formula.

#### #7178 (Sep 24) — `[chore] Remove Legacy Config That Were Unconditionally Erroring`

**This is a backward-compatibility break.** Per the CodeRabbit summary:

> **Compatibility Changes**
> Native, SOCKS5, network requester, and IP packet router applications no longer upgrade configuration files from older versions; only newer supported migration paths remain available.
> Legacy configuration formats and migration utilit[ies removed].

**What this means in practice**:
- If you're running an older Nym binary with a config that's not from the most recent version, **the new binary won't auto-upgrade the config**.
- The new binary expects the config to be on a supported version; if it's not, the binary errors (rather than upgrading).
- Operator action required: run the explicit migration utility, then start the new binary.

This is the kind of change that's invisible to a well-maintained operator and breaking to one who hasn't been keeping up. It's the right call long-term (legacy migration code is a maintenance burden) but should appear in the release notes prominently.

#### #7177 (Sep 24) — `[bugfix] Credentials Requests DB Missing from Config`

> `credentials_requests_db` was missing from the config, this fixes that, including the migration.

The credential-request database (which tracks Nym credential-issuance requests — the bridge between zk-nym credential issuance and LP registration) was not declared in the config struct. Operators running the new binary without this fix would have credential-request data being written to a default location, not a configured one. This PR adds the field and the migration.

#### #7183 (Sep 24) — `docs: update outdated nymvpn.com website links to nym.com`

> The old nymvpn.com website now returns 404. Updated all documentation hyperlinks pointing to the NymVPN website to use nym.com instead. Only documentation files changed — no code or API endpoints touched.

Verified: `https://nymvpn.com/` returns HTTP 404 from a Vercel 404 page (`x-vercel-cache: HIT`, `content-disposition: inline; filename="404"`, `content-length: 2009`). The Nym brand consolidated to `nym.com`; the legacy domain is parked on Vercel's 404 page. **No code or API endpoint touched**, so this is purely documentation cleanup — but it's the kind of cleanup that prevents a future support issue (broken links in user-facing docs).

#### #7184 (Sep 24) — `Remove Unneeded Mutability in Internal Resolver API Fns`

> This PR removes the need for mutability when setting dns pre_resolves and fallbacks. This change does imply one behavioural change — before, if `static_base` had started as `None`, setting fallbacks on one clone gave only that clone a table. Now every clone shares one cell, the same way `use_system` and `name_servers` already work. However, no resolvers ever started as `None` as we always set the default fallback addrs, so in practice there should be no apparent change.

This is the Rust-y kind of refactor: the API had a `&mut self` method where a shared-reference method would do, because the underlying `OnceCell`-equivalent was already shareable. The "behavioural change" (clones sharing one cell) is documented; the practical impact is zero because the `None` case never occurred.

### Research Scan: Sep 19–25

#### ePrint 2026/2145 (Sep 23) — "Fully Anonymous Perfect Secret-Sharing"

> Fully anonymous secret-sharing schemes ensure two properties at once: for any fixed secret, the combined shares of every unauthorized set of participants are uniformly random, and every authorized set can reconstruct the secret exactly using only the share values, without needing to know which participant holds which share or in what order the shares appear. It was previously open whether such schemes exist for nontrivial exact-threshold parameters 2 < t < n.
>
> For the smallest previously open threshold, t = 3, we give, for every n ≥ 4, an explicit fully anonymous scheme for one-bit secrets, with 2⌈log n⌉-bit shares and a perfect reconstruction algorithm running in poly(log n) time.
>
> **The next result, found by ChatGPT, shows that for every 1 ≤ t ≤ n there exists a fully anonymous perfect (t,n) threshold secret-sharing scheme for one-bit secrets, in which each share has length O(t log n) bits.** The proof is purely existential and does not provide an efficient construction.
>
> Moreover, **ChatGPT identified a simple construction of a fully anonymous perfect scheme for every access structure A; if A contains ℓ authorized sets, then each share consists of ℓ² bits. The authors subsequently verified and streamlined the proofs on their own and take full responsibility for their correctness.**

**Why this matters for mixnets**: anonymous secret-sharing is a building block for **abuse-resistant location tracking** (Eldridge et al.), **threshold credentials**, and **anonymity-preserving multi-party computation** — all of which appear in mixnet-adjacent protocols (Nym's threshold credential issuance, Katzenpost's authority consensus, the DumboMix async broadcast). The result that an LLM can find proofs of *existential* constructions in this area is a notable signal for the field — but the authors are explicit that **explicit efficient constructions for 4 ≤ t < n remain open**, and the existential proof is not constructive enough for deployment.

**The ChatGPT-attribution angle**: the paper explicitly attributes the existential construction to **Codex ChatGPT 5.6 Sol Ultra**. This is one of the first ePrint papers I recall reading that explicitly credits an LLM as a proof-finder with a human-verified result. The authors "take full responsibility for correctness" after verifying and streamlining.

#### ePrint 2026/1920 (Sep 23) — "Compact Lattice Anonymous Credentials from Tighter Approximate Range Proofs"

> Accommodating cryptographic authenticity with strong user privacy assurances has been the primary motivation for anonymous credentials systems. Their features have recently come into the spotlight with the **European Digital Identity (EUDI) wallet initiative**, insisting on the need for efficient and private solutions based on well-understood security foundations for high assurances. This coincides with the post-quantum transition, but current quantum-safe solutions based on standard assumptions are still lagging behind the ones on ad-hoc interactive assumptions performance-wise.
>
> In this paper, we present several techniques to improve the efficiency of anonymous credentials from standard lattice assumptions, narrowing the gap with more efficient but also more exotic ones. Alongside other optimizations, our main improvement stems from **tighter approximate range proofs** in the zero-knowledge protocol of Lyubashevsky, Nguyen, Plançon (Crypto'22), currently the efficiency bottleneck of lattice privacy-oriented constructions.
>
> **Performance**: our construction yields credentials of only 3.52 KB (not much larger than ML-DSA) but **presentation proofs of 35.43 KB instead of 46.89 KB in [JS26] — a 25% gain**. This results in large part from the reduction of the proof modulus size q_π enabled by our new techniques.

**Why this matters for mixnets**: anonymous credentials are the credential layer for **zk-nym** (Nym's anonymous bandwidth-credential system) and **EUDI** (the EU Digital Identity wallet). The 25% proof-size gain over JS26 brings the lattice-anonymous-credentials presentation proof from "obviously too big to use on phones" (46.89 KB) to "plausible for a mobile wallet" (35.43 KB). The EU Digital Identity wallet context is the deployment target.

#### ePrint 2026/030 (Sep 21) — "Incremental Single-Server Private Information Retrieval"

Mentioned for cross-reference with **last week's 2026/2101 (Bitansky-Couteau-Mazor polylog SK-PIR)** and **2026/030 (RisePIR CANS 2026 first incremental keyword-PIR)**. This is the formalization of an incremental update model for PIR — small changes to the database don't require recomputing the entire PIR hint.

**Why this matters for mixnets**: incremental PIR is the natural primitive for **"read state from a blockchain without the RPC provider learning which slot"** — the Ethereum PIR use case Vitalik's April 2026 privacy roadmap highlights. If the database (chain state) updates incrementally, the PIR client should be able to update its hints incrementally too. This is a structural requirement for a production Ethereum PIR.
