**The headline is `tor-browser#45333: Disable the fast-path to skip proxy resolution`** — paired with `tor-browser#45336` from last week's 16.0a12 (`Pass --disable-proxy-direct-failover` in mozconfigs). ### Nym sphinx 0.8.0 (PR #7197, merged Oct 1): Legacy SURB Formats Removed

Nym merged **#7197 (Oct 1 14:08 UTC)** `bump sphinx to 0.8.0` by simonwicky. The PR description is two lines and a diff of **+41/-532 across 23 files** — a **large net-removal** because the legacy format code paths come out entirely.

> Bump sphinx to 0.8.0
> Remove support for legacy SURB format
> Config fields are kept as-is to avoid another migration, it will disappear with LP

The CodeRabbit summary:

> **Protocol Changes**
> - Packet creation and reply SURBs now use the current payload-key format; legacy format selection is no longer available.
> - Repliable messages now use V2 content. V1 data, additional-SURB, and heartbeat formats are no longer supported.
> - Incoming V2 data messages are reconstructed with their reply SURBs forwarded. Additional-SURB and heartbeat messages forward associated SURBs according to their content type, with heartbeat SURBs handled separately from request-originated batches.

**The headline is "V2-only repliable"**: the protocol now speaks only the current payload-key format for repliable messages. **Config fields are kept as-is to avoid another migration** — the persisted config schema is not changed; the LP (likely "legacy payload" or "legacy protocol") replacement will remove the config field entirely later.

**Why this is consequential**: any Nym client that spoke V1 SURBs (or used `additional-SURB` / `heartbeat` formats) cannot interoperate with post-#7197 nodes. The deployable surface is the v2026.17-djibouti (Sep 2) release, which predates the merge — so the **first Nym Binaries release with the V2-only world is the next one after v2026.17-djibouti** (the v2026.18 or v2026.19 release). The changelog at https://nym.com/blog/nymvpn-roadmap lists v2026.18 as September 2026 and v2026.19 as October 2026 — so the deployable release is imminent.

**Co-deployed with #7191** `crates release: bump version to 1.22.1` — the public crates.io version bump that mirrors the in-tree 1.22.1 crates release.

### Nym Threat-Model Transport Docs Correction (PR #7192, merged Sep 29): Direct vs. Mixnet Visibility, Finally Explicit

Nym merged **#7192 (Sep 29 11:10 UTC)** `Max/threat model transport corrections` by mfahampshire (reviewed by merve64). +63/-17 across 5 files.

> **Documentation**
> - Threat-model references now distinguish what adversaries cannot observe over direct connections versus when the client uses the mixnet.
> - Actor descriptions clarify that **direct destinations can see the client's IP**, while **mixnet destinations see the exit gateway's IP**. They also explain how mixing and cover traffic limit network observers' visibility into routes, packet correspondence, and communication activity.
> - **The primary adversary is now labeled explicitly**.

**Why this matters**: the previous threat-model docs treated the destination's visibility as a single statement that was technically wrong in two cases — it overclaimed the destination's view over direct connections (the destination sees the client's IP) and it overclaimed the destination's view over mixnet-mode (the destination sees the exit gateway's IP, not the client's). The PR corrects both. **The primary adversary is now labeled explicitly** — readers no longer have to infer it from context.

For builders integrating Nym, the corrected model is: **direct connections leak the client's IP to the destination; mixnet connections leak only the exit gateway's IP to the destination; the network observer sees different information in each mode**.

### NymVPN Network Upgrade Pre-Announcement (Sep 24 blog): Credential-Issuer Key Rotation

[Nym published a blog post on Sep 24](https://nym.com/blog/nymvpn-network-upgrade) titled "Update NymVPN for an upcoming network upgrade". The headline:

> Nym will be rotating that system's signing keys and refreshing the operators who run it. The result is a more robust, more decentralized foundation for the credentials that protect your privacy. For most people this upgrade will be invisible. If you're on the latest version, your connection keeps working throughout the upgrade. Older versions may be briefly unable to fetch new credentials while it happens, which can interrupt new connections or fresh sign-ins.

**The action item** is `update to v2026.12.4 or newer`. The exact date is **not yet announced** ("We will announce the exact date soon. There's nothing to wait for: updating now means you're ready whenever it happens.").

**Why this matters**: NymVPN v2026.12.6 (Sep 21) was an Android-only fix (prefer Wi-Fi over cellular when binding the cover tunnel, PR #6421). **The Sep 24 pre-announcement targets the credential-issuer side of the network, not the client-app side**. The credential issuer is the decentralized set of operators that issue zk-nyms through the credential proxy — the anonymous-credentials layer that lets a NymVPN user authenticate without revealing their identity to the network. **Rotating the signing keys + refreshing the operator set** is a credential-network hygiene event: it limits the blast radius of any single operator compromise and re-randomizes the trust set.

**Practical impact**: any NymVPN user below v2026.12.4 (the Sept 1 release that fixed pinned-gateway bypass-of-blacklist, and the Sep 17 / 18 / 21 .5 / .6 stack) should upgrade before the announced key rotation date.

### Katzenpost #1182 (Oct 1, by tirewapped): client/thin Race Fix + Windows `-race` + Go 1.26.8

Katzenpost merged **#1182 (Oct 1)** `client/thin: read conn under connMu, run windows under -race, move to go 1.26.8` by tirewapped.

> I count **five places** that read `t.conn` without holding `connMu` while `Dial` and `redial` write it under the lock. This is likely the cause of the intermittent `found pointer to free object` crash in the Windows `client/thin` job. Also we restore runs of the Windows unit tests to be performed under `-race` like every other platform. This also moves the go directive to 1.26.8 so `make check` passes off the CI image and we have 1.26.8 rather than an older version with outstanding issues that (likely) caused the CI to fail.

The five sites are in `client/thin/thin.go`:
- `Dial()` — the handshake-timeout path reads `t.conn` to call `SetDeadline` on it. Snapshot under `connMu.RLock()`.
- `writeMessage(request)` — reads `t.conn` for `Write`. Snapshot under `connMu.RLock()`.
- `readMessage()` — two reads (the `ReadFull` of the 4-byte prefix, then the `ReadFull` of the message body). Both now snapshot under `connMu.RLock()`.

The pattern is: **read `t.conn` under `connMu.RLock()`, copy the local `conn` value, release the lock, operate on the local**. This eliminates the data race where a concurrent `Dial`/`redial` writes a new value to `t.conn` while another goroutine is reading the old value (which can produce the "found pointer to free object" symptom if the old value was finalized between the read and the use).

**Windows unit tests + `-race`** — the CI workflow now runs Windows unit tests under the race detector like every other platform; previously they ran without `-race`, which means Windows race regressions could ship undetected.

**Go 1.26.2 → 1.26.8** — the module `go` directive moves forward to 1.26.8 so `make check` passes against the CI image. The Go 1.26.8 bump is paired with the race-detector work to ensure the codebase is race-free under the newer Go.

### HOPR Oct 1 Cluster: Stalled-Sink Head-of-Line-Blocking Fix + Return-Path Blind-Spot Diagnostics + Crate Bump + SURB Eviction Counting

HOPR shipped **5 merged PRs on Oct 1** plus the Sep 29 **StartInitiation additional_data 128-bit extension** breaking change.

**#8463 (Oct 1)** — `fix(transport): time out and evict a stalled write-pump sink to stop egress head-of-line blocking`. ### Research Scan (Sep 25 – Oct 2)

**arXiv 2609.01326 (Sep 1) "Hidden Services Protocol for Mixnets"** by Constantinides et al. (Brave NewCoin research via Nym):

> Mix networks (mixnets) provide network-level privacy by routing each communication packet through a sequence of intermediaries, called mixnodes, that randomly delay and cryptographically transform packets before forwarding them, making it difficult for observers to link mixnet entries to exits. While this mechanism protects sender privacy from both external adversaries and the receiver, existing mixnets lack a secure and practical protocol that simultaneously protects receiver (destination) privacy, particularly from the sender. We close this gap. We introduce the first practical and secure hidden-service protocol for mixnets, providing receiver privacy alongside sender anonymity. Our design builds on Single-Use Reply Blocks (SURBs), which enable anonymous replies without revealing the receiver's address. We show, however, that existing approaches to using SURBs expose two practical attacks that can compromise sender or receiver anonymity when the opposing party controls only a single mixnode. We develop defenses against both vulnerabilities. Building on these defenses, we introduce NymHS, a secure and practical hidden-service protocol for mixnets that supports anonymous service discovery, authenticated bidirectional sessions, and asynchronous SURB replenishment. We implement NymHS on the open-source Nym codebase and evaluate its practicality through web-browsing experiments across 118 websites, measuring each of the 27 configurations three times (9,558 page loads). Our results demonstrate that hidden services can be deployed efficiently over mixnets. In particular, increasing the Sphinx payload from 2 KiB to 10 KiB reduces mean page-load latency by approximately 5.2x and decreases communication overhead from 21.7 % to 4.3 % relative to the current Nym baseline.

**The relevance to Nym's sphinx 0.8.0 upgrade**: the paper's headline result is that **increasing Sphinx payload from 2 KiB to 10 KiB reduces latency 5.2× and overhead from 21.7 % to 4.3 %**. Nym's prior payload size was 2 KiB; the paper's proposed 10 KiB payload is closer to Nym's 0.8.0 direction. **The Sphinx 0.8.0 upgrade is potentially the deployable path for the larger-payload result** — if Nym adopts 10 KiB Sphinx payloads, the hidden-service protocol from the paper becomes deployable on the open-source Nym codebase.

**arXiv 2609.01075 (Sep 1) "Lacan: Making Accountability in Anonymous Networks Real"** by Takada, Yoshinaka, Kita, Takemasa, Koizumi, Hasegawa:

> Anonymity and accountability are essential properties for our everyday activity on the Internet. However, they appear contradictory, and their reconciliation remains far from reality. Existing approaches fall short in this regard, as they either rely on an on-path trustee, per-packet authorization, per-packet public-key cryptography, or per-session intervention by a central authority. We propose Lacan, a protocol that reconciles anonymity and accountability within a realistic design. In Lacan, a sender enjoys anonymity provided by on-path relays, as long as she complies with a contract established with the receiver. Upon a contract violation, the verifier, an off-path trustee on behalf of the receiver, links the malicious message to the sender's identity indirectly via the packet, path, and session, thereby reducing public-key operations from per-packet to per-session.

**PoPETs 2026(4) "Breaking and (Partially) Fixing Onion Routing with Fragmentation"** — the "Fragging attack":

> Mix networks are a cornerstone of anonymous communication, protecting users' relationships by relaying their messages through a series of mix nodes. To accommodate large payloads, deployed systems rely on message fragmentation, but this seemingly benign feature unwittingly opens a subtle door for adversaries. In this paper, we show that fragmentation enables adversaries to tag messages by suppressing single fragments and thereby break sender-recipient unlinkability, striking at the core privacy guarantee of mix networks. We demonstrate the practicality of this attack on Nym, a real-world deployed mix network. To address this threat, we design a lightweight mitigation that incurs only little overhead in both packet size and processing time. We provide a formal model of fragmentation in mix networks and prove that our mitigation restores unlinkability in this model.

**The paper's mitigation is Scylla**, a Sphinx-derived mix format with all-or-nothing-transform fragmentation that ensures all fragments arrive before revealing the recipient or the message. **Same performance characteristics as Sphinx**; same-fragment drop losses turn from privacy leakage to DoS. **Direct Nym relevance**: Nym uses Sphinx fragmentation to handle multi-M messages, and the "Fragging attack" lets a malicious Nym server drop single fragments to confirm sender-receiver pairings.
