**The two H1-severity WebAssembly-at-Safer fixes are the most security-critical items in the release**:

- **tor-browser#45296 (H1)** — **SharedWorker Identity Mismatch allows WebAssembly execution at Safer**. Tor Browser's security levels (Standard, Safer, Safest) constrain WebAssembly to specific security levels — at *Safer*, WebAssembly should be sandboxed to the realm's origin. A SharedWorker's identity mismatch allowed WebAssembly execution at a level below where it should be allowed, bypassing the security-level boundary. The fix matches the SharedWorker's identity to the realm's identity for security-level checks.
- **tor-browser#45297 (H1)** — **Missing `setHTMLUnsafe` hook leaves a permanent WebAssembly-capable child realm at Safer**. The `setHTMLUnsafe` hook is one of the per-realm guards that the Tor Browser patches add to constrain WebAssembly execution to specific security levels. A missing hook for one method left a child realm permanently WebAssembly-capable at *Safer* — which should be impossible under the Tor Browser security model.

Both bugs were reported through Mozilla's bug bounty program and given H1 (highest severity) ratings — the WebAssembly-at-Safer class is exactly the failure mode the Tor Browser security patches are designed to prevent. Both fixes ship in 15.0.23.

**The Windows code-signing cert disclosure** (from the Tor Project blog):

As a temporary work-around, for Windows only we're keeping Tor Browser *15.0.20* (the latest correctly signed version) listed on our [download page](https://www.torproject.org/download/), relying on automatic updates (which are signed with a different key, not involving this expired certificate) to bring Windows users to the current version. The blog post is dated Sep 15 and explicitly tells users the workaround; this is the right way to disclose an expired-cert issue (public, workaround included, no security impact for installed users).

### HOPR PIX/Transport Trilogy: 4.1.x Throughput Regression Fix + Pool Arbiter + PIX Exit Telemetry Stack

HOPR shipped a dense cluster of PIX and transport-layer PRs Sep 15–17. The **headline is the 4.1.x throughput regression fix** (PR #8424) and the **pool arbitration design** (#8426), both written by Claude Opus 4.8 / 5 in the agent-traceable style that's become characteristic of recent HOPR PRs.

#### #8424 (Sep 17) — Derive Packet-Pipeline Concurrency Defaults from CPU Count

> **The 4.1.x line regressed relay throughput relative to 4.0.3.** Field measurements pinned it to the relays, not the exit: throughput collapsed only when the relays ran 4.1.x, regardless of the exit's version.

**The cause**: the ingress decode-concurrency default introduced in #8246. That change capped the default at `pool_thread_count − ENCODE_RESERVED_THREADS` to keep encode threads free for SURB generation on a busy exit. But in production the shared Rayon pool is sized to `available_parallelism()/2`, so **on a 4-core node the default evaluates to `2 − 2 = 0`, which clamps to `1`** — the node decodes packets essentially one at a time. Because forwarding is decode-only, a relay carries no encode/SURB work for that reservation to protect, so the cap was pure loss there, and since a session is bidirectional, throttling one relay direction dragged down both download and upload.

**The fix**: the default is now derived from the CPU count rather than the pool size — both the decode and encode stages fall back to `available_parallelism × 8` — the pre-#8246 deep-queue depth. These values are ready-queue depths feeding the shared pool, not thread counts, so tying them to the (smaller) pool size was the category error that produced the collapse. The ingress throttle mechanism is unchanged; its watermark simply scales with the corrected concurrency.

This intentionally restores the encode/decode balance to its pre-#8246 behaviour. The original goal of that change — protecting encode/SURB generation from decode floods under a congested shared pool — is real, but it belongs in a follow-up that arbitrates the pool dynamically.

#### #8426 (Sep 17) — Pool Arbitration (the Follow-Up to #8424)

> **Task 2** of the #8246 fix on master: wires the encode/decode pool arbiter into the packet pipeline. Task 1 (#8424) restored CPU-derived concurrency defaults, fixing the relay forwarding collapse; this PR removes the per-packet ingress sleep-gate and replaces it with an asymmetric, occupancy-gated arbiter (in `hopr-utilities`) that protects SURB encode from decode floods without ever throttling pure forwarding.

> The arbiter only throttles decode admission when the shared pool is saturated, encode work is present, and decode genuinely floods relative to encode — so a forwarding relay (encode ≈ 0) and any unsaturated node are never affected. It is configured *first-wins* (`configure_arbitration_once`) because the pool is process-global: a per-node pipeline startup cannot clobber a peer's arbiter or an explicit benchmark override. `PoolArbitrationConfig { enabled, occupancy_pct, encode_reserve_pct }` is operator-tunable with range validation.

**Measured with real SPHINX op costs on a pinned pool**: SURB encode ~2.1× protected under a decode flood with halved P99, and zero overhead for forwarding, balanced, and encode-heavy regimes.

This is the **structural answer** to #8424: the previous fix preserved the encode/decode balance by giving each stage its full `available_parallelism × 8`; this fix adds back the original #8246 protection for encode (SURB generation) against decode floods — but only when encode work is actually present and decode is genuinely flooding relative to encode. A pure-forwarding relay pays nothing. A balanced relay pays nothing. Only the case #8246 was originally trying to fix (busy exit with concurrent encode and decode, decode flooding) gets throttled, and even then only when the pool is actually saturated.

#### #8411 / #8412 / #8413 (Sep 16) — PIX Exit Telemetry Stack

A three-PR stack that adds **bounded node-level PIX Exit telemetry** with no PII labels.

- **#8411 (Sep 16)** — `feat(session): bounded node-level PIX Exit telemetry`: eight bounded aggregates under `hopr_pix_*` — `hopr_pix_sessions_active{gate_mode}` (live Sessions, funded vs unfunded), `hopr_pix_cycles_active{phase}`, `hopr_pix_predeposit_exposure_packets` (service given away, not yet paid for), `hopr_pix_cycles_total{event}` (requested / committed / funded / recovered / failed), `hopr_pix_admission_rejections_total{reason}` (why incoming PIX Sessions were refused), `hopr_pix_live_cycle_bytes` + `_reserved_total` / `_released_total` (reconstructor-cycle budget). The two existing per-Session gauges are unchanged — this adds alongside. The identifier deny-list guard lives in `generate-metrics-docs.sh` (run by the pre-commit hook) so a regression that adds a `session_id` label fails in CI.
- **#8412 (Sep 16)** — `feat(session): PIX egress gate pressure telemetry`: `ServiceGate::try_acquire_sync` returns a `GateVerdict` instead of a `bool`. Both refusal sites already knew which case they were — this only stops discarding it. New metrics: `hopr_pix_egress_packets_total{mode}`, `hopr_pix_gate_blocks_total{reason}` (`predeposit_exhausted` / `share_lag` / `closed`), `hopr_pix_gate_block_seconds{reason}`. Counting is **episodes, not refused packets** — a blocked gate is polled again by whoever is sending, so counting refusals would measure how hard the caller retries rather than how long the Exit was stalled. Episode is an RAII guard opened at the refusal — not at first poll, since the refusal has already happened — and closed by `Drop`. Benchmarks: `funded` path 31 µs (unchanged), `predeposit` path 60 µs (+3.7 ns/packet, under 4 µs for a whole rotation at the shipped value).
- **#8413 (Sep 16)** — `feat(session): PIX share and per-cycle recovery coverage telemetry`: `hopr_pix_shares_total{kind}` (newly accepted shares, `useful` vs `surplus`), `hopr_pix_cycle_egress_packets{outcome}` (what a cycle cost, observed once at finalization), `hopr_pix_cycle_useful_share_fraction{outcome}`, `hopr_pix_cycle_accepted_share_fraction{outcome}`. **Design note: absolute snapshots, never summed.** `SsaRecoveryProgress` is absolute and acknowledgement batches arrive out of order, coalesced, or not at all, so `shares_seen` must never be added to a counter. The supervisor keeps a high-water mark per cycle; the delta against it is taken at the one point where a snapshot is known to be both validated and newer than everything before it.

Plus `OTLP.md` documenting the `hopr_pix_*` / `hopr_session_pix_*` exporter split and worked PromQL for every operator question the issue lists.

#### Other HOPR PRs this week

- **#8420 (Sep 15)** — `fix(surb-store): keep newest reply openers so sustained uploads survive`. **The same fix as #8417 (v4.0 line) on master**: the inner per-pseudonym reply-opener cache was built with no eviction policy, so it uses moka's default Window-TinyLFU. Reply openers are written once and never read before they are used, so every entry carries the same zero access frequency and TinyLFU keeps the incumbent on each tie — **a full cache freezes the oldest openers and drops every newer one**. The exit's SURB ring always holds the newest SURBs — exactly the openers just discarded — so once the opener cache overflows, every reply becomes undecryptable, independent of pop order and buffer ratio. **Fix**: give the inner opener cache `EvictionPolicy::lru()`. On this write-only workload LRU evicts by insertion order — sheds the oldest, keeps the newest — a circular buffer that mirrors the SURB ring. Patch-bumps the crate to 6.3.1.
- **#8422 (Sep 15)** — `fix(session): datagram-aware UDP copy loop end to end`. **The Gnosis VPN WireGuard-over-Session download collapse fix.** Root cause (hoprnet#8421): the session copy loop coalesces several return-path UDP datagrams into one oversized session write under backpressure — before the segmenter runs — so the datagram boundaries are lost and cannot be recovered. hoprnet#8358 (one frame per write) is necessary but not sufficient on its own. **Forward-port of #8358 to master** + **datagram-aware copy loop, wired end to end**. `transfer_session_datagram` is re-exported through the transport chain and used by both UDP session bridges. TCP bridges keep the byte-stream fast path.
- **#8424 (Sep 17)** — see above.
- **#8426 (Sep 17)** — see above.
- **#8428 (Sep 16)** — `fix(logging): demote routine SURB expiry evictions and unbalanced-session notice to debug`. Log-level hygiene.
- **#8392 (Sep 16)** — `feat(session): gate organic SURB production on the balancer target`. SURB production only runs when the balancer has signalled it wants traffic.
- **#8398 (Sep 15)** — `feat(session): drain buffered SURBs after an Exit-side close when they cover the funded cycle`. Survivability: SURBs that cover a funded cycle get drained instead of dropped on close.
- **#8406 (Sep 16)** — `chore(renovate): run on numeric release branches`. Renovate now processes `release/<major>.<minor>` branches in addition to the default branch. The regex `/^release\/\d+\.\d+$/` matches the scheme produced by the release-promotion workflow and deliberately excludes non-numeric legacy branches and hotfix/patch/nested suffixes.
- **#8411/#8412/#8413 (Sep 16)** — see PIX Exit telemetry stack above.
- **#8430 (Sep 17)** — `refactor(session)!: drop pix_ssa_quota from session client config`. **Removes `pix_ssa_quota` from `SessionClientConfig`, `HoprSessionClientConfig`, and `HoprSessionClientExplicitPathConfig`.** `Capability::UsePIX` is now the whole per-Session PIX switch. The reason: PIX dimensions were never a per-Session choice — `new_session` builds what it announces from the node's installed `SsaShareGenerator`; `pix_ssa_quota` was only compared against that value and then discarded. Exactly one value was ever accepted — the node's own — so the field carried a single bit of information (`is_some()`) while presenting itself as a dial.

**The PIX/transport cluster as a whole**: HOPR is **making PIX (Payment-In-channel eXchange) operable at the supervisor level**. The previous two weeks added the SURB protocol-version boundary (#8365) and the relayer-diversity diagnostics (#8368). This week adds **observability for PIX operation** — bounded node-level aggregates with no PII, gate-pressure episodes instead of refused-packet counters, and cycle-by-cycle recovery coverage — so an operator can actually answer the question "is the PIX Exit doing what it's supposed to?". This is the kind of work that turns a research-quality protocol into a production system.

### Katzenpost: Dirauth Hardening Sweep + hpqc v0.0.87/v0.0.88/v0.0.89 Adoption

#### #1138 (Sep 17) — Review the Voting Directory Authority (the og-clean PR)

> Reviews the voting directory authority (the "og" dirauth) and fixes what turned up.

The PR has 444 lines of changes. The headline:

- **Reject bad input instead of panicking**: Addresses, short descriptor identity keys.
- **Guard the shared-random and certificate paths**: set-commit, cert epoch binding, vote-as-cert, reveal bounds, authenticator AD.
- **Give the PKI wire message a real size ceiling that covers the inter-authority certificate, derived from the configured schemes and topology, and wire it into clients.**
- **Connections**: recover per-conn panics, cap concurrent and per-peer conns, log and drop unknown peers, bound the first command and keepalive writes, drain accepted conns on shutdown.
- **Persistent inter-authority connections stay opt-in, default off.**

Adds a scheme matrix and per-fix regression tests. Verified on a full mixnet and a mixed patched/unpatched authority quorum.

This is the kind of code that doesn't generate a release note per-line; it generates a "we audited our own dirauth and here's what was wrong" PR. The size ceiling fix in particular is the kind of bug that lives in the protocol spec until a heterogeneous authority set is actually deployed — the assumption that every authority agrees on the PKI scheme was unenforced.

#### hpqc v0.0.87 → v0.0.88 → v0.0.89 Adoption (Sep 14–17)

hpqc is Katzenpost's hybrid post-quantum crypto library. This week Katzenpost adopts three consecutive releases of hpqc that together implement **degenerate-key hardening**.

**The high-level pattern**: hpqc's NIKE/KEM primitives now reject or neutralize degenerate peer input instead of panicking or silently using it. Specifically:
- `mkem Encapsulate` and `EnvelopeReply` now return an error (was: panic on degenerate recipient key).
- `Scheme.Blind` returns nil (was: panic on degenerate group element).
- `DeriveSecret` and the in-place `Blind` leave an all-zero result the caller must reject (was: attacker-predictable shared secret from a low-order point).

The Katzenpost PRs that adopt this hardening:

- **#1136 (Sep 14, "adopt hpqc's degenerate-key hardening")** — bump hpqc to v0.0.87, thread the new error return through every `mkem Encapsulate` and `EnvelopeReply` call site; a degenerate recipient now fails the operation. **Reject an all-zero shared secret in sphinx packet creation and unwrap paths (util.CtIsZero)**, per the hpqc DeriveSecret contract. **Reject a nil `Scheme.Blind` result and an all-zero in-place Blind result**, so a degenerate group element cannot propagate through the chain.
- **Followed by ~9 commits Sep 14**: `sphinx: reject a degenerate shared secret`, `sphinx: reject a nil blinded key`, `sphinx: reject a degenerate blinded key from the in-place Blind`, `adapt to hpqc's mkem error returns`, `go.sum: pin hpqc v0.0.87`, `Merge origin/main into adopt-hpqc-degenerate-key-hardening`, etc.
- **Sep 17: #1154** — `Bump hpqc v0.0.88` — breaking changes to hpqc's BACAP API now require Katzenpost to change its BACAP call sites.
- **Sep 17: `version bump to hpqc v0.0.89`** — additional BACAP-related call-site fixes (test fixture validity check, error-return handling).

The pattern is exactly the same as the Sep 11 katzenpost PRs that adopted the prior hpqc version, but bigger and more consequential. **The degenerate-key class** — low-order X25519/X448 points, CTIDH base curve E0 — is exactly the kind of input that an attacker can supply to crash the peer. hpqc hardening moves from "panic" to "return error" to "caller must reject"; Katzenpost adopts every step.

#### Other Katzenpost PRs this week

- **Sep 17: `authority/voting/client: close the dialed conn on a scheme lookup error`** — `initSession` dialed the peer, then returned without closing conn if the peer's configured `WireKEMScheme` or `PKISignatureScheme` name was unregistered. Every PKI client operation against a misconfigured peer (e.g. each polling interval) leaked one socket. Also: warn when a reply is rejected as oversized — `deriveMaxMessageSize` assumes a bounded topology since a client cannot know the real one before its first consensus fetch, so a network that outgrows that allowance otherwise fails PKI fetches with no diagnostic beyond a bare wire error. Export `wire.IsOversizedMessageError` to detect it.
- **Sep 17: `courier: reject a configured authority set that disagrees on PKI scheme`** — `newPKIWorkerWithDefaultClient` derived its PKI signature scheme (and so its wire ceiling) solely from the first-listed authority, on the unenforced assumption that every authority shares it. A heterogeneous config silently under-estimated the ceiling for whichever authority was not consulted, rejecting its legitimate traffic as oversized.
- **Sep 17: `authority/voting: split onCertUpload and dialAndHandshakePeer`** — pure extraction to bring both under the 95-line screen limit. No behavior change.
- **Sep 16: `authority/voting: bind uploaded vote, reveal and sig to the peer`** — `onCertUpload` verified that the certificate's declared PublicKey matches the wire-authenticated peer, but `onVoteUpload`, `onRevealUpload` and `onSigUpload` did not (onVoteUpload's comment wrongly claimed otherwise). An authorized but byzantine authority could therefore relay another authority's genuine vote, reveal or signature over its own connection. Apply the same identity-binding check to all three.
- **Sep 16: `authority/voting: wait a full keepalive interval between peer commands`** — the persistent authority serve loop reset the idle read deadline via `RecvCommand`, whose `armIO` caps every read at the session `ReadTimeout` (`ResponseTimeoutSec`, 30s). That clobbered the intended keepalive idle timeout (120s), so a warm connection closed 30s into an idle gap and the next keepalive (60s) never arrived, defeating the persistent-connection feature. Raise the session read timeout to the keepalive interval for the serve loop.
- **Sep 16: `core/wire: serialize each logical send and receive as a unit`** — `SendCommand` guarded only each individual cipher operation, so two concurrent sends on one Session could interleave a message's header encrypt, body encrypt and rekey with another's, desyncing (or reusing) the ChaChaPoly nonce stream and corrupting every subsequent frame. Hold one exclusive lock across the whole send (through the wire write) and across the whole receive.
- **Sep 16: `authority/voting: a missing shared-random reveal must not break consensus`** — the certificate embedded every commit and every reveal an authority had seen. When an authority saw a peer's vote (commit) but never its reveal, which happens when a peer goes down between the vote and reveal deadlines, the commit and reveal sets had unequal cardinality, so `IsDocumentWellFormed` rejected the certificate and the authority emitted none. When enough honest authorities were in that state the round produced no certificates and consensus stalled: a single non-revealing authority could break a six-authority network far above its fault threshold. Embed only the commit/reveal pairs we hold both halves for, logging and dropping a commit whose reveal we never received; as long as at least threshold authorities revealed, consensus still forms. Verify at reveal-upload time that a reveal opens its commit, so an honest certificate can never carry a signed-but-mismatched pair. Turn the commit/reveal mismatch case in `getMyConsensus` from a panic into an error.
- **Sep 15–16: `core/cert,pki: reject wrong-sized signatures before the sign scheme panics`** — `cert.Verify` and `cert.AddSignature`, and the descriptor upload verifiers, passed an attacker-controlled signature payload straight to the sign scheme. The hybrid "Ed25519 Sphincs+" scheme's Verify panics on a wrong-sized signature. Length-check the payload against the scheme's `SignatureSize`, and reject a nil descriptor signature, before calling Verify.
- **Sep 15: `authority/voting: pin the wire-KEM ceiling test to Ed25519 so it runs on Windows`** — Ed25519 Sphincs+ is not built on Windows, so the McEliece and MLKEM cases both collapsed to the flat default and the scaling assertion failed.
- **Sep 15: `authority/voting: close temp db and log handles so Windows cleanup can remove them`** — on Windows an open bbolt state.db or file-backed log keeps a lock, so `t.TempDir`'s `RemoveAll` cleanup cannot delete the file and the new authority tests fail.
- **Sep 15: `authority/voting: default to Ed25519 on Windows (no cgo Sphincs+)`** — hpqc builds Sphincs+ only with cgo, which it does not do on Windows, so `ByName("Ed25519 Sphincs+")` is nil there.

**The cluster as a whole** is **Katzenpost hardening its own dirauth** — the panics-on-attacker-input class, the consensus-stall-on-missing-reveal class, the wire-format ceiling class, the persistent-connection-class bugs are all closed in this window. The hpqc adoption work is the input to many of those: a panic on a malformed signature used to take down a directory authority, and now it doesn't. **Namenlos public mixnet** is still listed as "coming next" on katzenpost.network; the project's public letter to the European Parliament ahead of Chat Control remains front-paged.

### I2P: Tim C Hardening Sweep + i2psnark Network-Etiquette Hygiene

I2P shipped **~15 commits Sep 13–17** split between **I2P router core hardening (Tim C reports)** and **i2psnark tracker/announce hygiene**.

**Tim C hardening sweep (Sep 16, all reported by Tim C)**:

- **Sep 16: `crypto: make EdDSA sig comparison constant time`** — Defensive against side-channel timing attacks on signature comparison. I2P has historically used non-constant-time memcmp for this; the fix is the textbook constant-time comparison.
- **Sep 16: `crypto: make AES operation constant time` in deprecated/unused method** — Defense in depth: even though the method is deprecated/unused, making it constant-time means a future caller can't accidentally re-introduce a side-channel.
- **Sep 16: `Tunnels: Don't process dup fragments`** — A DoS-relevant fix: an attacker could supply duplicate fragment identifiers to cause redundant processing. (Reported by Tim C.)
- **Sep 16: `Tunnels: Limit size of fragment reassembly map`** — Bound the unbounded-growth class of bug. The fragment reassembly map could grow without limit if an attacker supplies many distinct fragments that never complete; this caps the map size to prevent OOM. (Reported by Tim C; fix adapted from Tim C.)
- **Sep 16: `i2pcontrol: Log and delay on auth failure`** — Anti-bruteforce: log failed authentication attempts and add a delay between them. Reported by Tim C.

**i2psnark network-etiquette hardening (Sep 13–17)**:

- **Sep 17: `streaming: Mark window size option methods unused`** — Cleanup: mark the unused methods.
- **Sep 15: `i2psnark: Limit max reported peers to protect against tracker bugs`** — Cap the number of peers reported to a tracker in a single announce, in case a tracker has a parsing bug that overflows on large lists.
- **Sep 15: `i2psnark: Extend keepalive interval from 30 to 60s, only send on inactivity`** — Network etiquette: don't send a keepalive every 30s if the connection is active; send it every 60s only when there's been inactivity. Reduces idle-bandwidth.
- **Sep 14: `Router: Update cert and re-enable new reseed`** — Update the bundled router certificate and re-enable the new reseed mechanism (i.e. the trusted reseed hosts that I2P clients use to bootstrap their router info from).
- **Sep 13: `i2psnark: Add all trackers to magnet links`** — Generate magnet links with the full tracker list, not just the primary tracker.
- **Sep 13: `i2psnark: Set next announce based on last response time, not request time`** — Tracker etiquette: schedule the next announce based on when the last response arrived, not when the last request was sent. Failures get retried faster because the response timing reflects when the tracker was actually reachable.
