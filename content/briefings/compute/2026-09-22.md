## Macro Thread — Bittensor V461 Basket Trading: Root Validators Get Active Rebalancing, `swap_basket` Gated Off

Bittensor's V441 (Root Reborn, July 2026) had already moved root-yield deployment away from the old `set_root_weights` vector and onto validator-driven alpha allocation. **V461 (Basket Trading, Sep 2026)** closes the second half of that transition by giving root validators an explicit `swap_basket` extrinsic to actively rebalance the holdings of their root-managed fund — and removes the last vestige of the `set_root_weights` machinery (call 146, the `RootWeightSettingEnabled` gate, the `RootWeightsCap` map, the `validator_root_weights` read API, and the `weights` field of `BasketSummary`). The Sep 22 reading is the spec itself, the testnet SDK, and what is/isn't on mainnet.

| V461 feature | Status (Sep 22) | What it changes |
|---|---|---|
| `SwapBasket` extrinsic (call 150) | **Testnet only** — mainnet still on V441 spec_version | `SubtensorModule::swap_basket(hotkey, origin_netuid, destination_netuid, amount, min_amount_out)` |
| `BasketTrading` proxy type | Live from upgrade block (testnet) | New proxy for governance-managed rebalancing |
| `basket_trading_status` read | Live (testnet) | Returns `enabled`, `frozen`, `budget_tao`, `remaining_tao`, `used_tao`, `refill_per_block_tao`, `refill_blocks` |
| `BasketTradingEnabled` toggle | **Defaults OFF at upgrade; fails with `BasketTradingDisabled`** until governance flips it on | Gates the entire `swap_basket` surface until validators + holders are ready |
| Migration of stored root vectors | Auto-cleared on upgrade | "no fund's holdings change" — only the deployment mechanism, not composition |
| Removal of `set_root_weights` (call 146) | Removed on testnet | "a fund could also be steered through the dividend stream" — that design is gone |
| Netuid 0 = TAO cash slot | Spec | Validator can move into/out of TAO cash the same way as any other holding |
| `min_amount_out` floor (last arg) | Spec — caller protection | `swap_basket` fails `BasketMinOutNotMet` if the buy leg credits less than the floor (in destination alpha, TAO if dest = netuid 0); `0` = no floor |
| Testnet SDK | `pip install "bittensor==11.3.0rc47"` + `-n test` | `11.3.0rc46` shipped with a broken `btcli` (no `root swap`, crash at exit); `11.3.0rc47` fixes both |

What the table tells you about the design:

1. **The dividend-vs-trading split is now explicit.** V461's release notes say it bluntly: "Until now a fund could also be steered through the dividend stream: a `set_root_weights` vector decided where new yield was deployed. That design is removed — dividends now always accumulate in place on the subnet they were earned on." This is the structural complement to V441's "we hand that stream to the people best positioned to manage it" line: V441 stopped forcing every dollar of root yield to be sold the block it arrived; V461 gives the validator the *active* lever to deploy existing holdings, with a MEV-shielded mainnet wrapper and a testnet-unshielded trial.
2. **Netuid 0 is now a first-class holding.** "Netuid 0 on either side is the fund's TAO cash slot, so a validator can also move into or out of cash." This is the missing piece that makes a root-managed fund function like an actual index fund — without cash, you can only rebalance within alpha holdings.
3. **Mainnet is gated behind governance.** `BasketTradingEnabled` defaults OFF, and `swap_basket` "fails with `BasketTradingDisabled` until governance flips `BasketTradingEnabled` on." This is a deliberately conservative launch — V461 is the SDK and the spec; mainnet activation is the next on-chain vote. The Sep 22 reading is that the upgrade is ready to be flipped on by token holders; it is not yet on mainnet.
4. **The SDK surface is small and intentional.** `btcli root swap --from --to --amount [--max-slippage] [--hotkey] [--proxy-for]` quotes both legs, sets the floor to the quote less `--max-slippage` percent (default 1%), and shows "origin and destination holdings, the expected and minimum output, and how much of the bucket is left before you sign." The "bucket" reference is the `budget_tao` mechanism that prevents a single validator from draining the fund via rapid swaps; on mainnet, swaps are MEV-shielded by default (`--no-mev-shield` is the testnet-only opt-out because the shield's validator-side reveal runs on mainnet only).
5. **No validator's income moves.** "Weights only ever decided how an earned dividend was deployed, never what a validator earned, so no validator's income moves." This is the key reassurance — the migration of stored root vectors is purely operational, not economic.
6. **The `Basket trading` operator walkthrough, the `Basket trading for governance` guide (enable, freeze, tune, rogue-key playbook), and the `Basket trading for stakers` guide ("nothing to do, and how to watch") are the three reference documents.** The governance guide is the one that matters for the next on-chain vote: it lays out the procedure to flip `BasketTradingEnabled` on, freeze it, tune the budget, and handle the rogue-key scenario (a validator that tries to drain the fund).

### Why V461 Matters for the Wider Subnet Economy

Three observations:

1. **The basket is the first primitive that lets a TAO holder delegate capital-allocation decisions to a validator they trust, without giving that validator custody.** A TAO holder stakes to root, a validator is chosen, the validator runs `swap_basket`, and the resulting alpha composition is on-chain. The TAO holder can withdraw their stake at any time and exit at the current composition. This is structurally different from staking to a subnet directly (which exposes the holder to that subnet's alpha price and that subnet's emission schedule) and from holding TAO (which gets the base 6.3%/yr yield but no upside on specific subnets).
2. **The MEV shield on mainnet is the production-grade primitive.** "On mainnet leave that flag off; swaps shield by default." The shield uses a validator-side reveal to prevent front-running; the testnet-only opt-out exists because the reveal protocol runs on mainnet validators, not testnet ones. This is the same MEV-shielded pattern that Bittensor used for `commit_reveal_vote` weights; V461 is the first time it's applied to a value-moving extrinsic.
3. **The Sep 28-29 Exploit Summit speaker list (from the Sep 15 weekly) gains a new relevance with V461.** Jacob Steeves (Affine CEO) and Jon Durbin (Chutes/SN64) are both on the speaker list; V461's basket-trading primitive is a natural reference for their talks on confidential-subnet infrastructure (Steeves) and production subnet inference (Durbin). The Sep 22 reading is that the Exploit Summit will land a week after V461 hits testnet, which means the room will have a fresh spec to argue about.

5. **The model-args for GLM-5.3-Flash are now public:** `--max-model-len 400000 --kv-cache-dtype fp8 --enable-auto-tool-choice --tool-call-parser glm47 --reasoning-parser glm45 --trust-remote-code`. The 400K context window is the largest of any PoC model on Gonka; the fp8 KV cache is the memory-optimization that lets the model fit on H100/H200 80GB. The `glm47` tool-call-parser and `glm45` reasoning-parser are the upstream Z.ai conventions; Gonka doesn't fork them, it adopts them.

### NEUS x Phala: Trust Harness as the Production Reference

The Sep 22 reading includes the **NEUS x Phala case study** (phala.com/posts/neusphalabuildagenttrustlayer) — a production deployment of an evidence layer on top of Phala's TEE substrate. The architecture has three layers:

1. **Sealed inference (Phala layer).** "Model calls execute inside Trusted Execution Environments: NVIDIA H100 and H200 GPU enclaves for model execution, Intel TDX confidential VMs for orchestration and pre/post-processing. Prompts, keys, tools, and agent memory are encrypted in memory and decrypted only inside the enclave's protected boundary. The host OS, the cloud provider, and the model operator cannot read the plaintext."
2. **Attested runtime (Phala layer).** "Before data enters the enclave, Phala's attestation system generates a hardware-backed proof that the runtime environment is genuine, unmodified, and running the expected code. The attestation document binds the enclave's measurement to a specific hardware platform and software hash. Any third party can verify, without trusting Phala or the cloud provider, that inference ran in the exact environment claimed, on the exact code expected, at the time the request was processed."
3. **Governed action (NEUS layer).** "NEUS sits on top of the inference pipeline and governs who can call it, under what authority, and within what scope. When a team deploys an agent, NEUS issues a trust receipt: a cryptographically signed record that binds the agent's identity to a delegated authority, a scope of permitted actions, and a set of constraints."

The combined artifact: "Two halves of one proof: the data was never exposed, and the action was authorized." This is the production case study that confirms the Phala pitch — confidential inference + on-chain receipts + third-party verification — works end-to-end with real customers (NEUS, OpenRouter, Z.AI, OPPO, Venice AI, NEAR AI, Uniswap per the case study).
