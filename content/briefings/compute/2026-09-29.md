| Compatibility requirement | — | Intel TDX-capable GCP zones OR Nitro Enclave-capable EC2 instances |

What the table tells you about the v0.6.0 release:

1. **dstack-cloud is the developer-facing product line that complements dstackOS** (the bare-metal runtime) and the dstack SDK (the lib for embedding in apps). Before v0.6.0, all three lived in the same repo and a developer who wanted to launch a CVM had to clone dstackOS, compile it, write a custom launch script, and run their own KMS. v0.6.0 ships the CLI + KMS + governance as separate binaries that install from a package manager.
2. **GCP TDX is the first hyperscaler-specific TDX deployment.** AWS has had Nitro Enclaves for years (since 2019 for EC2) but Nitro's TDX-equivalent (Nitro Enclave's NSM) is not Intel TDX — it's a custom Nitro Security Module with a different attestation surface. GCP Confidential VMs (released 2024) are the first hyperscaler Intel TDX deployment. Adding GCP TDX to dstack-cloud means a developer can now launch a dstack CVM on GCP without owning any bare-metal hardware.
3. **The on-chain governance surface (DstackKms + DstackApp + Multisig + Timelock) is the production-grade primitive.** Before v0.6.0, KMS key release was either (a) policy-gated by an off-chain admin (single point of failure), or (b) policy-gated by a dstackOS config file (mutable by the host). v0.6.0 wires both KMS key release AND app deployment to on-chain contracts; the contracts are owned by a Multisig+Timelock; key release requires both attestation AND on-chain policy check.
4. **RA-TLS for KMS↔workload is the security primitive that makes production key release safe.** Without RA-TLS, the workload cannot prove to the KMS that it is the workload that was authorized (vs a hostile workload that copied the key). RA-TLS binds the TLS cert to the workload's attestation quote, so the KMS only releases keys to the workload that was deployed with the right image + compose hash.
5. **VSOCK proxy for Nitro is the networking primitive** — Nitro Enclaves have no direct network access; the only networking primitive is VSOCK (host↔enclave). The dstack-cloud CLI's VSOCK proxy allows the enclave to make outbound HTTPS via the host's network, with the enclave's RA-TLS handshake preserved.
6. **The KMS bootstrap (Onboard → Finish) flow handles the cold-start problem.** A new dstack deployment has no KMS yet (because there's no CVM to host one yet, and you can't bootstrap a KMS-on-a-CVM without a CVM). The Onboard → Finish flow uses a temporary file-based KMS for the bootstrap, then migrates to a standalone KMS-on-a-CVM after the first attestation is verified. This is the same pattern Phala used internally for its own Phala Cloud launch.

### Phala dstack Cloud Pre-Production Caveats

Three caveats from the release notes page that are worth flagging:

1. **Compatibility requirement: Intel TDX-capable GCP zones OR Nitro Enclave-capable EC2 instances.** Not all GCP zones have TDX; the TDX-capable zones are the `n2d-standard-*-td` and `c3-standard-*-td` families in select regions. Not all EC2 instance types support Nitro Enclaves; the supported families are `c5`, `c6i`, `m5`, `m6i`, `r5`, `r6i` with `nitro-enclaves-enabled` AMI.
2. **The KMS bootstrap flow requires a working GCP or AWS account with quota for TDX/Nitro.** A solo developer without a cloud account can run dstack locally (Local Key Provider mode) but cannot test the production-grade KMS surface without cloud resources.
3. **The on-chain governance (DstackKms + DstackApp + Multisig + Timelock) requires a deployed chain to anchor to.** The default is Phala's own Phala Network; cross-chain anchoring (to Ethereum mainnet, Base, etc.) is roadmap, not shipped. This is the canonical "confidential compute requires a chain anchor" constraint — without an anchor, the on-chain policy check cannot happen.

These caveats don't change the structural story (v0.6.0 is the first developer-usable confidential compute product line) but they are the answer to "why is this still pre-production at the enterprise scale" — the friction is in the cloud account setup, not in the dstack code.
