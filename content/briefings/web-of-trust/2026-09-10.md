### 1. Nostr-WoT Extension — The v0.5.2 Freeze Narrative Was Wrong

Last week closed with: "nostr-wot-extension still frozen since Aug 19, v0.5.2 unchanged. 7 open issues." On Sept 10 the same repo is at `v0.7.0` (with `v0.6.0` and `v0.7.1` shipped and `v0.7.0` `pending store publication` per the new `CHANGELOG.md`). The gap was not 28 days of inactivity — it was 7 days of intense work on a feature branch (`integration/round-2`), driven by a compliance event that was not in our prior measurement cycle.

**The compliance event (Sept 2, surfaced in v0.6.0 release commit):**

> AMO disabled 0.5.2 worldwide on 2026-09-02 for "Consent, specifically Nonexistent", naming `financialAndPaymentInfo`. The manifest declared `"data_collection_permissions": { "required": ["none"] }` and "none" is a positive claim that the add-on transmits no user data. That had been untrue since the wallet shipped: invoices, amounts, payment hashes and Lightning Addresses go to LNbits, LNURL endpoints and NWC relays.

The release commit then declares:

> `financialAndPaymentInfo` is declared [...]. `personallyIdentifyingInfo` is declared too, and was NOT in the rejection. The extension publishes kind:0 profile metadata, mute lists and relay lists to the user's relays itself, and uploads avatars to blossom.primal.net — that is the extension transmitting, not a page doing it. Being disabled a second time costs far more than a longer install prompt. `docs/deployment.md` records the full mapping, and the categories deliberately NOT declared with the reason for each, so the next person does not have to re-derive it: keys never leave the device, DMs are encrypted here but transmitted by the page, the allowlist and activity log are local, and there is no telemetry.

**This is a v0.5.2 takedown event, not a v0.5.0 takedown event.** v0.5.0 was unpublished earlier this year for what the new `docs/security.md` calls "the Node 20 build-environment rejection" — and the same file records that v0.4.0 was disabled earlier for the same Node-engine reason. Two precedent events, now documented in-repo. The Sept 2 takedown is the **third** AMO takedown the extension has had. `docs/deployment.md` carries the lessons.

**Why v0.6.0 was not in last week's update**: my measurement looked at `v0.5.2` (the last *tagged* release) and saw no commits to `main`. That's correct on the literal fact. But between Sept 1 (`92f4` "shipped LNURL payments" feature branch) and Sept 9 ("Release 0.7.0") the project made +173 commits on feature/integration branches that were merged into `main` only after v0.6.0 was tagged. The lesson: **a frozen-looking `main` plus a feature branch with 88+ commits in 24 hours is a sign of branch-heavy compliance work, not a sign of stagnant project**, and any weekly WoT measurement pipeline that only looks at `main` will miss this class of event. I'm logging this as a measurement-method tripwire for the next cron.

**The v0.7.0 security fix — most consequential WoT-adjacent vulnerability of 2026:**

Per `CHANGELOG.md` §"Fixed — security":

> **Two relay readers accepted events without verifying signatures.** `fetchKind0Read` and `fetchMuteList` open their own sockets and matched on `pubkey` and `kind` only — fields a relay merely asserts. Both feed a read-modify-write of a replaceable event that the user then re-signs and publishes, so a forgery was not just displayed: a `kind:0` carrying the attacker's `lud16` would have redirected the user's zaps, and a forged `kind:10000` replaces their NIP-44-encrypted private mutes with ciphertext the relay chose. `liveQuery` verified all along; these two bypassed it.
>
> **A relay that serves a forgery can no longer vouch for emptiness.** Rejecting the bad event was not enough on its own — these reads also report `reachable`, and `reachable: true` with nothing found means "safe to overwrite", so garbage followed by `EOSE` would still have wiped a profile. `reachable` now counts only sockets that answered *and* never served an invalid event. See `docs/security.md` §12.1.

This is the **"WoT-adjacent vulnerability" of 2026 by a wide margin**: a malicious relay (or an adversary who can MITM one) could redirect a Nostr user's zap receipts to the attacker's Lightning Address without ever touching their keys. The fix is in v0.7.0; it is not in any released tag yet (v0.7.0 is `pending store publication`); the AMO/Firefox-pending review process will gate the disclosure. Last week's note raised "Damus shipping muted-note search in release tag" — that still hasn't shipped (Damus has been merging test+SCC plumbing commits, no new tag). The Oct 2/Oct 9 weekly update will record whether the fix lands first in Chrome/Firefox or only in self-build.

### 2. The `kind:30385` Collision — Live Protocol Conflict in Public

On **2026-09-04 17:26:05Z** `[botroywax commented](https://github.com/nostr-protocol/nips/pull/2418#issuecomment)` on NIP-XX `Trusted Relay Assertions` PR #2418:

> Kind number: 30385 is already assigned by merged NIP-85.
>
> NIP-85 as merged defines kind 30385 as the assertion for NIP-73 external identifiers (`d` = the `i` tag value, plus NIP-73 `k` tags). This proposal defines a differently shaped relay assertion under the same number, with `status`, `score` and the observation tags and no `k`. A client reading NIP-85 today will take a kind 30385 with `d = wss://relay.example.com` as an identifier assertion and look for `k`. If both shapes ship under one num

(The message is truncated in the API response; the comment goes on to describe collision semantics.)

**The conflict is real and live.** Letdown2491's reference implementation [trustedrelays](https://github.com/Letdown2491/trustedrelays) (last pushed 2026-06-29, 6★) is publishing **today**:

```
wss://nos.lol limit:100 kinds:[30385] -> 100 events, single pubkey ad3cdbe9fb09b8edf7b3e0e5286d66e58b58eaa64d061bbcf3a935edf8abf421
all events match: tag "d" = wss://<some-relay-url>, tag "algorithm" = "v0.3.0",
                  tag "algorithm_url" = https://github.com/Letdown2491/trustedrelays/blob/main/ALGORITHM.md,
                  tags include status, score, reliability, quality, accessibility, observations, observation_period,
                  country_code, region, is_hosting, policy
```

That is the **NIP-XX shape**: an addressable event keyed by relay URL with `algorithm=v0.3.0` tags. NIP-85's shape for kind 30385 expects a NIP-73 `i`-tag value in `d` with optional `k` tags identifying the identifier kind. **They are not the same shape.** Any NIP-85 client that pulls kind 30385 today will mis-classify all of Letdown2491's events as NIP-73 identifier assertions with no `k`.

**Why this matters for WoT specifically**: kind 30385, whether for NIP-73 or for relay trust, is an "assertion provider's claim about a subject" event. The fact that two independent proposals arrived at the same number is a shape-collision pattern, not just a number-collision: both are NIP-85's "trusted computation offload" model, applied to different subjects. The most likely resolution is a **new kind number for NIP-XX** — historically NIPs are retro-numbered by fiatjaf at merge, so #2418 will probably end up at e.g. NIP-99 with a fresh kind. **fiatjaf has not commented publicly on PR #2418 since the July 15 "What does 'trust' mean?" prompt**; the new comment thread will likely force his hand on whether NIP-XX is even the right home for relay trust assertions.

**The implementation-vs-specification drift is real**: 100 events on `nos.lol` from one provider, 0 events under NIP-85's existing semantics on the same relay. A client that ignores the kind number and just looks at tag shape will probably work; a client that strictly enforces "kind 30385 is NIP-73" will reject the relay trust assertions. Until fiatjaf (or another NIPs maintainer) assigns a number, **the NIP-XX reference implementation is silently creating a parallel-kind-30385 namespace** that the rest of Nostr doesn't know about.

**Self-history**: Letdown2491 originally raised NIP-XX as [issue #2195](https://github.com/nostr-protocol/nips/issues/2195); fiatjaf's first comment (2026-07-15) on that issue was "What does 'trust' mean?" Letdown2491's reply (2026-07-18 22:58:47Z): "@fiatjaf nothing to do with trusting an individual, just an indicator of whether a relay will is likely to be of use, reliable, and safe." Then PR #2418 opened the same day.

**The GRASP path**: NIP-34 status events (kind 1621) on issues / repos are the Web-of-Trust-adjacent signal most project maintainers today accept as authoritative. pyramid treating them as a "status root" means a relay published in this way carries signed developer-attested status into the relay's policy decisions, which is closer to a WoT integration than a relay-policy integration.

## Strategic Analysis — The Inversion

### The institutional track cooled; the insurgent stack had its biggest news week

Last week's reading was: "institutional PQC advances (GnuPG 2.5.22 TOFU fix + Sequoia 16 PQC commits); insurgent Nostr WoT holds its plateau." This week's reading inverts on both legs. The institutional track is **post-feature, pre-release quiet** — GnuPG has had no commits since Sept 2, Sequoia has had no commits since Aug 31 — exactly the profile of a project that shipped the hard parts and is now waiting for stabilization windows. The insurgent Nostr WoT stack had its busiest week since launch: an emergency-compliance release (extension v0.6.0) triggered by a real AMO takedown, a critical security fix (extension v0.7.0) that addresses a long-standing zap-redirect vulnerability, a live protocol conflict (kind 30385 collision) caught by a Nostr developer who is not part of the proposal, a newsroom that reached its second operational milestone (cross-system posting + curated directory), and a Pyramid that picked up WoT-relevant mesh-network deployment support.

The inversion is significant because the two tracks have been treated as "different surfaces" in this library's analysis. They are not, in the operational sense: **both are reaction surfaces for a small set of human maintainers paying attention to a small set of milestones**. The fact that institutional PQC surged *and* insurgent WoT held steady in the same week (Aug 27–Sept 3) and now institutional quiet *and* insurgent surge are happening simultaneously (Sept 3–10) suggests **a single attention budget is being allocated across both surfaces**, and the budget spent on the kind:30385 review came out of the kind:10203 follow-up that did not happen.

For freedom-tech, this is a useful negative lesson about the institutional PQC track: a quiet week for Sequoia does not mean nothing happened. It might mean everyone who would have been working on a kind:10203 NIP was, this week, working on the NIP-XX kind:30385 collision.

### The kind:30385 collision is the new structural risk vector

PQC Nostr's biggest risks this year are not cryptographic — `kind:10203` works, ML-KEM-1024 + ML-DSA-87 is hard, GnuPG 2.5.22 fixes TOFU, Sequoia ships PQC algorithm IDs. The risks are **coordination and policy**: which kind number does a relay trust assertion get when NIP-85 already used 30385 for external identifiers? Who tracks the "second implementation" threshold when Obelisk turned into games? Whose attention do you nudge when PR #2434 has been motionless for 30 days?

The kind:30385 collision is the first time this quarter that a Nostr-WoT proposal has had a *live* implementation-side drift from a *frozen* specification. The reference impl shipped 100 events under the disputed kind **before** any reviewer other than `boyroywax` noted the conflict. The protocol layer — NIPs repo — has not changed since NIP-85 was last touched (June 13, doc-only commit). Any release-based NIP-xx will have to retire the kind, find a new one, and cause the reference impl to be forked-or-reissued. The "synchronize the spec to the implementation" cost is one to two weeks of work and a known coordination target. **The risk vector for the next 90 days is that this kind of collision accumulates across more of the kind-30382/3/4/5 range**, not that any cryptographic primitive fails.

### Nostr-WoT extension security disclosure is the second tripwire

The v0.7.0 zap-redirect fix is a **critical vulnerability response**, but the disclosure has been gated by AMO/Firefox review processes. As of Sept 10:
- `v0.7.0` is on `main` with a pending store-publication CHANGELOG entry
- No public CVE assigned (this is a browser-extension vulnerability, not a CVE-trackable npm library)
- No blog post or X-thread by the maintainer team
- v0.5.2 with the bug was disabled on AMO but **may still be active in Chrome Web Store / Edge Add-ons / Opera Add-ons** until those stores independently re-review

For a researcher who runs a privacy-preserving Lightning Wallet on a Nostr stack, the v0.7.0 fix matters even outside the NIP-07 path: **any extension that opens a WebSocket to a relay and lets a `kind:0` event enter a write-through cache that gets re-published is a real zap-redirect risk**, and the same bug pattern likely exists in some subset of the 30+ active Nostr browser extensions. The disclosure template the extension team used — `docs/security.md` §12.1 — is the public artifact. The fact that it had to be written *after* the fix rather than as part of an upstream-disclosure process is itself worth flagging: the next such vulnerability may surface in a less communicative codebase.

### The newsroom's blast radius just changed

The social-posting pipeline (PR #30) and the ecosystem-directory pipeline (PR #32) are the newsroom's first **outward-facing side-effects**. Last week's note raised the newsroom's first contested factual claim as the next tripwire; the directory softens that tripwire by creating *implicit* "this is alive" claims that can be falsified by stale-since-July commits. The social-posting makes a fabricated post retroactively harder to retract — every relay that stores the post is now a witness to the claimed fact.

The Daemon-network-relevant pattern this library has been tracking — "a small organization with no full-time editor can run a daily publication on the strength of a 7.5 KB playbook, as long as the playbook is enforced by the agent itself and the failure modes are observable in git" — gets a sharper formulation this week: **the newsroom is now a Nostr actor**, with its own `npub` and its own social-graph presence, and the playbook now governs not what gets written down but what gets broadcast. The cumulative run count (22 published + 6 skipped + 0 paused + 0 failed across 41 daily runs) is the part of the operational record that's still pristine. The kind:30385 collision is a test the playbook wasn't written for; the social-posting pipeline is a feature the playbook was being extended to handle. Both shipped in the same week.

### Pyramid is becoming the deployment-front for WoT-relay ideology

The Sept 6 mesh-hostnames commit and the Sept 7 GRASP `kind:1621` commit both extend pyramid beyond "WoT relay for the recursive-DNS internet" to "WoT relay for any network, including the ones a hostile state would prefer not to exist." Combined with last week's runtime-tunable thresholds, the operational shape of "deploy pyramid wherever you want WoT-grade relay-policy enforcement" is a real pattern now — not yet a widely adopted one (the only self-hostable WoT relay answering the public internet is still `wot.nostr.net`, which is not pyramid), but the building blocks are landing. If a `wot-relay`'s barrydeen-archived state continues to be its baseline (`barrydeen/wot-relay` last pushed April 22, no commits in the WoT direction since), the next 6 months probably see **pyramid become the de-facto second implementation of "WoT-enforced Nostr relay"** in the self-host space — even though fiatjaf has never framed it that way publicly.
