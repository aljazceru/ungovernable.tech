### 2. NIPs Repo: Three Merges in Three Days — NIP-39 Unification + kind:10040 + kind:10021

The NIPs repo's three W40 merges represent **the most active weekly merge cadence of the year** — and each merge closes a structural gap in the Nostr protocol surface.

**[PR #2483](https://github.com/nostr-protocol/nips/pull/2483) (TheSeydiCharyyev, merged Sep 25 by vitorpamplona) — Four missing kinds added to the Event Kinds table**

The PR body is precise:

> Four kinds are defined in their NIPs but were missing from the Event Kinds table.
>
> - `10040` — NIP-85, section "Declaring Trusted Service Providers": "Kind `10040` lists the user's preferred source for each result." The table already lists NIP-85 kinds 30382, 30383 and 30384.
> - `21059` — NIP-59, section "Ephemeral Gift Wrap Event Kind". The table already lists kind 1059, which this one mirrors with ephemeral semantics.
> - `33534` — NIP-43, section "Role Definitions": "Relays MAY publish a `kind 33534` event which defines a role". The table already lists NIP-43 kinds 8000, 8001, 13534, 28934, 28935 and 28936.
> - `38000` — NIP-87 names it in its first line: "This NIP describes `kind:38173`, `kind:38172` and `kind:38000`". The other two are already in the table.

**The freedom-tech takeaway** is in the 10040 row specifically: **without 10040 in the table, a reader has to know NIP-85 exists, find the "Trusted Service Providers" section, and know that 10040 is a preference-list row** — most clients can't subscribe to "all kinds with tag X" without enumerating, and the kinds table is the canonical enumeration. **With 10040 in the table, the kind is a first-class addressable entry** — clients subscribing to kind:10040 receive the user's choices for "who computes my trust scores / who is my trusted relay oracle" without the NIP-85 deep-link. **The W40 surface for trust-source preferences is now structurally equivalent to the surface for trust-source assertions** (kinds 30382 / 30383 / 30384, all in the table for >1y).

**[PR #2417](https://github.com/nostr-protocol/nips/pull/2417) (fiatjaf, merged Sep 27 by vitorpamplona) — Favorite follow sets → kind:10021**

> fixes [#2413 (comment)](https://github.com/nostr-protocol/nips/pull/2413#issuecomment-4987010296)

The PR moves favorite follow sets to **kind:10021** because the previous kind **"is already being used"** for something different. **This is a clarification of NIP-51** — favorite follow sets and favorite relay sets share NIP-51's "lists" surface, but they need distinct kinds to avoid clients subscribing to one and receiving the other. **The W40 surface for favorite follow sets is now first-class addressable.**

**[PR #2486](https://github.com/nostr-protocol/nips/pull/2486) (alexgleason, merged Sep 27 by fiatjaf) — NIP-39 unification**

The PR is **the first published measurement of NIP-39 proof-validity in the wild**. From the PR body:

> ### One verification text
>
> Each claim type currently specifies a different proof text (github has no quotes around the npub, twitter uses an entirely different sentence, mastodon and telegram use quotes). This replaces them with a single string for every claim type:
>
> ```
> Verifying that I control the following Nostr public key: <npub encoded public key>
> ```
>
> It also says verifiers SHOULD accept any proof by `<identity>` that contains the user's npub, so existing proofs keep working.
>
> #### Why the lenient verification rule
>
> I surveyed kind 10011 across 11 major relays (5,859 authors, 756 with `i` tags) and fetched every github/twitter/mastodon/telegram proof. Of the 611 proofs, only **27** contain the exact spec text for their platform. Of the ones that could be fetched, most contain the correct npub with other wording: 101 are a bare npub, and about 77 use Divine's own template. Requiring the exact string would invalidate almost every proof in the wild; requiring the npub keeps about 290 of them valid.

**The freedom-tech takeaway**: **97% of in-the-wild NIP-39 proofs would fail a strict-text check** (27 of 611 contained the exact spec text). The lenient rule preserves real-world interop for ~290 proofs (those with the npub) while a single canonical text prevents future drift. **Plus, alexgleason's survey surfaces 271 bluesky claims and 70 discord claims already in the wild without spec support — the W40 PR retroactively legitimizes ~340 in-flight claims** that previously had no spec backing.

**The combined W40 NIPs surface is**:

- NIP-39 unified verification text + bluesky + discord (PR #2486)
- NIP-51 favorite follow sets on kind:10021 (PR #2417)
- NIP-85 / NIP-43 / NIP-59 / NIP-87 kinds enumerated in the table (PR #2483)

**Four NIPs touched, three merges, zero breaking changes**. The repo is operating in its "polish and legitimize" mode rather than its "add new primitives" mode — the W40 surface is **structurally tight rather than structurally novel**.
