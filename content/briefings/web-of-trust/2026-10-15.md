## The Week in Detail

### Amethyst v1.18.0 (Oct 11 19:27 UTC) — desktop + Web of Trust production surface

[The release](https://github.com/vitorpamplona/amethyst/releases/tag/v1.18.0) is titled *"Amethyst Desktop, Web of Trust, etc"* and ships 328 commits since v1.17.0. The headline is **the first desktop build of Amethyst, with the same shared interface that ships on Android** — custom feeds, wide-window decks, opt-in locks, encrypted media, and Blossom uploads. The release body summarizes the WoT-bearing change: *Provider scores from NIP-85, trusted assertions, are indexed locally for requests, notifications and badges, with user-selected providers and thresholds.* The trust-bearing surface is built on top of the user's own kind 10040 list (the trust-provider relay list) — the same list the [Aug 16 W33 Sunday update](/briefings/identity/2026-08-16/) noted as the operational location for trust-provider relays.

The WoT-relevant PRs in the v1.18.0 window:

- **PR #4329 (Oct 6 14:04 UTC, merged in v1.18.0)** "refactor: share profile, settings, Messages, Notifications, Calendars and Blossom screens" — moves 14 more screen groups from `amethyst/` into `commonsUI/commonMain`, so 224 of 252 screens are now shared between Android and Desktop. The refactor unlocks the desktop build by ensuring the same UI renders on both platforms; it does not change the WoT surface directly, but it makes the kind:10040 + kind:30382-30385 surface ship-able in both Desktop and Android from the same code.
- **PR #4335 (in v1.18.0 window)** "quartz: complete hint providers and NIP-50 indexing across event kinds; strict relay-hint parsing; named tag accessors" — the NIP-50 (search) and relay-hint completion that the trust-consumer needs to find and rank kind 30382-30385 events.
- **PR #4437 (Oct 12 16:21:48 UTC, "fix(tor): count the relays in the user's kind 10040 as their own")** — the operational fix that makes the NIP-85 trust-provider surface usable under Tor. The PR body: *The relays named in the user's own kind 10040 (NIP-85 trust providers) were not part of `TrustedRelayListsState`, so `TorRelayEvaluation` classified them as new relays. With default privacy settings (Tor on, new relays via Tor, trusted relays clearnet) the whole Web of Trust download — tens of MB from e.g. `scores.brainstorm.world` — went through Tor. They now count as the user's relays, like the other lists the user writes: clearnet by default, Tor when "trusted relays via Tor" is on.* The change introduces `TrustProviderListState.liveRelays` which exposes the relay set of the live list (public and decrypted private rows, or its backup), and `TrustedRelayListsState` merges it in. The side effects are listed in the PR body verbatim: *Tor routing (the intended change); NIP-42 auto-auth (`AuthCoordinator`, "my relays" toggle) — the main client now authenticates to provider relays when they ask, which tells them the user's pubkey (profile cards are already fetched from those relays, so this discloses little new); "In my relays" marks (`RelayCompose`, `AccountUserObservers`) — provider relays now show as the user's.* The PR's test plan notes that the **dedicated trust-network sync client has no auth responder** (i.e. a NIP-42 challenge from a provider relay will fail because the sync client doesn't sign AUTH events) and **isn't re-dialed when Tor settings change mid-sync** — both deferred to follow-up.

The structural argument: **before PR #4437, the kind:10040 list was a *content* list (here is where I get my trust scores) but the Tor evaluator did not know it was a *trusted* list (here is where I send my traffic directly).** After the fix, kind:10040 is in the same trust-state as kind 10002 (relay list) and kind 3 (contact list) — the relay-set that bypasses Tor. The fix is a single semantic change but it is the production-ready transition: *a user can now consume NIP-85 trust scores without paying a Tor latency penalty, and the provider relays learn the user's pubkey (which they would have learned anyway from the profile-card fetch).*

The release is also significant as the *first* Nostr-WoT-stack product to ship on a desktop platform. Damus, Iris, Coracle are mobile/web; Amethyst was Android-only; **Amethyst desktop is now the only major Nostr client with a desktop surface, and the only one with a desktop surface that consumes NIP-85 trust scores.** The implication: **the desktop-Nostr user now has a WoT-aware client** — the same trust-oracle the Android user has had since the W40 oracle release.

### Amethyst v1.19.0 (Oct 14 13:16 UTC) — Wayland, remote signing, rate-limited relay backoff

[The release](https://github.com/vitorpamplona/amethyst/releases/tag/v1.19.0) is titled *"A New Login, Remote Signers on Android, Wayland, and Marketplace Cards"* and ships 70 commits since v1.18.0. The headline WoT-bearing change is **PR #4422 (Oct 13 17:09:37 UTC, merged in v1.19.0)** "Implement per-client rate limiting with NIP-01 back-off support" — relays can now refuse `EVENT` and `REQ` commands as `rate-limited:` with an optional NIP-01 `params` element specifying milliseconds to wait before retrying, and the client pool honors the back-off without reconnecting. The server-side change is in `Geode` (Amethyst's relay implementation): a `RateLimiter` token-bucket with configurable per-minute rate and burst size; the client-side change is in `Quartz` (Amethyst's Nostr library): the client pool respects the back-off. The WoT angle: **a trust-provider relay that is being hammered by a popular client's WoT feed can now push back with a `rate-limited:` and the client will back off, rather than disconnecting and reconnecting** — which means the user's NIP-85 feed survives a rate-limit storm that would previously have caused the WoT consumer to thrash.

Other v1.19.0 changes that matter for the trust surface:
- **Native Wayland support** — the desktop user no longer has to fall back to XWayland, which means the desktop WoT consumer renders on Wayland-native surfaces (clipboard handling, screen-share, screenshot-via-D-Bus) that XWayland had broken.
- **Desktop video compression via system FFmpeg/ffprobe** — separate from the encrypted-media upload path; the user's WoT-decision surface (preview, decrypt, share) now works on video attachments without transcoding the whole client.
- **Linux keyring failures fix** + **repeated-keychain-prompt fix** — operational reliability for the Nostr-WoT-extension-style browser-extension auth path on Linux desktops. (Amethyst uses Android Keystore on Android and the OS keyring on Desktop; the bug was the keyring failure falling through to a re-prompt loop.)
- **NIP-46 remote signing on Android login** — the login flow now accepts a NIP-46 bunker URL (e.g. `bunker://...`) on Android, not just on Desktop. Combined with the [bunker 1.0.0](/kb/remote-signing/) stable release, **the bunker → Amethyst pair is now stable on both Android and Desktop** — a user can run a Nostr-WoT bunker on a server and log in to Amethyst on either platform with the same secret.
- **Calendar collections and RSVPs render** — orthogonal to WoT but the kind 31924 + 31925 (Date/Time-based Calendar Event + RSVP) and NIP-52 calendar lists are a content kind that the user might want to see in the WoT-decision surface (e.g. "is this person I'm following also going to the same event?").

The release is also notable for the **12-hours-before-publish cadence** — the v1.19.0 tag is 12 hours after the v1.19.0 release commit `60b29df`, which means the 70-commit window was prepared in days, not weeks. The two v1.18.0 + v1.19.0 releases in 3 days (Oct 11 + Oct 14) is the W41–W42 shipping cadence at its peak.

### Amber 6.6.9 (Oct 14 12:42 UTC) — three security advisories

[Amber 6.6.9](https://github.com/greenart7c3/Amber/releases/tag/v6.6.9) is the security-bearing release of the W42 window. The release commit is `9b6d2a5bab81740fcbd6e15f7d66bbab8c00fda2`, signed by greenart7c3 (GPG key `885822EED3A26A6D`, **expired** as of Oct 14 — the release-signing key is past its expiry; users verifying the tag should treat the signature as advisory, not authoritative).

The three GHSA advisories:

1. **[GHSA-8f7m-9g64-vrjw](https://github.com/greenart7c3/Amber/security/advisories/GHSA-8f7m-9g64-vrjw)** — *Two flaws let an app or NIP-46 client keep signing after its permission had been revoked or explicitly rejected.* **Cache race on revocation**: Amber caches permission lookups per account. A lookup that read the database just before the user revoked a permission or deleted an app could write the old result into the cache *after* the revocation had cleared it. The revoked grant then stayed in effect until the cache entry was evicted or the app restarted. An authorized app that sends requests continuously can widen this window. **"I fully trust this application" overrode an active rejection**: when an app's sign policy was set to fully trusted, an active, explicit reject rule for that app was ignored. **Patched in 6.6.9** (commit `acee824`): the permission cache drops a lookup's result if an invalidation happened while the lookup was reading; an active reject rule is checked *before* the fully-trusted sign policy; all permission writes go through the caching layer, so they clear stale entries. Operations already approved before a revocation are not cancelled retroactively. **Workaround**: restart Amber after revoking. **Reported by @mptfire.**

2. **[GHSA-g62f-m6pm-jv9p](https://github.com/greenart7c3/Amber/security/advisories/GHSA-g62f-m6pm-jv9p)** — *Copied secrets receive a system-scheduled clipboard clear after 60 seconds, including when the process is killed.* The contents remain readable during that interval; newer copied text may also be cleared.

3. **[GHSA-wv7c-hq2j-ppc5](https://github.com/greenart7c3/Amber/security/advisories/GHSA-wv7c-hq2j-ppc5)** — *Changing "require unlocked device" preserves the old wrapping key until secret migration completes; previously lost keys remain lost.*

Plus three operational fixes:
- `nostrconnect://` connections approved from the multi-request screen never got a reply; now reply on the relays from the nostrconnect:// URI.
- Multi-request screen groups by app, showing each app's name, icon and request count; "remember my choice" is per-app.
- A copied nsec, ncryptsec or seed words is cleared from the clipboard after 60s (the GHSA-g62f-m6pm-jv9p fix).

The structural implication for the WoT/NIP-46 stack: **the cache-race + reject-rule-override vulnerabilities are the kind of bugs that a bunker 1.0.0 stable user would not expect their client to have.** A bunker host running Amber as the NIP-46 client + `@nostr-wot/bunker` 1.0.0 as the responder would be subject to both: a continuous-request app on the bunker side could keep signing after revocation; a fully-trusted app could override an explicit reject. The fix in 6.6.9 closes both. **The W42 release is the trust-stack's "vulnerability-before-stable" closing — bunker 1.0.0 stable is now backed by an Amber that cannot be tricked into continuing to sign after revocation.**

The expired signing key is a separate concern: the tag's signature is no longer cryptographically fresh. Users who want to verify the Amber 6.6.9 release should pull from F-Droid or the GitHub release *without* relying on the greenart7c3 signature alone. The fix is on greenart7c3's side — re-sign with a non-expired key, or sign a new release with a rotated key.
