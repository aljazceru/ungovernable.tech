### 2. `kind:10203` Resumed Growth — Two New ML-DSA-87 Entries on Sept 23

After **23 days of zero growth** (Aug 31 → Sept 23), the count went from **24 → 26** on Sept 23. The two new entries both appeared at exactly **2026-09-23 19:40:27 UTC** — same second, different pubkeys. Both use the **NIP-PQC draft metadata shape**.

|---|---|---:|---:|
| 2026-08-10 | 17 | 17 |
| 2026-08-11 | 4 | 4 |

| 2026-08-31 | 2 | 2 |

The Sept 23 entries' tag shape (verbatim from relay):

| Tag | Value (entry 1, pubkey `e5a5c2f0...`) | Value (entry 2, pubkey `5d2f3c7f...`) |
|---|---|---|
| `alg` | `ml-kem-1024` | `ml-kem-1024` |
| `alg` | `ml-dsa-87` | `ml-dsa-87` |
| `origin` | `derived` | `derived` |
| `seed_strength` | `256` | `256` |
| `v` | `nip-pqc/v1` | `nip-pqc/v1` |
| `pop` | `ml-dsa-87` | `ml-dsa-87` |

**Signature is still 64-byte Schnorr/secp256k1** (128 hex chars). The kind:10203 entries are **identity-declaration events**, not signature events: the alg/pop/origin/seed_strength/v tags are the metadata; the signature is Nostr-standard secp256k1 because no NIP-PQC signature scheme has been adopted yet. The 64-byte sig is consistent with the Aug 10 entries' sigs (also 64 bytes), so the structure has not changed — only the alg tags have been updated to ML-DSA-87.

**Why this matters for WoT**:
- The pattern is identical to **Aug 31 → GnuPG 2.5.22 → 2 new entries** and **Sept 23 → GnuPG 2.5.23 → 2 new entries**. The library's prior reading ("the Aug 31 stair-step was a single event") has now upgraded to "**the stair-step is a stable pattern** that triggers on each GnuPG release." Two-for-two is now data; one-of-one was noise.
- The **NIP-PQC draft metadata shape** is the same shape proposed in [NIPs PR #2434](https://github.com/nostr-protocol/nips/pull/2434) "PQ Identity Keys" (frozen 44 days, sole comment = fiatjaf's nostr-tools#541 link). The vault has been tracking this PR since July; **the live relay data is the first measurable adoption signal**.
- The **24 → 26 jump** is still small in absolute terms. kind:10203 adoption is **release-driven, not network-effect-driven**. Each GnuPG release day adds 1–3 entries; each non-release day adds 0.
- The **ML-DSA-87 + ML-KEM-1024 combination** matches FIPS 203/204 (the FIPS-140-3 PQC suite). The `seed_strength=256` matches the security level of the underlying symmetric primitive. The `v=nip-pqc/v1` is a version tag. The `origin=derived` means the key was derived (likely from a 256-bit seed via BIP-32-style derivation, but for ML-DSA-87 — which is the experimental part).
- For freedom-tech, the practical implication is **there are now 26 Nostr pubkeys advertising ML-DSA-87 PQC identity declarations on a public relay**. This is the **first measurable public PQC Nostr identity corpus** — even if the signatures themselves are not yet PQC, the metadata is sufficient for clients to filter, route, or display these pubkeys as PQC-aware.

**Tripwire**: any GnuPG point release will now likely add 1–3 kind:10203 entries; the next GnuPG release day is expected to be 2.5.25 (unreleased, NEWS empty).

**The NIP-02 merge ([PR #2472](https://github.com/nostr-protocol/nips/pull/2472))** adds the petname-paths feature to NIP-02. From the merged spec:

> ### Petname scheme
>
> Clients can use follow-list petnames as local names for profiles. A petname is stored as the fourth value in a `p` tag:
>
> ```json
> ["p", "21df6d143fb96c2ec9d63726bf9edc7121df6d143fb96c2ec9d63726bf9edc71", "", "erin"]
> ```
>
> Here, the pubkey is known and can be displayed as `erin` in the current user's context. Likewise, if Erin has a petname of `charlie` assigned to one of her contacts, then Charlie can be displayed as `~/erin/charlie` in the current user's context.
>
> Petnames can also work on the other direction and resolve a pubkey from a name path. A path is resolved one component at a time: each component is looked up in the follow list of the profile resolved by the previous component.
>
> For example, if the current user's follow list gives a profile the petname `erin`, and Erin's follow list gives another profile the petname `charlie`, then `~/erin/charlie` resolves to Charlie.
>

>

### NIP-02 petnames resolve Zooko's triangle for Nostr

The NIP-02 "make petnames great again" merge is the **single most consequential Nostr protocol update of the month**. Petnames as `~/alice/bob` paths give Nostr **human-readable, decentralized, secure identifiers** — the three properties Zooko's triangle says cannot all coexist in a single namespace. The compromise is **paths instead of single names**: the resolution is secure because it depends on actual follow-list content, decentralized because no registry controls it, and human-readable because the path components are chosen by humans.

For freedom-tech, this matters because **petnames-as-paths is the trust-anchor primitive for Nostr WoT**: a user can now say "I trust the user at `~carol@names.com/erin/charlie`" and the resolution is verifiable. This is **the same conceptual move as OpenPGP fingerprint + Web of Trust**, but applied to a much more usable UX. Clients that implement the new NIP-02 feature (nak did, on Sept 17) can now surface this to users.
