*The weekly companion to [Overview - Identity & Pseudonymity](/kb/identity-and-pseudonymity/), covering September 27 – October 04, 2026 (since the [September 27 update](/briefings/identity/2026-09-27/)). Three stories dominate the week. First: **the Nostr-WoT extension shipped twice in twelve hours on October 1** — [v0.8.9](https://github.com/nostr-wot/nostr-wot-extension/releases/tag/v0.8.9) (Oct 1 10:30 UTC, "Clear zap and payment approvals") and [v0.8.10](https://github.com/nostr-wot/nostr-wot-extension/releases/tag/v0.8.10) (Oct 1, "isolates nonstandard login approvals") — both targeting the same attack surface from two different directions: v0.8.9 makes the *good path* unambiguous (zap amounts in sats, distinct signing-vs-paying review, separate detail review required for zap and wallet requests, no "approve all" batching), v0.8.10 makes the *legacy compatibility path* unambiguous (kind:22242 with `domain`+`challenge` tags is *not* NIP-98, gets a one-time approval, no saved permission inheritance). Second: **the newsroom published two explainers that have been building for months** — *NIP-09 deletion requests do not prove erasure* (Sept 30) and *strfry 1.1.3 backs out an epoll teardown guard* (Sept 29), both pointing at the gap between what a signed event can do and what a client should claim it does. Third: **Amber 6.6.6 (Sept 28 / F-Droid Oct 1) shipped a NIP-46 nostrconnect parser fix** — a connection parameter containing `=` (such as a padded secret) had been altered before Amber answered, which made NDK-based clients fail their secret check even when the signer connection otherwise looked valid; also sends feedback issues to the relays advertised by Amber's repository announcement with longer Tor timeouts. The week closes with **the [Thursday WoT update](/briefings/web-of-trust/2026-10-01/)'s kind:10203 plateau still at 26**, **NIP #2434 (PQ identity keys) now 54 days frozen**, and the wider Nostr client/release surface largely quiet at the protocol level (the Sept 30 [Nostr Compass #42](https://nostrcompass.org/en/newsletters/2026-09-30-newsletter/) is the canonical event log of the week).*

## The Week in Detail

### Nostr-WoT v0.8.9 (Oct 1 10:30 UTC) — clear zap and payment approvals

The release notes for [v0.8.9](https://github.com/nostr-wot/nostr-wot-extension/releases/tag/v0.8.9) are organized into two groups: *store release notes* (the content the AMO / Chrome Web Store reviewers will see) and *approval clarity* / *publishing automation* (the actual code changes). The store notes begin with a four-bullet list of user-facing improvements that all reduce ambiguity in the approval queue: *show zap amounts in sats, including fractional sats, alongside the recipient and comment*; *clearly distinguish signing a zap request from paying its invoice*; *show Lightning invoice amounts in individual and grouped payment approvals, and explain wallet connection access*; *missing or ambiguous amounts are never presented as zero*. The last sentence is the operational one — an amount that is missing from the underlying event is *not* displayed as "0 sats" or a blank amount; the approval screen surfaces the absence. The store notes continue with *require separate detail review for zap and wallet requests instead of including them in the queue's Approve all action* (the structural change — the bulk-approve button no longer covers the request types where ambiguity has the highest cost) and *automatically supersede older store reviews and recognize Mozilla's formatted release notes, with duplicate-submission and downgrade protection* (the publishing path closes the door on accidentally republishing an older version).

The *approval clarity* group covers the code: *reuse the verified public-profile cache for zap recipients* (zap requests show the recipient's profile picture and name from the local cache without re-fetching), *keep raw event inspection available and escape comments as text* (the user can still click into the event to see the raw JSON; comment text is escaped, not interpreted as Markdown or HTML), *keep amounts visible on single-request queue cards and on every grouped payment, without expanding a section* (no click-to-reveal), *preserve the existing signing, wallet-access and payment permission boundaries* (the change does not collapse the request-type boundaries; it strengthens them), *translate the new review copy into all six extension languages*.

The *publishing automation* group is the operations work: *verify Mozilla-rendered changelog lists by their text and item boundaries, so successful submissions are not reported as failures merely because Markdown became HTML* (the prior release cycle was a one-day lag in the AMO pipeline because the validator was matching the Markdown source rather than the rendered HTML output), *automatically supersede older store reviews when publishing a newer stable release, skip duplicate submissions and reject stale downgrades* (prevents two different `v0.8.x` releases from being live simultaneously in the AMO review queue), *remove release-specific Chrome replacement variables* (the Chrome Web Store has its own placeholder variables for release version; they were being substituted at review time and breaking build reproducibility), *add a recovery entry point for existing published releases, preserving their verified packages, source and exact-commit CI checks while using corrected publishing tooling* (a release that was already published can be re-published against a fixed publishing pipeline without losing the verified-build metadata — important because the Chrome and Firefox pipelines are different and the recovery path was non-obvious in v0.8.7's AMO disable event).

### Nostr-WoT v0.8.10 (Oct 1) — isolates nonstandard login approvals

Released on the same day as v0.8.9, [v0.8.10](https://github.com/nostr-wot/nostr-wot-extension/releases/tag/v0.8.10) is a narrower, more pointed release. The newsroom's [Oct 2 piece](https://nostr-wot.com/news/nostr-wot-0-8-10-isolates-nonstandard-login-approvals) opens: *Nostr WoT extension 0.8.10 keeps website login working for an explicitly supported client that sends a nonstandard authentication event. The compatibility path is deliberately narrow: the extension labels the request as a legacy login, displays a risk warning and requires a new one-time approval every time.* The supported legacy request uses kind:22242 with `domain` and `challenge` tags. It is not NIP-42 relay authentication, and it does not follow NIP-98.

The [comparison with v0.8.9](https://github.com/nostr-wot/nostr-wot-extension/compare/v0.8.9...v0.8.10) shows the meaningful boundary in code. Three properties:

1. *A legacy request cannot inherit a saved authentication grant.* The permission lookup returns no reusable decision for this protocol, so the approval queue must ask again.
2. *The interface offers only two outcomes: approve this request once, or deny it.* It removes persistent site approval and connected-site approval from this path. Two requests from the same origin are kept as two review items rather than grouped behind one action.
3. *Backend automation and saved relay grants cannot authorize the legacy format.* The change also preserves checks for the browser frame, verified origin, active account, and timestamp. Unknown clients, mismatched domains, duplicate tags, blank challenges, and events carrying URL or HTTP-method tags in the wrong format are rejected rather than routed through the exception.

The structural argument from the newsroom: *compatibility can otherwise become policy by accident. A user may decide to complete one login without granting the same site an open-ended way to request more legacy signatures later.* This is the same principle as Amber 6.6.5 (Sept 21) — drawing a boundary at the cryptographic/permission layer that the protocol's spec did not name. A v0.8.9 user who bulk-approved *all queued requests* for a domain that uses kind:22242 would have authorized a forever-saved grant; v0.8.10 closes that path by declaring the format's *protocol-level* property (not NIP-98, not NIP-42) rather than letting the approval queue treat it as a special case of NIP-98.

The second visible change is small but characteristic: *the release registers `https://nostrwot.com/uninstall` with the browser's uninstall URL API. Supported browsers can open that page after removal. The registered URL contains no account identifier, wallet data, or tracking parameter.* The form on the URL is the feedback form, and only a submitted form sends the text and optional email address. Browsers without the API skip registration; an API failure does not stop the extension worker. The cost is low (a few lines in the manifest); the benefit is feedback during the only moment a user is guaranteed to be looking at the extension icon — the moment they removed it.

The release does not turn kind:22242 into a Nostr standard, and it does not give that format the request-level binding of NIP-98. The practical outcome is a *contained exception*, not an endorsement. Users can recognize the warning and decide on one request. Client developers still need NIP-98 when a website login should bind a signature to an exact HTTP destination and method. The next step is for the supported legacy client to migrate to NIP-98 — the newsroom's "contact the site developers" sentence is the migration ask.

### Amber 6.6.6 (Sept 28 source / F-Droid LastRepoUpdate Oct 1) — NIP-46 nostrconnect parser

[Amber 6.6.6](https://github.com/greenart7c3/Amber/releases/tag/v6.6.6) fixes its `nostrconnect` parser: a connection parameter containing `=`, such as a padded secret, had been altered before Amber answered — that made NDK-based clients fail their secret check even when the signer connection otherwise looked valid. The release also sends feedback issues to the relays advertised by Amber's repository announcement, with a fallback to the prior relay if the announcement cannot be fetched. Longer Tor timeouts give slow relays more time to acknowledge that publication. The remaining changes improve icon and text visibility in Amber's themes.

The `nostrconnect` URI scheme is the standard NIP-46 remote-signing connection protocol. A connection URI looks like `nostrconnect://<pubkey>?relay=<wss://...>&secret=<base64>` (with `metadata=<json>` and `perms=<comma-list>` optional). The `secret` is a 32-byte random value base64url-encoded; in the standard Nostr base64url encoding, padding is *omitted*, but some NDK clients use base64 with padding (`=`-suffixed). Amber's parser was stripping the trailing `=` before passing the secret to the secret-check hash, which meant any NDK client sending a padded `secret=...=` URI would fail the verification step on the Amber side even though the client had computed the correct hash from the unpadded form. The fix: parse the parameter as a base64url with padding preserved (or, equivalently, parse as base64 and strip the `=` after parsing). Either way, the surface is narrowed to a single file in Amber's codebase — the newsroom piece estimates the diff is "tests for repeated one-time review, origin restrictions and the uninstall URL" but does not show the actual nostrconnect fix; the release notes from the GitHub release page would have to be consulted for line-level detail.

The wider context: Amber 6.6.5 (Sept 21, covered in the September 27 update) split backup-encryption keys from app-permission keys via a dedicated HKDF derivation outside the NIP-44 namespace. The two releases, two weeks apart, are both *permission-boundary fixes*: 6.6.5 fixed a key-derivation boundary that was wider than the intended scope, 6.6.6 fixed a URI-parsing boundary that was narrower than the spec. The pattern is the same: a small correctness change at the cryptographic/transport layer that closes a gap between the documented behavior and the deployed behavior. Amber's release cadence (six releases in five weeks: 6.6.1, 6.6.2, 6.6.3, 6.6.4, 6.6.5, 6.6.6) is the most active Nostr-side identity surface in this fortnight.

### NIP-09 deletion requests do not prove erasure (Sept 30 newsroom)

The [NIP-09 deletion-requests-explainer](https://nostr-wot.com/news/nip-09-deletion-requests-do-not-prove-erasure) is the structural post for the week. From the lede: *Deleting a post in a Nostr client does not send a command that can reach into every relay, cache and device. It publishes another signed event. NIP-09 defines that event as kind:5, a deletion request that points to one or more events with `e` or `a` tags. The distinction matters. A valid request gives cooperating software enough information to stop serving or displaying an event. It does not make the referenced bytes impossible to retrieve, and it cannot prove that every earlier recipient erased a copy.*

The piece walks through the structural argument: *Kind 5 identifies what the author wants removed* — `e` tags name a specific event ID, `a` tags address a replaceable event by kind + pubkey + d tag, the `k` tag records the referenced event kind. *For an `e` reference, the request is effective only when the referenced event and the kind 5 request have the same public key. A client must check that match before hiding or deleting anything. Without it, anyone could sign a request that makes another author's post disappear from compliant interfaces.* This is the *authorship check* — NIP-09 deletion is itself a signed event, and the verification is the same as for any other Nostr event: same-pubkey-bound.

The second argument: *An `a` reference has a wider scope. Relays should delete every version of that replaceable event up to the deletion request's `created_at` timestamp. Newer versions are outside that request, so the timestamp is part of the boundary rather than decorative metadata.* The third: *NIP-09 says relays should delete or stop publishing matching events. It does not say that a relay can be forced to comply. A relay may never receive the request, may not store the referenced event, or may apply a different retention policy.* The fourth: *The protocol also tells relays to keep publishing the deletion request itself indefinitely. That may sound backwards, but it lets clients that already hold the original event learn that its author later disowned it. Clients are encouraged to rebroadcast the request to other relays that may not have seen it.*

The structural takeaway: *A signature proves authorship, not global deletion. NIP-01 makes every event an independently signed object with an ID derived from its serialized contents. Once an event has been copied, a later signature cannot alter that earlier object. It can only add a new instruction that other software may honor.* The piece concludes: *The practical rule is to treat Nostr publication as durable. Use kind 5 when content should be withdrawn, broadcast it to the relays that received the original, and let clients hide valid targets. But do not put secrets into an event on the assumption that a later deletion request can retrieve every copy. NIP-09 coordinates removal. It does not turn a distributed network into a remote-wipe system.* This is a *cryptographic boundary* in the same sense as Amber 6.6.5: the spec defines what a signed event can do, and the boundary is the same one — the spec cannot reach what the spec's protocol does not own.

### strfry 1.1.3 backs out an epoll teardown guard (Sept 29 newsroom)

The [strfry 1.1.3 explainer](https://nostr-wot.com/news/strfry-1-1-3-backs-out-an-epoll-teardown-guard) is a postmortem of a defensive code change that turned out to cause problems. From the lede: *strfry tagged 1.1.3 on 4 September 2026, eight days after 1.1.2. The release changes none of strfry's own source. Two commits separate the tags and they touch two paths, `CHANGES` and the `golpe` submodule pointer. The first of the two is named `bump golpe to back out uWebSockets change`.*

The `CHANGES` entry is reproduced as it appears in the file: *Revert uWebSockets fix that doesn't apply to release branch and may cause be causing problems.* (sic — the file contains the typo *be causing*). The typo is the lede of the post — a one-line, self-doubting changelog entry that itself becomes a small documentation case study in how to communicate a defensive revert.

The structural argument: *The reverted work reached uWebSockets through pull request #6, merged on 20 July 2026. It added two hunks, both short, both carrying their own explanation in a comment.* The first sits in the dispatch loop in `src/Epoll.cpp`: *if (poll->isClosed()) { continue; }*. Its comment states the reason: a poll closed by an earlier callback in the same batch is still present in `readyEvents`, because its deletion is deferred to `loop->closing`. Dispatching to it would operate on a closed fd of `-1` and run the teardown path a second time. The second is an early return at the top of `WebSocket<isServer>::onEnd` in `src/WebSocket.cpp`: *if (webSocket->isClosed()) { return; }*. That comment sets out the sequence in more detail: `terminate()` can be called from a different poll's callback, and the comment names the slow-client back-pressure cap as a caller that does exactly that. `closeSocket()` sets the fd to `-1` but defers deleting the object, so the stale event still sitting in the same epoll batch re-enters `onEnd`. Without the guard, `disconnectionHandler` fires twice and the socket is closed twice, which the comment describes as double-freeing both the user data and the `WebSocket` itself.

The piece's structural argument: *Both hunks are absent from `45816de8`, and the two files return to the form they had before the merge. Which releases carried it: golpe picked the merge up in `3cbace13` on 20 July, and strfry 1.1.1, tagged the following day, points at that golpe commit. 1.1.2 kept it: its own golpe bump moved uWebSockets from `85d00e24`, the merge commit, to `1ef91686`, a descendant of it. The guard therefore shipped in 1.1.1 and 1.1.2, and 1.1.3 is the first tag in that line without it.*

What did *not* come out: *The fix that led 1.1.2 is untouched. That release's uWebSockets bump carried `1ef91686`, which added a check of the accumulated fragment buffer against `maxPayload` and closed a path where a client could keep appending continuation frames, each one under the per-frame limit, and grow relay memory without a ceiling. `45816de8` is built on top of that commit rather than reverting it, so 1.1.3 still has the fragment check. The epoll teardown guard is the only thing removed.* For an operator, the direction matters: moving from 1.1.1 or 1.1.2 to 1.1.3 removes the guard rather than adding it. The `golpe` pointer changed, so a build has to update the submodule instead of reusing a cached checkout, the same condition that applied to 1.1.2. The lesson is the same as the kind:5 case: defensive code that prevents a real attack class (duplicate teardown) can break other invariants in ways the merge-time test suite does not catch, and the correct response is to back the defensive change out and write a tighter changelog than "fix" — even one with a typo.
