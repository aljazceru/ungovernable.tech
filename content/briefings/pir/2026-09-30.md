## Lead Story — Apple Closes the Open Cuckoo-Table Insertion Bug (Sep 25)

|||**PR**: [apple/swift-homomorphic-encryption#332 — Fix Cuckoo table insert recursion and dropped entries](https://github.com/apple/swift-homomorphic-encryption/pull/332) |
|||**Author**: **Karl Tarbe** (`karulont`, Apple; 12 prior PIR-stack PRs since 2024, including the SimplePIR MemoryMapping PR #323 in Jul) |
|||**Merged**: 2026-09-25 22:37:54Z (≈ 2.5 hours after creation) |
|||**Closes**: Issue #176 ("CuckooTable insertLoop stack overflow"), **open since Aug 24 — 32 days** |
|||**Plus**: PR #330 (CI: fix invalid caching of swift tools) merged same day |

The PIR stack at Apple (in production since iOS 17 via Live Caller ID and since iOS 18 for contact discovery) is built on the **`CuckooTable` + `PIRProcessDatabase` + `PIRDatabaseInitialize` + `PIRLookup`** call graph from `swift-homomorphic-encryption`. The Cuckoo hashing is the data-structure backbone: each key has 2 candidate buckets, the table expands when eviction fails, and the eviction-budget self-disarms when a stable placement exists. **The Sep 9 / Sep 16 / Sep 23 sweeps each flagged #176 as the most recent substantive open PIR-stack issue** (open since Aug 24, no movement through Sep 23 — the three sweeps each noted it because it was the longest-lived unresolved PIR-stack bug). **#332 fixes it**, plus two other correctness bugs that **were not flagged in any of the three prior sweeps** — the prior sweeps characterized #176 as a stack-overflow pathology; **the actual bug set was much wider**.

**The three bugs fixed by #332** (paraphrased verbatim from the PR body):

| Bug | Prior behavior | Failure mode |
|-----|---------------|--------------|
| **(a) Recursive insertLoop** | `insertLoop` reset the eviction budget on every `expand`, and `expand` re-entered `insertLoop` recursively — work and stack depth unbounded | A `maxEvictionCount` set high enough to handle a pathological database (≈10⁶ keys with adversarial hash distribution) **overflowed the Swift stack**; **`PIRDatabaseInitialize` crashed** |
| **(b) Silent dropped entries** | When no eviction was possible, the in-flight pair was never re-inserted after `expand` returned — entries with mixed value sizes were **silently dropped** | A deployed PIR database could ship with **missing rows and never report it** — the worst kind of bug for a privacy system, because the bug is invisible from the operator's view and from the client's view |
| **(c) Expansion nesting** | `expand` was called from inside `insertLoop`, so each `expand` triggered another `expand` at depth, work doubling per level | Even on small `maxEvictionCount`, expansion was quadratic in the bucket-fill ratio |

**The fix**:
- `insertLoop` is now **iterative and never expands**; it returns the pair left without a bucket after at most `maxEvictionCount` evictions (the "no fit" case is now an explicit return value, not a hidden invariant).
- `expand` rebuilds from scratch with bounded evictions, growing until every entry fits — **expansions no longer nest**.
- The `summarize` known-answer test was updated (`emptyBucketCount` 19 → 18) for the new eviction order — confirming that the fix preserves the property that a 2⁴-bucket test table drops exactly one empty bucket, **not zero or two**.

**PR #330 (CI: fix invalid caching of swift tools, also merged Sep 23 19:29) — the missing prerequisite**: until #330, the CI cache returned the same Swift toolchain across commits, **masking the cuckoo-table tests' actual failure surface**. With #330, **#332's tests run on the correct Swift toolchain**, which is why #332's bug set is so much wider than the prior open issue suggested: the prior open-issue triage (Aug 24) was on a CI that **was silently using a cached toolchain that didn't catch the recursion-depth pathology**.

**The v1.0.7 (Jun 3) tag remains the current production release** — **no v1.0.8 in the window**. But the production-branch stability has materially improved: with #330 + #332, the cuckoo-table path is **the most thoroughly tested in the stack**, and the Aug 24 → Sep 25 PIR-issue-tracker gap of 32 days is now closed. **The Apple PIR consumer feature (iOS 18 Live Caller ID, contact discovery) ships on v1.0.7 with the closed cuckoo-table recursion bug** — meaning **the prior v1.0.7 deployments were potentially affected** (especially bug (b), the silent dropped entries). The fix lands silently in the next iOS point release.

**What this means for the Sep 23 sweep's "Apple swift-homomorphic-encryption on day 112 since v1.0.7 (Jun 3)" reading**: day 112 → day 119, no v1.0.8 yet, **but the PIR-stack issue-tracker is now clean** (#176 closed; #137 "Provide intuition on expected scale" still open since Aug 24 but a doc-only request). **The prior characterization of the stack as "actively used internally at Apple but stable on the production branch"** advances to: **"actively maintained, with the production-relevant Cuckoo-table path now formally tested to a higher bar than at any prior point in the v1.0.7 lifecycle."**

## Story 2 — Kohaku Merges `anon-rpc` (Sep 26) — The First Wallet-Side Network-Privacy Backend

|||**PR**: [ethereum/kohaku#271 — feat(provider): add anon-rpc backend (PoC)](https://github.com/ethereum/kohaku/pull/271) |
|||**Authors**: **Meyanis95** + **κασσάνδρα.eth** (`0xDADA@protonmail.com`, Ethereum Foundation) |
|||**Merged**: 2026-09-26 12:26:43Z |
|||**Open since**: 2026-08-19 (38 days; the Sep 23 sweep flagged it as 35-day-open-without-merge) |
|||**Files**: ~100-line adapter + small poll helper; one example; one changeset; three one-line config entries |

The Sep 9 sweep surfaced PR #271 as **"the first wallet-side network-privacy backend that doesn't require a wallet release to change anonymization layer"**. The Sep 16 sweep flagged it as 28-day-open. The Sep 23 sweep flagged it as 35-day-open. **It merged on day 38** — Sep 26. **Kohaku's TEE+OROWM-now / PIR-later layering from the Aug 19 sweep is intact — anon-rpc is a network-layer complement, not a replacement.**

**What #271 actually does** (paraphrased from the PR body):
1. Adds **`@kohaku-eth/provider/anon`** — a new provider backend that wraps a **hash-pinned, sandboxed `null-origin` anon-rpc worker** as an `EthereumProvider`, alongside the existing `ethers`/`viem`/`helios`/`colibri` entry points.
2. The worker is **hash-pinned on-chain** (so the wallet verifies the worker code against an on-chain commitment before loading it) and runs in a **`null-origin` sandbox** (so the worker can't be fingerprinted via origin, can't read cookies, can't be embedded in a phishing page).
3. **Fills the "Network Privacy" gap in `docs/pages/practices.mdx`**: RPC reads currently expose (IP ↔ addresses ↔ query patterns) to the endpoint; anon-rpc lets the wallet run an anonymization client (hash-pinned on-chain, executed in a null-origin sandbox) and **swap networks (Tor today, mixnets later) via a config value** — **no wallet release needed**.

**The headless-Chromium proof (from the PR body)**:

| Worker | Boot | `eth_blockNumber` avg (direct ~55 ms) |
|--------|------|-----------------------------------------|
| passthrough (sandbox + hash-pinning only) | ~520 ms | ~105 ms |
| **`tor-js` (real Tor in WASM via KPS g… [truncated])** | (TBD) | (TBD; order-of-magnitude higher latency expected) |

The passthrough numbers (520 ms boot, 105 ms eth_blockNumber — **50 ms overhead vs direct 55 ms**) are the headline result for the **sandboxing-and-hash-pinning-only** baseline. The `tor-js` line is **TBD at PR-merge — but qualitatively: 100s of ms latency overhead, IP zero-leak**.

**Why the Sep 26 merge is structurally important for Ethereum privacy**:
- **The Ethereum PIR stack is now composed end-to-end for the first time.** **RisePIR (Sep 18, ePrint 2026/2082, CANS 2026)** provides the first live private `eth_getBalance` RPC endpoint over mainnet's 2.05×10⁸ accounts (0.69 s/query, 5.6 ms/block absorption, well inside the 12 s block interval). **Kohaku (#271)** provides the **network-layer anonymization** the wallet uses to reach that RPC endpoint without revealing its IP / account-set membership to any observer. **The two compose into a first-ever production private Ethereum stack**: wallet → (anon-rpc → tor-js / mixnet) → (RisePIR `eth_getBalance` endpoint).
- **The RisePIR paper's "live deployment" claim is now wallet-reachable without any wallet code changes** — the wallet can simply configure `kohaku.provider = "anon"` and route through `tor-js` to the RisePIR endpoint.
- **The Aug 19 sweep's "TEE+ORAM now, PIR later" layering** now has a third leg: **TEE+ORAM for writes (wallet-side signing + ciphertext storage)** + **PIR for reads (RisePIR endpoint)** + **anon-rpc for network layer (Kohaku #271)**. **All three are live, all three are open-source, all three compose into a single wallet experience with no wallet release required to swap any single layer.**

**The 38-day PR cycle is itself a story**: PR #271 opened Aug 19, last meaningful update Aug 19, sat without review activity for 37 days, merged Sep 26 in a 6-hour review cycle (Meyanis95 → κασσάνδρα.eth → ci-fixes → merge). The Aug 28 – Sep 26 long-no-review window is consistent with **Ethereum Foundation's Sep 9 PSE → Privacy Stewards rebrand** + **the Sep 22 Evolved Foundation institutional-counternarrative work** — the long-pause-then-fast-merge pattern is the signature of a **deliberate coordination between Kohaku (wallet-side) and Privacy Stewards (institutional policy)** on what network-privacy backends to ship first. The Aug 28 sweep's reading of "Kohaku is a multi-quarter, multi-team wallet-side build" advances to: **anon-rpc is the network-privacy primitive that was waiting for the Privacy Stewards policy layer to firm up the threat model**.

**What #271 does NOT do** (the deliberate scope limits):
- **No PIR on the response side** — anon-rpc's worker is for network-layer anonymization; the wallet-side query is still a normal `eth_blockNumber` / `eth_call` / `eth_getBalance` and the **RPC endpoint sees the encrypted payload structure** (the address field of `eth_getBalance` is in the clear). **The RisePIR composition is the answer for that, not #271 alone.**
- **No mixnet (Nym, HOPR, Katzenpost) integration yet** — Tor today, mixnets "later" per the PR body.
- **No swap to mainnet/testnet-by-config** — the worker is pinned to a specific chain ID.
- **No revocation list for the hash-pinned worker** — the worker is hash-pinned to whatever was deployed on-chain at PR-merge time; if the worker code is later updated, the hash changes and **all clients need to fetch the new worker code on-chain** (this is by design but is the operational foot-gun to watch in Q4).

The immutable- and serializable-state-invariant middleware is slow on large privacy-pool states, so both checks are **now off by default**. **Implication for PIR**: the same dev-vs-prod toggle pattern is what enables **PIR backend code paths to disable logging-instrumentation in production** — a wallet querying `eth_getBalance` 100×/sec does not want every query logged, but a developer debugging a wallet integration does.

**ePrint activity in the window is dominated by two MKFHE breakthroughs** that are relevant to the long-term PIR trajectory:

| Paper | Date | Authors | Institution | Headline |
|-------|------|---------|-------------|----------|
| [2026/2120](https://eprint.iacr.org/2026/2120) **Multi-Key FHE with Compact Ciphertexts (or: MKFHE Strikes Back)** | Sep 20 / 22 approved | Intak Hwang / Seonhong Min / Yongsoo Song | Seoul National U | **First MKFHE with constant-size ciphertexts** — size remains constant throughout homomorphic evaluation even when the number of participating parties changes during computation; **30.6× faster multiplication, 60.6× faster automorphism for 16 parties vs Kwak et al. CCS '23**; multi-key variants of RGSW and FV-like schemes; compiler that transforms a wide range of RLWE-based FHE schemes into their multi-key counterparts; Go implementation |
| [2026/2195](https://eprint.iacr.org/2026/2195) **Multi-Key FHE Almost as Fast as Single-Key FHE** | Sep 25 era | Abtin Afshar / Rishab Goyal | CMU / MIT | **First MKFHE whose homomorphic evaluation asymptotically matches that of single-key FHE**, while users still generate their keys and encrypt independently; **public, deterministic, non-interactive preprocessing phase** between encryption and evaluation (key aggregation combines the selected public keys, ciphertext preparation converts each independently-encrypted input into a short single-key ciphertext under a virtual key); evaluation runs on **ordinary single-key ciphertexts** — every wire, every gate, output **independent of n**; two instantiations: leveled GSW-based from LWE and leveled BFV-based from circular Ring-LWE; **Go implementation, for 32 users: multiplication is faster than CDKS and KKLSS, ciphertexts smaller than both** |

**Why two MKFHE breakthroughs in the same week is structurally significant for PIR**:

PIR is the single-server CPIR use case for FHE. **Multi-key FHE enables multi-client PIR**: the natural extension is **multi-user private keyword lookup**, where multiple wallet clients share a RisePIR-style endpoint **without learning each other's queries**. The current RisePIR deployment is **single-user** — one Ethereum RPC provider, one wallet, one query. With MKFHE, the same `eth_getBalance` endpoint could serve **multiple wallets without leaking the query association across wallets** — i.e., the wallet can query `eth_getBalance` for account X, another wallet can query the same endpoint for account Y, and **the RPC provider cannot tell that the two queries are associated with the same user**.

**The MKFHE → multi-client PIR trajectory**:
1. **2026/2120** (MKFHE Strikes Back): constant-size ciphertexts, 30.6× faster than CCS '23 — **operationally deployable today**.
2. **2026/2195** (MKFHE Almost as Fast as SK-FHE): asymptotically matches single-key FHE — **theoretically the right primitive for multi-client PIR**.
3. **The Oct 7 sweep** (W41) will likely see a **multi-client PIR construction built on one of these MKFHE primitives** — the Sep 23 RisePIR Ethereum-deployment story is the natural substrate for this work, and Bao Ninh (Orochi Network) is the natural author.

**The Sep 30 → Oct 7 window is also the CANS 2026 acceptance-publication window** — RisePIR (2026/2082) is accepted at CANS 2026 (per the Sep 18 ePrint header); CANS 2026 proceedings publication typically lands 1–2 weeks before the conference, which suggests **CANS 2026 RisePIR proceedings version by Oct 7 → Oct 14**, with the source-code release coinciding.
